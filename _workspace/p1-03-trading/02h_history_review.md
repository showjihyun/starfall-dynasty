## 결론 (한 줄)

**p1-03 은 Historical Event 를 하나도 만들지 않는다.** 거래 도메인 이벤트는 Level 0 이고 역사 러너에서 `Unjudged` 로 지나간다. 대신 (a) 거래 payload 가 미래 규칙·Biography 가 쓸 "그 시점의 사실"을 빠짐없이 싣고, (b) 시장 화면이 **기존** `MINERAL_DISCOVERED` 를 읽어 보여 주는 것(역사 → 플레이 방향)으로 이 슬라이스의 역사 연결을 삼는다. 새 규칙·새 `rule_version`·새 마이그레이션·`starfall-history` 코드 변경은 없다.

## 1. 거래가 Historical Event 를 낳아야 하는가 — 아니다

### 1.1 판단 기준

historical-engine §8 의 세 질문(누가 발견하나 / 발견한 사람이 무엇을 할 수 있나 / 그 행동이 다시 도메인 이벤트를 만드나)과 HSE §89 의 10종 밖 타입에 대한 문턱(스펙 + 레지스트리 + "이어지는 플레이" 정의). p1-02 디자인 §4.2 가 같은 기준으로 광맥 고갈·개인 첫 획득을 Level 0 으로 둔 선례를 따른다.

### 1.2 후보와 판정

| 후보 | 판정 | 이유 |
|---|---|---|
| 모든 거래(`*_SOLD`/`*_TRADED` 류) | **Level 0** | HSE §9 "10톤 채굴 = 일반 이벤트" 와 같다. 수량이 거래 수에 비례하는 기록은 역사가 아니라 원장이다 |
| 광물별 성계 첫 판매(`FIRST_SALE`) | **기록 안 함** | (1) 이 슬라이스에서 첫 판매자는 거의 항상 발견자다 — 발견 몇 초 뒤 같은 사람이 같은 광물을 판다. `MINERAL_DISCOVERED` 와 정보가 겹치고 "발견"의 무게를 나눈다(p1-02 §4.2 의 "광맥 첫 추출" 기각과 같은 논리). (2) 고정가·무한 유동성(designer 안이 이쪽이라면) 시장에서 첫 판매는 세계에 아무것도 바꾸지 않는다 — 다른 플레이어가 그 흔적으로 할 수 있는 행동이 없다. (3) 상한이 월드당 4 건이라 소음은 아니지만, 답 없는 §8 질문을 가진 타입을 10종 밖으로 추가하는 비용(레지스트리·계약·ADR·golden)이 이득보다 크다 |
| 최대 단일 거래·누적 거래량 기록(`TRADE_RECORD`) | **기록 안 함** | 기록이 갱신될 때마다 새 사건(원칙 5 — 옛 것을 고치지 못한다)이라 소음이 되고, 본질은 **순위표**다. 순위표는 `domain_events` 에서 다시 만들 수 있는 프로젝션이지 사실이 아니다. 또 "쪼개 팔기/몰아 팔기" 로 조작 가능한 기준을 역사에 새긴다 |
| 시장 붕괴·가격 충격(`MARKET_CRASHED`) | **이번엔 불가, 후보로 남김** | 진짜 후속 플레이가 있는 유일한 거래 계열 사건(차익·책임 추궁·세력 개입)이다. 그러나 (a) 동적 시장은 GDD §37 MVP-2 의 "시장" 범위다, (b) 여러 거래를 묶는 집계 규칙(Correlation Window)이 필요하고 이는 ADR-0014 "다시 검토할 조건 (a)" — 코어 모양(이벤트 1건 → 결과) 재검토 — 를 연다. 고정가 슬라이스에서는 조건 자체가 발생하지 않아 테스트가 `0 == 0` 이 된다(CLAUDE.md 검증의 규율) |
| 유물 거래(소유 이력) | 이번 범위 밖, 후보로 남김 | GDD 677 "유물은 거래 가능한 희귀 자산". 유물의 소유 사슬은 Object History(HSE §85)라 역사가 된다. `ARTIFACT_DISCOVERED` 가 생긴 뒤의 일 |
| 플레이어 간 계약 거래 | 이번 범위 밖 | 그때는 10종 안의 `CONTRACT_SIGNED`/`CONTRACT_BROKEN` 이 맡는다(p3) |

### 1.3 "다른 플레이어가 흔적을 발견할 수 있는가"(GDD §36 핵심 테스트) — 역사가 아니어도 된다

거래의 흔적은 이 슬라이스에서 역사 기록이 아니라 **시뮬레이션 상태**로 남는 것이 맞다. designer 가 시장에 유한 재고·수요(결정적 회복)를 둔다면 "누가 Starfall Glass 를 잔뜩 팔아 값이 내려갔다" 가 다른 플레이어에게 보이는 흔적이다 — 그것은 사실(Fact)이고 역사 판정을 거칠 필요가 없다. 고정가라면 흔적이 없고, 그것도 이 슬라이스의 정직한 상태다.

### 1.4 그래도 이 슬라이스가 역사와 이어지는 방법 — 읽는 쪽으로

p1-02 디자인 §4.3 이 이미 적었다: "p1-03 거래 | 발견된 광물이 처음으로 값을 가진다. 발견자가 첫 공급자다". 이것은 **역사 → 플레이** 방향이다.

- **권고(표현 계층, 선택)**: 시장 화면의 광물 행에 기존 `MINERAL_DISCOVERED`(클라이언트가 이미 BACKFILL/LIVE 로 받아 가진 것)의 발견자 표지를 함께 보인다(예: "발견: Pilot-3f9a"). 서버·DB 변경 없음, 새 메시지 없음. 다른 플레이어가 "이 광물을 처음 찾은 사람"을 거래 순간에 다시 마주친다 — GDD §36 핵심 테스트의 두 번째 접점이다.
- **금지(정본 경로)**: 시장의 가격·허용 여부 같은 **판정이 역사 표를 읽으면 안 된다.** 역사는 커밋 뒤 비동기(ADR-0014 §7)이므로, "발견된 광물만 거래 가능" 이나 "발견 직후 프리미엄" 을 역사 표에 기대면 같은 명령의 결과가 러너 지연에 따라 달라진다 — sim 의 결정성(원칙 9)이 깨진다. 그런 규칙이 필요하면 sim 자신의 상태(예: 이 월드에서 채굴된 적이 있는 광물 집합)로 판정한다.

### 1.5 지금 해 둬야 나중에 고칠 수 없는 것 — 거래 payload

역사는 과거를 다시 계산하지 않고(원칙 5), 판정은 payload 만 읽는다(ADR-0014 §1 "라이브 WorldState 를 읽지 않는다"). 미래 규칙(시장 충격 @1, Biography 의 "첫 판매" 줄, p1-04 의 화물·약탈 연결)이 쓸 사실이 payload 에 없으면 **그 이전 거래는 영원히 그 판정에서 빠진다.** 그래서 거래 도메인 이벤트에 아래를 요구한다(이름은 architect 가 정한다).

| 필드 | 이유 |
|---|---|
| envelope `actor_id`(필수, null 아님) | 누가 — Biography·참여자 |
| `ship_id` | p1-02 와 같은 이유로 함선 Biography 의 줄 |
| *(v1 주: 디자인이 동적 시장을 골랐으므로 §3.1 의 갱신 목록이 이 표보다 우선한다)* | |
| `star_system_id`, 시장/정거장 id | 어디서 — 미래 규칙의 location |
| `mineral_id`, `quantity_kg`(정수) | 무엇을 얼마나 |
| **적용 단가와 총액(정수 크레딧)** | 가격이 나중에 동적이 되면 "그때 값" 은 payload 말고는 복원할 곳이 없다. 가격표 데이터를 판정 입력으로 쓰면 데이터 변경이 재생 결과를 바꾼다(ADR-0014 §5 "다른 데이터 값을 판정 입력에 넣지 않는다") |
| 가격 근거 식별자(가격표 버전 또는 규칙 버전 문자열) | 감사 — 같은 거래가 왜 그 값이었나 |
| 거래 방향(팔기/사기) — 사기를 넣는다면 | 같은 이벤트 타입을 쓸 때 판정이 갈라질 축 |
| 거래 후 시장 상태(동적 시장이라면, 예: `market_stock_after`) | `deposit_remaining_after_kg` 와 같은 역할 — 미래의 "충격" 판정이 세계 상태를 읽지 않게 |

지갑 잔액 같은 사적 경제 상태는 역사에 필요 없다(원장·감사 쪽 판단은 server/architect 몫).

## 2. 거래 이벤트가 역사 러너에 들어갈 때 — `mineral-discovery@1` 의 결정성·재생을 깨는가

코드로 확인한 현재 동작과 그 위에서의 판정.

| 점검 | 현재 코드 | 판정 |
|---|---|---|
| 새 타입의 해석 | `decode_row`(`persistence/src/history.rs` ~948): `event_type != MINERAL_MINED` 이면 좌표만 담아 `DomainEvent::unjudged` — payload·`schema_version` 을 보지 않는다 | **안전.** 거래 payload 의 모양·버전과 무관하게 러너가 멈추지 않고, 코어는 빈 결과를 낸다(`core.rs` judge 의 2단계). 기존 규칙의 출력에 영향 없음 |
| 순서·역행 검사 | 코어는 **모든 타입**에 `(tick, sequence)` 엄격 증가를 요구(같아도 오류). `domain_events` 에 `UNIQUE (world_id, tick, sequence)`(0001:37) | **조건부 안전.** 한 거래 명령이 이벤트를 여러 개 낸다면(예: 인벤토리 변화 + 크레딧 변화 분리) 각각 **다른 `sequence`** 를 받아야 한다. DB UNIQUE 가 막아 주므로 같은 좌표 둘이 커밋될 수는 없다 — 대신 영속화가 실패해 월드가 멈춘다. → 스펙 요구 R-2 |
| 커밋 경로(단일 작성자 전제) | 러너는 커서 뒤·`tick <= worlds.last_tick` 만 읽는다. 전제: 영속화 단일 작성자·tick 오름차순(ADR-0013 §6, ADR-0014 §2) | **조건부 안전.** 거래가 tick 배치 밖(REST 핸들러가 자기 트랜잭션으로 `domain_events` INSERT 등)으로 쓰이면 커서보다 옛 tick 이 나중에 끼어들 수 있고, 러너는 그 행을 영원히 보지 못한다. 지금 규칙엔 `Unjudged` 라 결과가 같지만, **러너와 재생의 입력 집합이 달라지는** 구조가 생기고 미래의 거래 판정 규칙에서 "러너 결과 ≠ 재생 결과" 가 된다. 또 원칙 1·ADR-0013 의 "돈·아이템 변경 = 한 트랜잭션 + 도메인 이벤트" 가 tick 배치가 아닌 두 번째 작성자를 만든다. → R-1 |
| 판정 입력 오염 | 거래가 `MINERAL_MINED` 를 내면 발견 판정 대상이 된다 | **치명 가능.** "사기"(시장이 플레이어에게 광물을 판다)를 넣고 그 지급을 채굴 이벤트로 표현하면 **구매자가 그 광물의 최초 발견자로 영구 기록**된다. → R-3 |
| 재생 도구(`history-replay`, `replay_and_compare`) | 워터마크까지 전체 `domain_events` 를 빈 상태에서 재판정, `Unjudged` 포함 | **안전.** 거래 행은 `domain_events_replayed` 만 늘린다. 단, 검증의 규율상 p1-03 의 재생 검증은 **거래 행이 실제로 섞인 월드**에서 돌아야 의미가 있다 → R-4 |
| golden(`server/crates/history/tests/data/golden/`) | 규칙 파일 해시 + 고정 입력열 출력 | **영향 없음.** 규칙 파일·코어 불변. golden 재생성 금지(바뀌면 그것이 결함 신호) |
| 지연 예산(ADR-0014 §7, NOTICE p95 ≤ 1 s) | 러너가 `Unjudged` 행도 읽고 커서를 전진 | 30~100 명 규모에서 무시할 만하다(행당 판정 O(1), `BATCH_SIZE` 500). 단 Unjudged 행마다 커서 전진 트랜잭션을 따로 커밋하는 구조라면 거래 폭주가 발견 알림을 늦출 수 있다 — p1-03 qa 에서 **거래가 섞인 상태의** 발견 NOTICE 지연을 한 번 잰다(R-5) |
| 세션 시작 메시지 수(ADR-0014 §6 BACKFILL 32 트리거) | 트리거는 "세션 시작 3 건 + 여유" 를 가정 | p1-03 이 세션 시작에 지갑·시장 상태 메시지를 더하면 여유가 줄어든다. 지금 BACKFILL 상한이 4 건이라 실제 위험은 없지만 ADR-0014 §6 의 가정(시작 메시지 3 건)이 낡는다 → R-6(기록만) |

### 2.1 스펙·계약에 넣어 달라는 요구 (architect3)

- **R-1** 거래의 크레딧·인벤토리 변경과 그 도메인 이벤트는 기존 tick 배치(ADR-0013 §2 "tick 배치가 곧 outbox")로만 커밋된다. 두 번째 `domain_events` 작성자를 만들지 않는다. 스펙에 이 한 줄과 ADR-0013 §6 참조를 둔다.
- **R-2** 한 명령이 도메인 이벤트를 여러 개 내면 각자 고유 `sequence` 를 받는다(sim 의 tick 안 발행 순번, ADR-0007 §4). 가능하면 거래 1건 = 도메인 이벤트 1건(인벤토리 차감·크레딧 증가를 한 payload 에)을 권한다 — 원자성이 이벤트 경계와 일치하고, 미래 판정 규칙이 두 이벤트를 짝지을 필요가 없다.
- **R-3** 거래는 `MINERAL_MINED` 를 내지 않는다(사기 포함). 계약 레지스트리에 거래 이벤트를 새 타입으로 두고, 스펙 불변식에 "인벤토리 증가 경로가 채굴 아닌 경우 `MINERAL_MINED` 를 남기지 않는다" 를 적는다. qa 반례: 시장에서 산 광물(사기를 넣는 경우) 뒤 그 광물의 `MINERAL_DISCOVERED` 가 생기지 않음 — **분모로 구매 이벤트 ≥ 1 을 먼저 단언**.
- **R-4** 역사 회귀 AC 하나: 발견 ≥ 1 과 거래 ≥ 1 이 **섞인** 새 월드에서 (a) 러너가 멈추지 않고 커서가 마지막 거래 좌표 이상까지 전진, (b) `history-replay` 가 일치, (c) 출력에 "재생한 행 중 거래 타입 수 ≥ 1" 을 찍는다(0 이면 FAIL). (d) 거래 행에 대해 `historical_event_sources` 0 행 — 분모(거래 행 수)와 함께.
- **R-5** (측정, 실패 경계 아님) 거래가 섞인 부하에서 `MINERAL_MINED` 커밋 → `HISTORICAL_EVENT_NOTICE(LIVE)` 지연 p95 를 한 번 기록한다.
- **R-6** ADR-0014 §6 의 "세션 시작 3 건" 가정을 p1-03 의 실제 시작 메시지 수로 갱신(개정 메모 한 줄). 트리거 32 자체는 유지 가능.
- **R-7** 거래 payload 필드: §1.5 표.
- **R-8** 스펙의 "범위 제외/기록하지 않기로 한 것" 에 §1.2 표의 판정(특히 시장 붕괴·유물 거래를 **다시 볼 조건**: 동적 시장(MVP-2) + 집계 규칙 ADR, `ARTIFACT_DISCOVERED`)을 옮긴다. 스펙의 역사 절이 "없음" 한 줄이면 다음 슬라이스가 같은 논의를 처음부터 한다.

- 역사 오라클(월드·성계·광물별 최초 `quantity_kg > 0` `MINERAL_MINED` 의 actor)은 `MINERAL_MINED` 만 읽으므로 판매와 무관하다. 인벤토리를 다 팔아도 발견은 그대로다(발견은 보유가 아니라 최초 추출 사실). **조건**: 어떤 경로도 판매·구매를 `MINERAL_MINED` 로 표현하지 않는다(R-3). 사기를 넣으면 이 조건이 오라클의 전제가 된다.
- I-54 를 `Σ MINED − Σ SOLD` 로 바꾸는 데 동의. **I-55 보존 법칙도 바뀐다**: `Σ 인벤토리 + Σ 광맥 잔량 = Σ 초기 매장량 + Σ 회복량` 은 판매가 인벤토리를 시장으로 빼는 순간 깨진다 → 우변에서 `Σ SOLD` 를 빼거나(시장 = 소멸점) 시장 재고를 좌변에 넣는다. 사기를 넣으면 `+ Σ BOUGHT` 도. 고치지 않으면 p1-02 AC-5(a) 가 p1-03 월드에서 FAIL 한다.

**확인 3 — `MINERAL_SOLD` 의 consumers 에 history 를 넣지 않는다: 동의.** 러너는 그 타입을 해석하지 않는다(좌표만). 소비자로 올리면 커버리지 스크립트가 history 경로에서 그 타입의 디코딩을 찾게 되고, 맞추려면 이름만 등장하는 거짓 소비 코드가 생긴다(ADR-0014 §6 의 NOTICE 생산자 판정과 같은 논리). 미래 규칙이 판정하게 되는 날 `consumers` 에 history 를 더하는 것이 그 규칙 ADR 의 일부다.

## 3. designer3 초안·architect3 스펙 검토

### 3.1 designer3 디자인(`docs/design/p1-03-trading.md`) — §4·§5·§9.3 중심

**결론: §5 "이번 슬라이스엔 Historical Event 없음" 에 동의한다. `MARKET_CRASH` 는 p2 후보로 넘긴다.**

v0(§1.2) 는 "고정가면 붕괴 조건이 발생하지 않는다" 를 근거 하나로 썼는데, 디자인은 **D 안(구간형 포화 + 회복)** 을 골랐다 — 동적 시장이 이번 슬라이스에 들어온다. 그 근거는 빠지고, 결론은 아래 이유로 유지한다.

1. **같은 흔적이 이미 사실로 보인다**(디자인 §5.2-1). 눌린 시세(UI-05)·마지막 거래 줄(UI-12)은 시뮬레이션 상태이고 모든 접속자에게 보인다. 역사로 한 번 더 쓰면 새 플레이가 아니라 중복이다.
2. **읽는 자리가 없고 배너는 소음이다**(§5.2-2). 30 명 세션 초반에 모든 광물이 한 번은 바닥을 친다(§3.6) — 처음 10 분에 Level 1 배너 4 개가 Level 2 발견 배너의 무게를 깎는다.
3. **(history 추가) 제안된 판정식이 이 시장의 성질과 충돌한다.** 후보 조건 "한 판매가 b=0 → floor_band" 는 **한 번에 판 사람만** 붕괴의 주인으로 만든다. 그런데 디자인 §3.4-1 은 "나눠 팔아도 대금이 같다" 를 핵심 성질로 둔다. 14,000 kg 을 한 번에 팔면 역사에 남고 7,000 kg 씩 두 번 팔면 안 남는다 — 대금에는 차이가 없는데 **역사에만 차이가 생기는 숨은 규칙**이고, 기록을 원하거나 피하려는 플레이어가 그 경계를 조작할 수 있다. 정직한 붕괴는 **여러 판매(여러 판매자일 수 있다)를 창으로 묶는 집계 사건**이고, 그 순간 ADR-0014 "다시 검토할 조건 (a)"(집계 규칙 → 코어 모양 재검토)가 열린다. "누가 무너뜨렸나" 가 여러 사람에게 나뉘는 것은 바로 p2 Claim(시장 조작 주장)의 자리이기도 하다. 그래서 이 규칙은 p2 의 집계 규칙 ADR 과 함께 설계해야 하고, 지금 단일 판매 규칙으로 넣으면 원칙 5 때문에 나중에 고칠 수 없는 모양을 역사에 새기게 된다.
4. HSE §89 의 10 종 밖으로 나갈 이유가 1~3 으로 사라진다.

**문을 열어 두는 payload — 동의하고 셋을 더 요청한다**(디자인 §9.3, 스펙·계약 R-7 의 갱신):

| 요청 | 이유 |
|---|---|
| **`star_system_id`** 를 payload 에 직접 | `market_id` → 성계는 데이터 파일 조회다. ADR-0014 §5: 판정 입력에 데이터 표의 값을 넣지 않는다. `MINERAL_MINED` 가 이미 `star_system_id` 를 싣는 것과 같은 규칙 |
| **바닥 정보** — `floor_price_cr_per_kg` 또는 `band_before`·`band_after`·`floor_band` (또는 `saturation_cap_kg`) 중 하나 | 디자인 §5.1 의 조건 "`price_after == floor price`" 는 바닥값을 알아야 하는데, 지금 §9.3 목록에는 `base_price` 만 있고 바닥값은 `price_floor_pct`(데이터)에서 계산해야 한다. `base_price` 를 실은 이유("데이터가 바뀌어도 이벤트만으로 판정")가 바닥에도 똑같이 적용된다. 집계 규칙이라면 포화 상한이 필요하다 — 가장 일반적인 것은 `saturation_cap_kg` |
| (선택) 가격 규칙 식별 문자열 | 가격식 자체(§3.3)가 바뀌면 같은 `price_before/after` 라도 뜻이 달라진다. 데이터 스키마에 버전 문자열이 생기면 함께 싣는다. 없으면 생략 가능 — 위 두 항목이 판정에는 충분하다 |

`wallet_before/after_cr`·`inventory_before/after_kg` 는 역사에 필요 없지만 보존 법칙 감사에 쓰이므로 반대하지 않는다(경제 쪽 판단).

**p2 로 넘기는 결정에 대한 history 기본값**(디자인 §5.2-4 "소급 판정은 history 가 정한다" 에 대한 답 — p2 ADR 에서 확정):
- **소급하지 않는 것을 기본값으로 둔다.** 새 규칙의 소비자 커서(`history_cursor(world_id, consumer)` — 소비자별 행이 이미 가능하다)는 **규칙 활성화 좌표**에서 시작하고, 그 좌표를 ADR 에 남긴다. 이유: p1-03 월드는 플레이테스트 월드이고, 그때 아무도 보지 못한 Level 1 사건이 p2 Chronicle 첫 화면을 채우면 "역사" 가 아니라 소급 데이터 덤프가 된다. 소급을 택하더라도 원칙 5 위반은 아니다(기존 기록을 고치지 않는다) — 그래서 payload 를 지금 완전하게 두는 것이 옳다. 선택지를 남겨 두는 비용이 가장 싸다.
- **멱등 키에 서수(`crash_ordinal`)를 쓰지 않는다.** 서수는 "규칙이 어디서부터 셌는가" 에 달려 있어, 소급 여부·재구축 시작점에 따라 같은 사건의 id(UUIDv5)가 달라진다. 사건을 여는 판매의 좌표에서 키를 만든다(예: `"{market_id}/{mineral_id}/{바닥 진입 판매의 tick}:{sequence}"`). 집계 규칙이면 창을 여는 첫 이벤트의 좌표.
