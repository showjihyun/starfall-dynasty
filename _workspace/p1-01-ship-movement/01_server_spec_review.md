## 동의하는 결정

### 와이어는 정수 양자화, 데이터는 SI 실수 (ADR-0009 §2)

동의한다. 특히 **"결정성 검증이 바이트 비교가 된다"**가 결정적인 근거다. 실수를 쓰면 AC-8이 "충분히 가까운가"를 판정하는 별도 규칙을 필요로 하고, 그 허용 오차가 정확히 이 테스트가 잡아야 할 차이를 덮는다. p0-02에서 `occurred_at`을 문자열로 비교한 것과 같은 결의 선택이다.

데이터 테이블을 예외로 둔 것도 동의한다 — 와이어를 왕복하지 않고, 서버 내부 상태도 같은 SI `f64`라 변환 지점 자체가 없다. **다만 이 예외가 계약 테스트에 부딪힌다** → B-2.

### 초월함수 금지 (ADR-0010 §3)

동의한다. 그리고 이것이 이 슬라이스에서 가장 값진 규약이라고 본다 — "결정적"이라는 말이 검증 **가능한 주장**이 되는 이유가 이 한 줄이다. 게인 단위를 `sin(θ/2)`당으로 바꿔 가면서까지 지킨 것도 옳다. 읽기 불편한 것이 대가이고, 데이터 필드 이름(`turn_gain_deg_s_per_sin_half`)이 그 제약을 기억하고 있는 것이 좋은 설계다.

**금지 목록에 빠진 것이 있다** → B-4.

### 수학·해시 크레이트 금지 (ADR-0010 §3·§4, A-7)

동의한다. `glam`·`nalgebra`는 버전에 따라 내부적으로 `mul_add`나 SIMD 경로를 쓸 수 있고, 그러면 결정성 보장이 우리 것이 아니라 그 크레이트의 릴리스 정책이 된다. 해시도 같다.

**`Vec3`/`Quat`를 손으로 쓴다.** 필요한 것은 더하기·빼기·스칼라곱·내적·외적·노름·정규화·Hamilton 곱·켤레·회전 — 150줄 안쪽이고, `starfall-sim`의 의존성 1개(=`starfall-contracts`)를 그대로 유지한다. 해시도 손으로 쓴다(splitmix64류 + 고정 입력 테스트). **크레이트 요청은 없다.**

### 전체 스냅샷 브로드캐스트, 델타·관심 영역 없음 (ADR-0011 §1)

동의한다. "델타의 실패 양상은 손실이 아니라 **오염**"이라는 서술이 정확하다. 31척에서 살 이유가 없고, 도입 트리거가 **40척**이라는 숫자로 남은 것이 이 ADR의 값이다.

### 큐가 아니라 "마지막 것이 이긴다 + 이월" (ADR-0011 §4, A-1)

동의한다. **입력이 절대 상태가 된 순간 큐는 해가 된다** — 늦게 온 옛 조준을 뒤늦게 재생하게 된다. 그리고 속도 핵 방어가 코드가 아니라 **데이터 모양**으로 이뤄지는 것이 p0-02의 I-22(거부는 관측 가능하다)와 같은 결이다. 쌓아 둘 것이 없으므로 10배로 보내도 갈 곳이 없다.

거부를 유지하고(I-33) 이월이 그것을 안전하게 만든다는 논증도 맞다. `STALE_INPUT`으로 답하는 것(A-3)도 동의한다 — I-15가 p0-02의 손실 계측 기준이고, 이동 명령만 예외로 두면 이 슬라이스에서 계측기가 눈이 먼다.

**단, 세 규칙(마지막 승 / 단조 `input_seq` / 이월)의 상호작용이 한 경우에 정의되지 않았다** → B-8.

### 30초 잔류·재개, 짝짓기를 `ship_id`로 (ADR-0011 §6, A-5)

동의한다. "되찾는 것은 월드 객체인 함선이지 연결 상태가 아니다"가 ADR-0005 §3과 충돌하지 않는 정확한 구분이다. 그리고 **짝짓기 기준이 `correlation_id`에서 `ship_id`로 바뀐다는 것을 architect가 먼저 발견해 QA에 통보한 것**(A-5)이 이 문서에서 가장 값진 한 줄이다 — 그게 없었으면 QA의 p0-02 SQL이 조용히 틀린 답을 냈을 것이다.

### `SHIP_DESPAWNED.causation_id` 비-null 유지 (A-4)

동의한다. 리더 지시와 다르게 결정하고 이유를 적은 것도 옳은 처리다. "원인을 못 찾았다"와 "원인이 없다"를 구분할 수 없게 되는 것이 널 허용의 진짜 비용이고, 잔류가 언제나 `SESSION_CLOSED`로 시작하므로 원인은 항상 존재한다.

**단 한 경우가 문서에 없다** → B-9.

### 이동은 도메인 이벤트를 만들지 않는다 (I-31, ADR-0007 §1 개정)

동의한다. designer가 독립적으로 같은 결론에 도달하고 숫자(시간당 216만 행)를 낸 것이 근거로 강하다. 그리고 **"기록하지 않는다"는 결정이 표로 남는 것**이 판단이 아니라 규칙이 되는 유일한 방법이다.

### 송신 큐 256 → 64

메모리 근거에 동의한다(세션당 최악 0.94 MB, 31세션 29 MB — 실측). **다만 ADR-0011 §5의 "잘리기까지" 열이 3배 틀렸다** → B-10.

## 수정 요청

### B-1 (차단·계약 변경) 스냅샷이 각속도를 복원 불가능하게 실어 보낸다

**무엇이 문제인가.** ADR-0010 §2의 함선 상태는 각속도를 **둘**로 들고 있다.

- `ω_aim` — 3성분, 월드 프레임. 3단계가 `turn_accel_deg_s2`로 슬루 제한한다.
- `ω_roll` — 스칼라, 전방축 둘레. 5단계가 `roll_accel_deg_s2`로 슬루 제한한다.

그런데 `WORLD_SNAPSHOT`의 `ShipState`에는 `angular_velocity_{x,y,z}_mdeg_s` **3성분 하나뿐**이다(실측: `required` 17필드 확인). ADR-0012 §3은 "`ω_roll`은 월드 각속도에서 전방축 성분으로 분해해 얻는다"고 적었다.

**그 분해는 손실이다.** `ω_aim`이 전방축 성분을 갖지 않는다는 보장이 없기 때문이다 — 2단계의 `ω_t`는 자세 오차 `q_err`에서 나오고, `q_aim`과 `q`의 롤 차이가 있으면 `ω_t`에 전방축 성분이 생긴다. 그러면 클라이언트는 `ω_aim`의 롤 성분을 `ω_roll`로 잘못 귀속시킨다.

**왜 AC-12를 깨는가.** 잘못 분해된 (ω_aim′, ω_roll′)은 합은 같지만 4·5단계가 **두 번의 1차 적분**이라 결과가 다르다. 두 단계의 차이는 2차항 `0.25·dt²·W₂W₁`이고, 최대 각속도 75 °/s에서 tick당 약 **0.06°** — AC-12(b)의 자세 임계 **0.02°의 3배**다. 게다가 두 축의 슬루 한계가 다르므로(220 vs 300 °/s²) 이후 tick에서 발산이 누적된다. **AC-12(e)가 요구하는 "선회 중 스냅샷" 케이스가 바로 이것이고, 지금 계약으로는 반드시 실패한다.**

**요청 (계약 변경):** `ShipState`에 **`angular_velocity_roll_mdeg_s` 1필드를 추가**하고, 기존 3성분의 `description`을 **"`ω_aim` — 자세 제어기의 월드 각속도. 롤은 포함하지 않는다"**로 좁힌다.

- 비용: 함선당 약 26 B → 31척 프레임 15,463 → **약 16,270 B (+5.2 %)**. 세션당 10 Hz에서 151.0 → **158.9 KiB/s**(예산 192의 82.8 %). 40척 트리거는 그대로 유지된다(193.8 → 204 KiB/s로 여전히 40척에서 깨진다).
- 대안(더 싸지만 덜 정확): B-3의 롤 성분 제거를 채택하면 `ω_aim ⊥ fwd`가 **계산 시점에는** 성립해 분해가 거의 정확해진다. 그러나 `fwd`가 매 tick 최대 3.75° 회전하므로 잔차가 남고, 그 잔차는 다시 0.02° 임계와 같은 자릿수다. **정확한 해는 필드 추가뿐이다.**

### B-2 (차단) U-20이 깨진다 — 긴 소수가 아니라 **정수 리터럴** 때문이다

**실측 (스크래치 Rust, serde_json 1.0.151):**

```
1) 긴 소수:  {"a":2165.0635095,"b":-2165.0635095,"c":0.00098,"d":0.0009}
   → equal = true, 재직렬화가 원본과 글자까지 같다
2) number 필드에 정수 리터럴: {"a":192,"b":200,"c":30,"d":140.0}
   → equal = false,  back = {"a":192.0,"b":200.0,"c":30.0,"d":140.0}
4) Value(192) == Value(192.0f64) ?  false      (as_f64() 끼리는 true)
```

`serde_json::Number`는 `PosInt`와 `Float`를 **다른 값으로 취급**한다. 스펙이 걱정한 `2165.0635095`는 문제가 없고(Ryū가 최단 왕복 표기를 낸다), 실제로 깨지는 것은 **스키마가 `"type": "number"`로 선언한 필드에 정수가 적힌 경우**다.

**실측으로 확인한 해당 필드 (지금 fixture·data에 실제로 있다):**

| 타입 | 필드 | 선언 | 적힌 값 |
|------|------|------|--------|
| `SYNC_TUNING` | `egress_budget_kib_s_per_session` | number | `192` |
| `SYNC_TUNING` | `remote_interp_delay_ms` / `remote_extrapolate_max_ms` / `reconcile_smooth_duration_ms` | number | `200` / `250` / `200` |
| `STAR_SYSTEM` | `linger_seconds` / `reconnect_resume_window_seconds` | number | `30` / `30`·`0` |
| `SHIP_CLASS` | `cargo_capacity_t` / `shield` | number | `20` / `100` |

**요청: 비교 방식을 고친다(스펙 §10 U-20의 지시 그대로). 데이터를 정수로 바꾸지 않는다.**

구체안: 계약 테스트의 왕복 비교를 **kind에 따라 나눈다.**

- `command`·`server_message`·`domain_event`(와이어 타입) → **지금 그대로 `Value` 엄격 비교.** 와이어 드리프트를 잡는 것이 이 테스트의 존재 이유이므로 느슨하게 만들지 않는다.
- `data`(데이터 테이블) → 비교 직전에 **양쪽 `Value`를 재귀적으로 정규화**한다: 모든 `Number`를 `as_f64()`로 바꾼 뒤 **정확히(`==`) 비교**한다. 근사 비교가 아니다 — `192` vs `192.5`는 여전히 실패한다.
  - 근거: 데이터 테이블은 와이어를 왕복하지 않으므로(ADR-0009 §2) 요구사항은 **바이트 동일이 아니라 값 동일**이다. `192`와 `192.0`이 다른 값이라고 주장하는 것은 JSON의 사실이지 우리 계약의 사실이 아니다.
  - 이 정규화가 놓치는 것 하나를 기록해야 한다: `"type": "integer"` 필드에서 `10` ↔ `10.0` 드리프트도 함께 통과한다. 그래서 **Rust 타입에서 integer 선언 필드를 정수 타입(`u32`/`i64`)으로 받는 것**을 별도 단언으로 고정한다(정수 타입이면 `10.0`은 역직렬화 단계에서 이미 거부된다).

대안으로 fixture·data에 `192.0`처럼 쓰게 하는 방법도 있지만 **반대한다**: designer가 `30`이라고 타이핑할 때마다 테스트가 깨지고, 실패 메시지가 이유를 설명하지 못한다. 규율을 사람에게 지우는 대신 비교기에 지우는 쪽이 맞다.

### B-3 (차단에 가까움) 2단계가 롤 축 권한을 정하지 않는다

**무엇이 문제인가.** 자세 제어기(2~4단계)는 `q_err = q_aim ⊗ conj(q)`에서 **3축 전부**의 각속도를 만든다. 롤 제어기·오토레벨(5단계)도 전방축을 돌린다. **두 제어기가 같은 축에 권한을 갖는다.**

오토레벨이 켜진 상태를 보자. 5단계가 전방축 둘레로 함선을 돌린다 → `q`의 롤이 바뀐다 → `q_err`에 롤 성분이 생긴다 → 2단계가 그 롤을 **되돌리는** 각속도를 만든다. 두 제어기가 서로를 지운다. AC-4(g)("오버슈트 없이 안착")가 정확히 이 형태로 실패할 수 있다.

이것이 지금 안 터지려면 **클라이언트가 `q_aim`에 함선의 현재 롤을 합성해 넣어야** 한다. 그러면 롤 오차가 0이 되어 자세 제어기가 롤에 개입하지 않는다. 하지만 **그 의무가 어느 문서에도 적혀 있지 않다.** 적히지 않은 의무는 지켜지지 않는다.

**요청: 둘 중 하나를 골라 ADR-0010 §2에 적는다.**

- **(A) 권장 — 2단계에서 롤 성분을 제거한다.** `ω_t` 계산 직후 한 줄:
  ```
  f = rot(q, (0,0,1)) ;  ω_t = ω_t - f * dot(ω_t, f)
  ```
  - 비용: 내적 1 + 곱 3 + 뺄셈 3. 초월함수 없음. 결정성 영향 없음.
  - **규약을 지키는 클라이언트에게는 no-op**이다(롤 오차가 이미 0이므로). 즉 동작을 바꾸는 것이 아니라 **규약을 어긴 클라이언트로부터 서버를 지키는** 변경이다.
  - designer 모델과 정합: 마우스=조준(피치·요), 롤은 별도 입력, 수평은 오토레벨. 세 입력 채널이 세 축에 1:1로 대응한다.
  - 부수 효과: `ω_aim`이 계산 시점에 `fwd`와 직교해 B-1의 분해 잔차가 작아진다(단, B-1을 대체하지는 못한다).
- **(B) 클라이언트 의무를 명문화한다.** "`q_aim`은 함선의 **현재 롤을 포함**해야 한다. 자세 제어기는 3축 전부에 권한을 가지며, 롤을 포함하지 않은 `q_aim`은 오토레벨과 진동한다." ADR-0010 §2와 ADR-0012에 같은 문장을 넣는다.

(A)를 권한다. 비용이 6 연산이고, 지키지 않는 클라이언트의 진동이 **서버 쪽 지표로는 보이지 않는다**(두 구현이 똑같이 진동하므로 예측 오차는 0이다). 문서로만 막는 규약 중 가장 깨지기 쉬운 형태다.

### B-4 금지 함수 목록에 빠진 것

ADR-0010 §3은 `sin·cos·acos·atan2·exp·pow`를 금지한다. **다음이 빠졌고, 전부 결정성 경계를 넘거나 넘을 수 있다.**

| 함수 | 왜 금지해야 하는가 |
|------|------------------|
| **`f64::mul_add`** | **가장 위험하다.** FMA는 중간 반올림이 없어 `a*b+c`와 **다른 비트**를 낸다. Rust는 쓰면 쓰는 대로 나오고, C#은 `Math.FusedMultiplyAdd`가 별도 함수라 한쪽만 쓰면 즉시 어긋난다. 최적화 도중 손이 미끄러지기 쉬운 자리(내적·적분)가 정확히 12단계가 도는 곳이다 |
| `f64::hypot` | `|v|` 계산에 쓰고 싶어지는 함수인데 IEEE로 정확히 규정되지 않았다. §2는 `sqrt(x²+y²+z²)`를 명시했으므로 그 형태를 지키면 되지만, 금지 목록에 이름이 있어야 grep이 잡는다 |
| `to_radians` / `to_degrees` | Rust는 `self * (PI/180.0)`이라 사실상 안전하지만, §2가 "리터럴을 손으로 적지 않는다"고 한 것과 같은 이유로 **양쪽이 같은 표현을 쓰는지**가 눈에 보여야 한다. 금지하고 `* (PI/180.0)`을 쓰게 하는 편이 대조가 쉽다 |
| `signum` | 5단계의 `sign(d)`가 이것으로 구현되면 **`d == 0`에서 갈라진다**: Rust `f64::signum(0.0) = 1.0`, C# `Math.Sign(0.0) = 0`. §2에서는 `|d| > roll_accel*dt > 0`일 때만 쓰므로 d≠0이라 안전하지만, **그 안전이 조건문에 숨어 있다.** `sign(d)`를 `d > 0.0 ? 1.0 : -1.0`으로 풀어 쓰도록 명시 요청 |
| `min`/`max`/`clamp` | NaN 처리가 Rust와 C#에서 다르다(`f64::max`는 NaN이 아닌 쪽, `Math.Max`는 NaN). NaN이 없어야 정상이지만, 그 가정이 깨졌을 때 **두 구현이 다르게 망가진다** — 금지가 아니라 기록으로 남길 것 |

**검사 방법 (AC-1이 요구한 것, 실측으로 확인):**

```bash
# 순진한 grep 은 오탐 13건 (p0-02 기존 코드 기준 실측)
grep -rInE "sin|cos|exp|pow|atan|acos" crates/sim/src crates/contracts/src   # → 13건
#   가장 큰 오탐원: `.expect(` 가 exp 에 걸린다.
#   예: crates/sim/src/session.rs:102  UuidV7::parse(&text).expect(...)

# 메서드 호출 형태로 좁히면 0건 (= 지금 코드는 깨끗하다)
grep -rInE "\.(sin|cos|tan|asin|acos|atan|atan2|exp|exp2|ln|log|log2|log10|powf|powi|hypot|cbrt|sinh|cosh|tanh|mul_add|to_radians|to_degrees)\s*\(|f64::(sin|cos|tan|asin|acos|atan|atan2|exp|ln|log|powf|powi|hypot|mul_add)" \
     crates/sim/src                                                          # → 0건
```

이 두 줄을 그대로 `03_server_impl.md`에 증거로 남기겠다. **오탐 13 → 0을 함께 보이는 것이 "검사가 실제로 무언가를 검사한다"의 증거**다(p0-02 AC-1이 요구한 것).

### B-5 스폰 자세의 "임의의 수직축"이 결정성 구멍이다

ADR-0010 §4: `q = normalize((cross(f0, fwd), 1 + dot(f0, fwd)))`, 그리고 "`dot`이 −1에 가까우면 **임의의** 수직축 180° 회전으로 처리한다."

**"임의의"는 두 구현이 다른 것을 고른다는 뜻이다.** 서버와 클라이언트가 다르면 첫 스냅샷부터 자세가 다르고, 서버 두 프로세스가 다르면 AC-8이 깨진다.

그리고 **이 경로는 실제 데이터로 이미 가까이 간다**(실측): `cradle.json`의 스폰 지점 `[0.0, -250.0, 2500.0]`은 `dot(f0, fwd) = -0.995`, `1 + dot = 0.005`다. 퇴화는 아니지만 정규화 전 노름이 0.0997로 작아 **조건수가 나쁘다**. 지금 `y_alternation_m = ±250` 덕분에 정확히 −1이 되지 않을 뿐이고, **`data/`는 designer 소유**라 그 보호는 우연이다.

**요청: 대체 규칙을 수식으로 못박는다.** 예:

```
if 1 + dot(f0, fwd) < 1e-6 :
    axis = normalize( |f0.y| < 0.9 ? cross(f0, (0,1,0)) : cross(f0, (1,0,0)) )
    q    = (axis.x, axis.y, axis.z, 0)        # 축 둘레 180°
```

어떤 축이든 상관없다 — **적혀 있기만 하면 된다.**

### B-6 6단계 대각선 클램프의 상수가 뒤집힐 수 있다

6단계는 `|a_local| > main_thrust_mps2`일 때 `main_thrust_mps2`로 자른다. 현재 데이터는 main 35 / lateral 18 / reverse 18이라 의도대로 동작한다(실측: 세 축 전개 43.28 → 35.0으로 클램프).

**그러나 designer가 `lateral > main`인 함선을 만들면 클램프가 의미를 잃는다** — 순수 측면 전개가 `main`보다 커도 잘리지 않거나, 반대로 전방 성능이 측면보다 낮은데 측면 기준으로 잘리게 된다.

**요청: I-38의 기동 검산에 두 줄 추가.** `main_thrust_mps2 >= lateral_thrust_mps2`, `main_thrust_mps2 >= reverse_thrust_mps2`. 실측으로 현재 데이터는 둘 다 통과한다. 검산 비용 0, 얻는 것은 "클램프 상수가 항상 최대값"이라는 불변식이다.

부수 기록(설계 결과이지 버그가 아니다): 순수 측면 대각선 `(1,1,0)`의 크기는 25.46 m/s²로 클램프에 걸리지 않는다. **측면 실효 최대는 `lateral × √2`**다. 의도한 것이면 디자인 문서에 한 줄 있는 편이 좋다.

### B-7 5단계의 부호가 손 방향이 새는 유일한 지점이다

5단계 `sin_err = dot(cross(up_s, u/nu), fwd)`는 **외적의 부호**에 의존한다. 외적을 표준 성분 공식으로 계산하면 왼손 좌표계에서는 시각적 회전 방향이 오른손 직관과 반대가 된다. 서버와 클라이언트가 같은 공식을 쓰면 **두 쪽이 일관되게 틀린다** — 모든 자동 테스트가 통과하고 예측 오차도 0이다.

즉 **오토레벨이 반대로 도는 버그는 AC-14(d)(사람의 눈)만 잡을 수 있다.** 스펙이 AC-14(a)에 대해 이미 같은 말을 했으므로 새로운 원칙은 아니지만, **어느 한 줄이 그 위험을 지고 있는지**가 문서에 없다.

**요청: ADR-0010 §2 5단계에 주석 한 줄.** "이 부호가 이 슬라이스에서 손 방향이 새는 유일한 지점이다. 뒤집혀도 서버·클라이언트가 함께 뒤집히므로 자동 검증이 잡지 못한다 — AC-14(d)가 유일한 검출기이고, 틀렸으면 고치는 것은 `sin_err`의 부호 하나다."

### B-8 세 입력 규칙의 상호작용이 한 경우에 정의되지 않았다

"마지막 도착이 이긴다"(I-28)와 "`input_seq`가 증가하지 않으면 `STALE_INPUT`"(ADR-0011 §4)이 만나는 자리:

> 한 tick에 `input_seq` 5가 먼저, 3이 나중에 도착했다.

"마지막 도착"은 3이지만 3은 stale이다. 그러면 그 tick은 **아무 입력도 적용하지 않고 이월**하는가, 아니면 5를 적용하는가? 한 연결의 메시지 순서는 보존되므로(ADR-0005 §3) **정상 클라이언트에서는 일어나지 않지만**, 망가진·악의적 클라이언트는 `(5, 3)`을 매 tick 보내 서버를 영원히 이월 상태로 둘 수 있다. 피해는 없지만 **두 구현이 다르게 셀 수 있다**(`input_superseded_total` vs `commands_rejected_total{STALE_INPUT}`).

**요청: ADR-0011 §4에 한 줄.**

> 한 tick의 도착분 중 `input_seq`가 **마지막으로 적용한 값보다 큰 것들만** 후보다. 그 중 **가장 마지막에 도착한 것**을 적용하고, 나머지 후보는 `input_superseded_total`, 후보가 되지 못한 것은 `STALE_INPUT` 거부다. 한 연결의 순서는 보존되므로 정상 경로에서 "마지막 도착"과 "최대 `input_seq`"는 같다.

### B-9 정상 종료 시 **활성** 함선의 `causation_id`가 정의되지 않았다

I-30·A-4는 `SHIP_DESPAWNED.causation_id`를 "그 잔류를 시작시킨 `SESSION_CLOSED.event_id`"로 정의한다. 그런데 **정상 종료 시점에 잔류가 아니라 활성인 함선**은 그 시점까지 `SESSION_CLOSED`가 없다.

구현상 자연스러운 답은 있다: 종료 스윕이 같은 tick에 `SESSION_CLOSED`를 먼저 발행하므로 그 `event_id`를 쓰면 된다. 하지만 그러려면 **한 tick 안의 `sequence` 순서가 강제**돼야 한다 — `SESSION_CLOSED`가 `SHIP_DESPAWNED`보다 먼저. AC-3(b)("원인의 `(tick, sequence)`가 결과보다 작다")가 **같은 tick 안에서도** 적용된다는 뜻이다.

**요청:** ADR-0011 §6에 "정상 종료 시 활성 함선의 `causation_id`는 **같은 tick에 발행된 그 세션의 `SESSION_CLOSED.event_id`**이며, 발행 순서는 `SESSION_CLOSED` → `SHIP_DESPAWNED`다"를 명시. 이건 구현이 쉽게 틀리는 자리다(스윕을 함선부터 돌면 원인이 아직 없다).

### B-10 ADR-0011 §5의 "잘리기까지" 열이 3배 틀렸다

**실측 계산** (`WORLD_SNAPSHOT/two-ships-one-lingering.json`을 공백 없이 직렬화해 잰 실제 바이트):

| 값 | 세션당 최악 버퍼 | 31세션 합계 | **잘리기까지 (실제)** | ADR 표기 |
|---:|---:|---:|---:|---:|
| 256 | 3.78 MB | 117.0 MB | **8.5 s** | 25.6 s |
| **64** | **0.94 MB** | **29.3 MB** | **2.13 s** | 6.4 s |

ADR은 스냅샷 10 Hz만 세었지만, `SET_SHIP_CONTROL`마다 `COMMAND_RESULT`가 나가므로 실제 생산율은 **30 msg/s**(스냅샷 10 + 결과 20)다. 메모리 수치는 맞고, 시간 수치만 3배 틀렸다.

**이것이 판정에 영향을 준다**: 2.13초는 **Unity Editor의 도메인 리로드·GC 히치보다 짧을 수 있다.** AC-13/AC-15를 돌리는 도중 Editor가 2초 넘게 멈추면 서버가 그 연결을 `SLOW_CONSUMER`로 끊고, QA는 그것을 서버 버그로 읽는다.

**요청 셋.**

1. §5의 표를 위 숫자로 정정한다.
2. 스펙 §8 또는 AC-13에 "정상 클라이언트도 2.1초 이상 읽기를 멈추면 `SLOW_CONSUMER`로 끊긴다 — Editor 히치가 원인일 수 있고 그 경우 재측정한다"를 적는다.
3. **용량 64 자체에는 동의한다.** 다만 다음 결정을 위해 `send_queue_bytes`(이미 계획됨)에 더해 **`send_queue_depth_max`를 메시지 종류별로 나누지 말고, 끊긴 세션의 `close_reason=SLOW_CONSUMER` 발생 수**를 함께 보는 것을 제안한다 — 정상 부하에서 0이어야 하고, 0이 아니면 용량이 아니라 소비자가 문제다.

중간안이 필요하면 **128**(4.3 s, 세션당 1.9 MB, 31세션 58 MB)이 있다. 메모리는 p0-02 RSS 16.6 MB의 3.5배지만 최악값이고, Editor 히치 내성이 2배가 된다. **선택은 architect가 한다** — 내 의견은 "64로 가되 §5 표를 고치고 Editor 히치를 스펙에 적는다"이다.

### B-11 `max_entities_per_snapshot: 64`와 40척 트리거가 어긋난다

실측: 40척에서 세션당 193.8 KiB/s(예산의 100.9 %)로 이미 깨지는데, 스키마 `maxItems`와 데이터는 **64**를 허용한다. 64척이면 307.9 KiB/s(예산의 160 %)다.

계약 상한과 운영 트리거가 다른 것 자체는 정상이다(하나는 구조적 여유, 하나는 설계 한계). 다만 **그 사이 구간(41~64척)에 들어가면 아무도 경고하지 않는다.** 요청: 기동 검산이 아니라 **런타임 경고** 하나 — 월드의 함선 수가 예산 초과 지점을 넘으면 `WARN` 1회 + `snapshot_over_budget_total` 카운터. 이 슬라이스는 31척 상한이라 발동하지 않지만, 다음 슬라이스가 40을 넘길 때 **측정된 사실로** 알게 된다.

### B-12 `q_aim` 노름 하한 `1e-3`이 잡음을 증폭한다

1단계는 `n < 1e-3`이면 퇴화로 처리한다. 그 바로 위(예: `n = 0.002`)는 정규화가 **양자화 잡음을 500배 증폭**한다 — 결과는 단위 쿼터니언이지만 방향이 사실상 잡음이다.

악용은 아니다(정상 쿼터니언으로도 같은 목표를 보낼 수 있으니 얻는 것이 없다). 다만 **"퇴화"의 정의가 "수치적으로 정규화 불가능"이지 "회전으로 보기 어렵다"가 아니라는 점**이 기록될 가치가 있다. 임계를 `0.1` 정도로 올리면 후자가 되고 정상 클라이언트는 영향받지 않는다(양자화된 단위 쿼터니언의 노름은 1 ± 1e-6). **차단 아님 — architect 판단.**

### B-13 AC 문구 5건

아래 §"수용 기준 검토" 참조. 요약: AC-3(c), AC-3(d), AC-4(g), AC-7(d), AC-20(e).

### B-14 `tick_body_us`가 이 슬라이스에서 이봉분포가 된다

스냅샷은 2 tick마다 만들어지므로, tick 본문 소요가 **"스냅샷 tick"과 "그냥 tick" 두 무리**로 갈린다. p50은 낮은 쪽만 보고 p99는 높은 쪽만 본다 — **p0-02 기준선(본문 최대 21.65 ms)과의 비교가 의미를 잃는다.**

**요청: `snapshot_build_us` 히스토그램을 따로 노출한다.** 그러면 AC-19가 "tick 본문이 늘었다"를 "스냅샷 조립이 X µs, 나머지가 Y µs"로 분해해 적을 수 있다. 메트릭 1개 추가이고 구현은 `Instant` 하나다.

## 적분 12단계 순서 검토

**결론: 12단계의 순서 자체는 바꿀 곳이 없다.** 아래는 각 단계를 실제로 따라가며 확인한 것과, 순서가 아니라 **내용**에 대한 요청 3건이다.

### 순서가 옳다고 확인한 것

| 확인 | 왜 옳은가 |
|------|----------|
| 4·5단계가 `q_pure(w) ⊗ q` 형태 | `ω`가 **월드 프레임**이므로 `q̇ = ½ ω ⊗ q`가 맞다. 바디 프레임이면 `q ⊗ ω`여야 하고, 둘을 섞으면 회전이 거울이 된다. 표기가 정확하다 |
| 5단계가 `fwd`를 **롤 적분 전에** 계산 | 롤은 전방축 둘레 회전이라 전방축을 바꾸지 않는다. 전후 어느 쪽이든 같지만, **적는 쪽을 고정한 것**이 계약으로서 옳다 |
| 6단계가 **5단계 후의 자세**로 추력을 변환 | 한 tick 안에서 "돌고 나서 민다". 반대로 하면 빠르게 선회할 때 추력 방향이 한 tick 뒤처지고, 그 차이는 저속에서 안 보이다가 격렬한 기동에서만 나타난다 |
| 9단계가 8단계 **뒤**의 `v`로 계산 | ADR이 명시한 대로. 앞에서 하면 가속과 감쇠가 같은 tick에서 다른 값을 본다 |
| 9단계 감쇠를 **정확히 하나만** | 브레이크와 보조가 겹치면 `brake_decel_mps2`가 거짓 수치가 된다 |
| 10(속도 상한) → 11(위치) → 12(하드 경계) | 12는 `|v|`를 **줄이기만** 하므로 10의 클램프를 깨지 않는다. 순서를 바꾸면 경계에서 상한을 넘을 수 있다 |
| 7단계 경계 당김이 **더하기**(조작을 이기지 않음) | 벽이 벽처럼 보이지 않게 하는 장치. 조작을 무시하면 "조작이 먹통"이 되고 그것이 더 나쁘다 |
| 9단계가 `a_bound`를 감쇠 기준에서 제외 | 경계 당김은 조종사 의도가 아니다. 보조 감쇠가 당김 방향을 "추력 방향"으로 오인하면 경계에서 옆으로 미끄러지는 게 아니라 붙어 버린다 |

### 순서가 아니라 내용에 대한 요청 (재게)

1. **2단계에 롤 성분 제거를 넣는다** → B-3. 단계를 옮기는 것이 아니라 한 줄 추가다.
2. **`sign(d)`를 풀어 쓴다** → B-4. `signum`으로 구현되면 `d==0`에서 언어가 갈린다.
3. **§4 스폰의 대척점 대체 규칙을 수식으로** → B-5.

### NaN·0 나눗셈 경로를 전부 따라간 결과

| 단계 | 나눗셈 | 가드 | 판정 |
|------|--------|------|------|
| 1 | `q_aim_raw / n` | `n < 1e-3` | 안전 (B-12는 정밀도 문제이지 NaN 아님) |

## 스냅샷 31벌을 tick 본문에서 만드는 비용

**실측 (fixture 실제 바이트):**

| 함선 수 | 프레임 | 세션당 @10 Hz | 예산 192 대비 | 서버 송신 합계 |
|---:|---:|---:|---:|---:|
| 2 | 1,340 B | 13.1 KiB/s | 6.8 % | 0.2 Mbit/s |
| 8 | 4,262 B | 41.6 KiB/s | 21.7 % | 2.7 Mbit/s |
| **31** | **15,463 B** | **151.0 KiB/s** | **78.6 %** | **38.3 Mbit/s** |
| 40 | 19,846 B | 193.8 KiB/s | **100.9 %** | 63.5 Mbit/s |
| 64 | 31,534 B | 307.9 KiB/s | 160.4 % | 161.5 Mbit/s |

`ShipState` 1개 = **486 B**(architect 실측과 일치), 0척 봉투 = 367 B. architect의 31척 15,419 B와 내 15,463 B의 44 B 차이는 fixture의 id 길이 차이다 — **결론에 영향 없음.**

### tick 본문에서 무엇을 만들 것인가

| 방식 | tick당 복사 | 비고 |
|------|---|---|
| 세션마다 배열을 통째로 복제 (31 × 31) | 961 `ShipState` ≈ **150 KiB** | 할당 31회 + 복사 |
| **공유 배열 1벌 + 세션별 머리 2필드** | 31 `ShipState` ≈ **4.8 KiB** | 할당 1회 |

150 KiB memcpy는 그 자체로 재앙은 아니지만(수십 µs), **할당 31회가 tick 본문에 들어가는 것**이 p0-02의 tick 본문 예산(최대 21.65 ms 중)에 불필요한 변동을 더한다. 그리고 공유안은 구현이 더 짧다.

**제안하는 형태 (크레이트도 serde feature도 추가하지 않는다):**

```
sim 이 반환:  Arc<[ShipState]>  (tick 당 1회 생성, 직렬화되지 않는다)
              + 세션별 { controlled_ship_id, ack_input_seq }
게이트웨이가: #[derive(Serialize)] struct WorldSnapshotOut<'a> { … ships: &'a [ShipState] … }
              로 세션마다 직렬화 (tick 본문 밖)
```

- `Arc<[T]>`를 serde로 직렬화하려면 `serde`의 `rc` feature가 필요하지만, **빌려 쓰는 뷰 구조체를 쓰면 필요 없다.** `&[ShipState]`는 기본 기능으로 직렬화된다.
- 계약 타입 `WorldSnapshotMessage`(`Vec<ShipState>`)는 **계약 테스트 전용으로 그대로 둔다.** 두 타입이 갈라지지 않도록 단언 하나를 건다: 같은 데이터로 만든 `to_value(WorldSnapshotOut)`와 `to_value(WorldSnapshotMessage)`가 **동일**. 이 한 줄이 "와이어 뷰가 계약과 같은 모양"을 타입 대신 테스트로 고정한다.
- **직렬화는 tick 본문 밖**이라는 경계(스펙 §8)는 그대로 지킨다. 31 × 15.1 KiB = 468 KiB/스냅샷 tick의 JSON 직렬화는 세션별 송신 태스크에서 일어난다(초당 4.7 MB → 한 코어의 2~3 % 수준으로 예상, AC-19가 간접 확인).

**이 제안은 스펙이 정한 경계("직렬화는 tick 밖") 안에서의 구현 선택이므로 ADR 변경을 요청하지 않는다.** 실측 결과는 `03_server_impl.md`에 적는다.

## AC-8 "서로 다른 프로세스에서 2회" — 실측으로 확인했다

**결론: 이 PC에서 돈다. 새 의존성 0개. 패턴을 스크래치에서 실제로 실행해 확인했다.**

```rust
#[test] #[ignore = "부모가 별도 프로세스로 호출한다"]
fn replay_child() { std::fs::write(env("REPLAY_OUT"), run_replay()).unwrap(); }

#[test]
fn deterministic_across_processes() {
    let exe = std::env::current_exe().unwrap();          // 테스트 바이너리 자신
    for run in 0..2 {
        Command::new(&exe)
            .args(["--exact", "replay_child", "--ignored", "--nocapture"])
            .env("REPLAY_OUT", path(run)).status().unwrap();
    }
    assert_eq!(read(path(0)), read(path(1)));            // 바이트 비교
}
```

실행 결과: 두 자식 프로세스가 각각 64 B를 산출했고, 일부러 `HashMap` 순회를 넣은 페이로드에서 **바이트가 달라 실패했다** — 즉 이 하네스는 실제로 비결정성을 잡는다(검사가 무언가를 검사한다는 증거).

**정확히 무엇을 더 잡는가 (과장하지 않기 위해 실측으로 구분했다).**

같은 프로세스에서 2회 돌리는 대조 테스트도 **함께 실패했다.** Rust의 `RandomState`는 프로세스당이 아니라 **HashMap 인스턴스마다** 다른 키를 쓰기 때문이다. 따라서 "`HashMap` 순회 의존"은 같은 프로세스 2회로도 잡힌다.

**별도 프로세스가 추가로 잡는 것은 "프로세스 수명 동안 한 번만 정해지는 상태"에 대한 의존이다**: ASLR에 따라 달라지는 포인터 값, `OnceLock`으로 한 번만 시드되는 난수, 기동 시각에서 파생된 값, CPU 기능 검출 캐시. 이 슬라이스에는 그런 것이 없어야 하지만, **없다는 것을 증명하는 것이 이 테스트의 일**이다.

**구현 시 지킬 것 둘.**

1. 자식이 쓰는 것은 **운영과 같은 직렬화 경로**여야 한다. 테스트 전용 덤프 형식을 쓰면 "스냅샷 바이트가 같다"가 아니라 "덤프가 같다"를 증명하게 된다.
2. 입력열은 **파일에서 읽는다**(스펙 §8이 이미 요구). 자식이 입력을 생성하면 입력 생성기까지 결정적이어야 한다는 부담이 늘고, C4가 쓸 자산이 되지 못한다.

**client와 미리 맞출 것 (S6 산출물 형식):** 입력열 파일과 tick별 스냅샷을 어떤 형식으로 낼지. 제안 — 입력열은 `SET_SHIP_CONTROL` payload의 JSON Lines(tick 번호 포함), 스냅샷은 tick당 한 줄의 **직렬화된 `WORLD_SNAPSHOT` payload**. 그러면 C4가 파서를 새로 쓰지 않고 계약 DTO를 그대로 쓴다.
