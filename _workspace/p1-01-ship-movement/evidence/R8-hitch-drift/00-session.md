`H` 주입 9회 중 tick=-1(접속 전) 1회를 뺀 **8회가 전부 140 m/s 부근**에서 났다.

## 2. qa r9 §B.5의 예측과 어긋난 부분 — 판정은 qa 몫이다

qa r9는 이 절차가 짝을 만들지 못한다고 판정했다. 근거는 밀린 스냅샷이 `PendingRebaseSlot`에서
하나로 합쳐져 히스토리에 해당 tick이 없고 따라서 **`HasError = false`**가 되어
밴드 분류와 `HardSnapTotal++`이 실행되지 않는다는 것이었다.

관측은 다르게 나왔다 — `speed ≥ 100` 드리프트 사건 99건 중 **`HasError=false`는 5건뿐**이고,
주입 히치에 대응하는 `drift=±7~8` 사건들은 **오차가 측정됐다**(0.0003~0.0009 m).

**리더는 이것으로 SC-56이 닫혔다고 주장하지 않는다.** 왜 모델과 관측이 갈렸는지,
그리고 이 짝이 (c2)를 실제로 만족시키는지는 qa 판정 사항이다. 이 문서는 관측까지만 적는다.

한 가지 산술만 덧붙인다: `drift = -7`은 7 tick 어긋남이고, 수정 전 코드의 오차 모델
(`|drift| × v × dt`)로는 `7 × 140 × 0.05 = 49 m`다. 관측값은 **0.0009 m**다.
이 대조가 RED/GREEN을 가르는지도 qa 판정 사항이다 —
qa r9 §H.2는 "적중 스냅샷에서 수정 전 코드도 0.0000을 낸다"고 적었고, 그 모델과 이 산술이
충돌한다. 둘 중 하나가 틀렸다.

## 3. 새 결함 후보 — F-28 (리더 발견)

`reconcile_tick_drift_max = 6983`은 **세션 경계의 허수**다:

```
drift=-6983  delta_tick=7004  tick=1057794  speed_mps=0.0  position_error_m=n/a
```

직전 세션이 끝난 tick(≈1050790)과 새 세션의 첫 스냅샷 tick(1057794) 사이의 차이를
드리프트로 계산했다. `GreyboxSession.cs:295-296`이 `_driftPrevAck`/`_driftPrevTick`을
리셋하지만, 이 사건은 그 리셋을 거치지 않았다(`sessions_opened_total = 2`).

영향: `reconcile_tick_drift_max`가 실제 최대(8)의 **873배**로 오염된다. 계약이 이 값을
판정에 쓰게 되면 그대로 거짓 신호가 된다. `drift_total = 18`도 1건이 허수다.

**이 문서는 `reconcile_tick_drift_max`를 판정 근거로 쓰지 않는다.**

## 4. 아직 판정하지 않은 것

- `position_error_m max = 0.3151`(> (c3) 0.25)은 **드리프트 사건이 아니다** —
  드리프트 사건 중 0.25를 넘은 것은 0건이다. 즉 이 오차는 `drift == 0`인 재조정에서 났고
  출처가 다르다. 리더는 출처를 확인하지 않았다. **추측하지 않고 미확인으로 남긴다.**
- `orientation_error_deg max = 3.2981`. 1 tick 최대 회전 3.75°(`turn_rate_max_deg_s = 75`)
  이내이므로 qa r9 §A-3의 논거가 그대로 적용될 것으로 보이나, 확인은 qa 몫이다.
- `truncated = 2`가 어느 순간에 났는지, 그리고 qa r9 §B.4가 지적한
  "하드 스냅 카운터의 truncate 사각"(F-27)이 이 세션에서 발동했는지.

## 5. 정정 (qa r10 판정 후) — 절대 원칙 5에 따라 위 절은 고치지 않는다

### 정정 1 — §1 표의 모집단이 섞여 있다

`speed ≥ 100` 드리프트 사건 "99건 / `n/a` 5건"은 **두 세션을 합친 값**이다.
로그에 `SESSION_READY`가 2회(:580, :2130) 있고 **히치 주입은 세션 2에서만** 일어났다.
세션 종료 덤프(`n=307`, `hard_snap=0`)는 세션 2만의 값이므로 99건과 **같은 모집단이 아니다.**

세션 2만의 값(qa r10 확정): 드리프트 **18건** / 고속 **16건** / `n/a` **4건(25 %)** /
측정된 12건 최대 **0.0183 m**.

판정은 바뀌지 않았으나, 이 오류의 형태가 중요하다 — **같은 문서 §3에서 내가 F-28
(세션 경계에서 드리프트가 허수로 잡힌다)을 발견해 적어 놓고도, 정작 내 집계에
그 경계를 적용하지 않았다.** 결함을 찾는 것과 그 교훈을 자기 작업에 적용하는 것이
별개라는 것을 한 문서 안에서 보여 준 셈이다. R7 세션에서 누계를 구간 사건처럼 읽은 것과
같은 형태이고 두 번째다.

### 정정 2 — §3의 F-28 원인 규명이 틀렸다

나는 `drift=-6983`을 **세션 경계**의 허수로 단정했다. 틀렸다.
qa r10이 로그 줄 번호로 확인한 바: 그 사건은 세션 2 **안**에서 났고
(`SESSION_READY :2130` → 사건 `:2573` → `closing :2585`),
`_driftPrevTick = 1050790`은 같은 세션의 직전 적용 스냅샷이다.
**`GreyboxSession.cs:295-296`의 리셋은 돌 이유가 없었고 결함이 없다.**

진짜 원인은 **약 350초 클라이언트 정지**(직전에 `Asset Pipeline Refresh` — Editor 포커스 복귀).
즉 그 값은 허수가 아니라 **정지 길이를 그대로 잰 값**이다.

허수 계수(qa r10): 세션 경계 허수 **0건**, 정지 길이를 잰 값 **2건**(-76, -6983).
- `_max = 6983`은 100 % 오염이라 계약 판정에 **쓸 수 없다**(현 계약이 안 쓰므로 차단은 아니다).
- `_total = 18`은 2건 오염이나 **쓸 수 있다** — (c2)의 `speed ≥ 100` 짝이 그 2건
  (96.3 m/s, 0.0 m/s)을 정확히 걸러낸다.

내가 코드를 읽지 않고 "리셋을 거치지 않았다"고 단정한 것이 오류의 원인이다.
로그에 세션 경계가 보였고 값이 컸다는 두 사실에서 인과를 만들었다.

### 정정 3 — 서버 명령 수

§1에 "1,148건"이라고 적었으나 `commands_received_total`은 **1,187**이다.
위반 0 · 드롭 0 · 거부 전 항목 0 · tick 오버런 0은 확인됐다.

### 유지되는 것

§2에 적은 산술(`drift=-7` → 수정 전 모델로 49 m)은 **qa r10이 실행으로 확인했다**:
실소스와 `git show 8b0a78d`의 ack 키 `Reconciliation`을 같은 서버·같은 입력·같은 프레임
일정으로 돌린 결과 **수정 전 `position_error_m = 49.0000`, `hard_snap = 2`**,
수정 후 `0.0000`, `0`. 소수점까지 일치한다.
따라서 이 세션의 `hard_snap = 0`은 **자명하지 않다.**

## 6. 추가 (qa r10 §A.4) — 세션 1이 주입 없이 83건을 냈다

이 세션에서 가장 중요한 관측은 주입 구간이 아니라 **주입이 없던 세션 1**이다.

세션 1에는 유효한 주입이 **0건**이다(유일한 `hitch_injected` 줄이 `tick=-1 speed=0.0`,
접속 전 키 입력이라 무효). 그럼에도:

| | |
|---|---|
| 드리프트 사건 | **97건** (그중 96건이 `|drift|=1 delta_tick=2`) |
| `speed ≥ 100 m/s` | **83건** (측정 82건, 최대 0.0037 m) |
| 기전 | 서버 분기 — `input_carried_forward_total=227`, `input_superseded_total=110` |

**실제 운영에서 드리프트는 난다. 흔하게, 최고속에서, 주입 없이.**

그리고 수정 전 코드라면 그 83건이 각각 `1 × 140 × 0.05 = 7.0 m`를 내고
`reconcile_hard_snap_total`을 83 이상 올렸을 것이다(qa r10이 하네스로 확인:
`±1 dt=2` → `7.0000 m`, HardSnap 밴드). **즉 세션 1만으로도 RED/GREEN이 갈린다.**

`7.0000`은 `Reconciliation.cs:19` 헤더가 직접 예고한 수다 —
*"an error of exactly v*dt (140 m/s -> 7.0 m, well past reconcile_hard_snap_threshold_m=5.0)"*.
코드 주석의 예고를 실행이 소수점까지 확인했다.

### 이것이 정정하는 것

qa r9 §A.2는 R7 세션을 근거로 "겨냥한 조건이 한 번도 성립하지 않았다",
"고속 주행 중 의도적 히치를 넣어야 한다"고 판정했다. **같은 코드·같은 서버에서
세션 1은 83번 성립시켰다.** R7이 조용했던 것은 구조적 이유가 아니라 그 세션의 사정이었다.

**그리고 주입은 SC-56을 닫는 데 필수가 아니었다.** 주입의 가치는
(ⅰ) 조건을 결정적으로 만들고 (ⅱ) 오차를 7 m에서 49 m로 키워 분리를 넓힌 것이지
조건을 처음 만든 것이 아니다. F-25(250→400)의 가치도 같은 층에 있다.

### 세션 1의 `drift=-59`는 자연 히치가 아니다

```
:1836  [ScriptCompilation] Requested script compilation because: AssetDatabase observed changes
:1862  reconcile_tick_drift_event drift=-59 delta_tick=80 tick=1049790 speed_mps=105.0 ... n/a
:1864  bee_backend.exe ... ScriptAssemblies  →  Csc  →  ILPostProcess  →  도메인 리로드
```

**스크립트 컴파일 + 도메인 리로드가 4초(80 tick) 메인 스레드를 잡았다.**
Editor 고유 사건이고 플레이어 빌드에는 없다. `dt=80 > M=20`이라 truncate → `n/a`이며,
**r9 §B.5 모델이 자연 발생 사례에서도 맞았다**(그 모델이 틀린 것은 일반화 부분뿐이다).
