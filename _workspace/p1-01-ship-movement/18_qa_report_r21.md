## 1. SC-56 (e) — **PASS**

계약이 요구한 넷이 **전부 비-0** 이다. **`셋 중 하나라도 0이면 미검증(증거 요건)`** 의 반대다.

| # | 요구 | 관측 | 축 |
|---|---|---|---|
| ① | `Smooth`/`SmoothTracked` 분류 수 ≥ 1 | **102** | **⚠ 축 공유 — §1.1** |
| ② | 오프셋이 0 이 아니었던 프레임 > 0 | **2,107** | **위치 전용** |
| ③ | 오프셋 최대 크기 (+ `n`) | **3.8427 m** (`n = 17,585`) | **위치 전용** |
| ④ | 재조정 없던 프레임에서 줄어든 횟수 > 0 | **2,044** | **위치 전용** |

**밴드 안이다**: `0.25 m < 3.8427 m < 5.0 m`, 그리고 **`reconcile_hard_snap_total = 0`** —
**하드 스냅으로 새지 않았다.** 블록 7 이 못 넘은 자리를 이번에 넘었다.

### 1.1 ⚠ **① 은 위치 축의 증거가 아니다** — ②③④ 가 증거다

`GreyboxSession.cs:837` 이 이렇다:

```csharp
if (RenderOffset.IsSmoothed(positionBand) || RenderOffset.IsSmoothed(orientationBand))
    _smoothedReconcileTotal++;
```

**`||` 다.** 즉 **① 102 는 자세만 밟아도 올라간다.** 이 세션은 **마우스가 움직여 자세 축도
1,378 프레임 발동**했으므로, **① 만 보면 블록 7 과 구분되지 않는다.**

**판정을 떠받치는 것은 ②③④ 다** — 셋 다 `_renderPositionOffset.Length()` 에서 나온다
(`:1119-1126`, 코드 확인). 그래서 이 PASS 의 근거를 *"넷이 비-0"* 이 아니라
**"위치 축 전용 세 수가 비-0"** 으로 적는다.

**④ 의 제외 조건도 확인했다**: `!_reconciledThisFrame && offsetM < offsetBeforeDecayM`
— **재조정이 오프셋을 갈아치운 프레임을 세지 않는다.** 계약이 ④ 를 신설한 이유
(*"세워 놓고 한 번도 감쇠시키지 않는 구현"*)를 실제로 막는 형태다.

### 1.2 겨냥한 조건이 실제로 발생했는가 — **수로 단언한다** (§7a)

| 물음 | 답 |
|---|---|
| 히치를 몇 번 주입했나 | **11회** (tick 1647954 … 1658525) |
| 그중 **무효는 몇 회인가** | **5회** — `speed_mps = 0.0`. **속도 0 이면 400 ms 를 멈춰도 위치 오차가 0 이다.** 이 다섯은 아무것도 만들지 않았다 |
| **유효 주입** | **6회** (`speed_mps = 140.0`) |
| 위치 오프셋이 선 프레임 | **2,107 / 17,585** (11.99 %) |
| 감쇠가 단독으로 돈 프레임 | **2,044** |

**②③④ 가 0 이었다면 이 세션은 `미검증` 이었다.** 그 분기가 실제로 존재했다는 것이
블록 7 이 남긴 기록이다.

## 2. 절차 이탈 셋 — **판정을 바꾸지 않는다. 이유를 적는다**

| 이탈 | 판정에 걸리는가 | 왜 |
|---|---|---|
| **앞 5회가 `speed_mps = 0.0`** | **아니다** | 그 다섯은 **아무것도 만들지 않았다**(무효 표본). 유효 6회가 남고, 계약은 주입 횟수가 아니라 **①~④ 의 값**을 요구한다. **무효 수를 리포트에 적는 것**이 §7a 가 요구하는 처리다 |
| **뒤 6회가 `140 m/s`** (내 표는 10~30 을 권했다) | **아니다** | 계약에 속도 요건이 없다. 내 표는 **"겨냥하기 쉬운 속도"** 이지 판정 조건이 아니었다 — §3 |
| **마우스가 움직였다** (자세 축 동반 발동) | **아니다** | ②③④ 가 **위치 축 전용**이라 자세 발동이 그 수를 오염시키지 않는다. **다만 ① 은 오염된다** — 그래서 §1.1 대로 ① 을 근거에서 뺐다 |

**셋 다 "절차가 덜 정확했다"이지 "판정 입력이 오염됐다"가 아니다.** 만약 판정을 ① 에
걸었다면 **마우스 이탈이 판정을 무효로 만들었을 것이다** — 축을 가른 것이 그 차이를 만들었다.

## 3. 내 §2.3 계산 표 — **관측과 다르다. 고치지 않고 관측을 옆에 붙인다**

절차서 §2.3 은 *"140 m/s 에서 창이 34 ms 라 겨냥할 수 없다"* 고 적었고, **계산이지 관측이
아니라고 명시했다**(규칙 9).

**관측은 다르다**: 140 m/s 에서 `max_m = 3.8427` 로 **밴드 안**에 들었고 하드 스냅은 0 이다.

> **왜 다른지는 모른다.** 재조정이 tick 단위로 누적돼 실효 창이 더 넓을 가능성이 있지만
> **그것은 가설이고 아무도 재지 않았다.** 리더의 가설도 같은 상태다.
> **모른다고 적는다 — 추측을 절차서에 남기면 다음 사람이 그것을 근거로 쓴다.**

**표를 지우지 않는다**: 표가 **계산으로 표시돼 있었기 때문에** 이 관측이 *모순*이 아니라
*보강*이 된다. 절차서에 **관측 한 줄을 표 옆에 붙이고 "계산 ≠ 관측, 이유 미상"** 으로 남긴다.
**낮은 속도 권고도 유지한다** — 한 세션의 성공이 "140 에서 늘 된다"를 뜻하지 않는다.

## 7. 절차서에 반영할 것 (다음 세션을 위해)

1. **§2.3 표 옆에 이번 관측** — *"140 m/s 에서도 밴드에 들었다(3.8427 m, 하드 스냅 0). **계산과
   다르고 이유는 미상이다.** 낮은 속도 권고는 유지한다."*
2. **속도를 0 으로 만들지 않는다** — *"`X` 로 낮추되 **멈추지 않는다**. `speed_mps = 0` 에서의
   히치는 위치 오차를 만들지 않는다(이번 세션 5회 무효)."* **리더의 지시 오류였고 절차서 문구가
   그것을 허용했다** — 내 책임이다.
3. **`-logFile` 경로를 준 뒤 그 파일이 실제로 생겼는지 확인한다** — **Unity 는 경로가 이상해도
   조용히 그 경로에 쓴다**(이번에 `$E` 가 확장되지 않아 엉뚱한 디렉터리에 썼다).
4. **환경 변수 셋이 비어 있으면 빈 씬이 나온다** — §3.0 표에 *"Play 전에 셋이 실제로 주입됐는지
   확인"* 을 넣는다. **시크릿을 영구 환경 변수에 박지 않는다**(리더가 프로세스 환경에만 주입했다).
