## 1. 작업 1 — (f) `cmd_compare` 의 불리언 묶음: **분리했다**

### 1.1 무엇이 틀려 있었나

`two_client_view.py:113-118`(개정 전)의 한 불리언이 세 항목을 묶고 있었다:

```python
ok = (not mismatch                      # SC-63
      and monotonic_back == 0           # SC-61
      and path_mm > 0                   # SC-61
      and (path_mm / 1000.0) <= max_possible_m * 1.05)   # SC-61
```

**SC-62 는 이 식에 없다.** `b_own_displacement_m` 을 계산해 출력에 싣기만 하고 판정에 쓰지 않았다 —
즉 **B 의 함선이 얼마나 움직였든 SC-62 의 verdict 는 다른 항목의 초록불을 그대로 받았다.**
이것은 계약 §7b 규칙 1 의 자명 통과다. **분리가 (f) 만이 아니라 이것까지 드러냈다.**

### 1.2 무엇을 했나

- `evaluate_compare()` 를 순수 함수로 떼어내고 **`SC-61_verdict` · `SC-62_verdict` 를 각각** 낸다.
- **SC-63 계산을 `compare` 에서 삭제했다.** "참고로 싣기"는 리포트를 읽는 사람이 verdict 로 읽는다.
  그 자리에는 **어디서 판정하는지만** 문장으로 남겼고, selftest 가
  `sc63_key_is_prose_not_verdict == true` 로 그것이 값이 아님을 단언한다 — 재결합이 **구조적으로**
  불가능해야 한다.
- 종료 코드를 verdict 에 맞췄다: `0` 통과 / `1` FAIL / **`4` 미검증**(신설 `EXIT_EVIDENCE`).
  FAIL 과 미검증을 같은 1 로 내보내면 §0.3 이 나눈 두 칸이 셸에서 다시 합쳐진다.

### 1.3 §7a 양성 대조 — **분리가 실제로 동작하는가**

같은 두 파일(`evidence/R14-.../posctl_{A,B}.csv`)을 **옛 도구와 새 도구에** 각각 먹였다.

| | 개정 전 (HEAD) | 개정 후 |
|---|---|---|
| 인쇄되는 verdict | `"item": "SC-61/62/63 …"` · **`"verdict": "FAIL"` 한 개** | `"SC-61_verdict": "PASS"` · `"SC-62_verdict": "PASS"` |
| (SC-63 칸) | `mismatching_pairs: 20` (같은 출력 안에서 verdict 와 섞인다) | **없다.** "블록 10 에서 판정한다"는 문장만 |
| exit | **1** | **0** |

**그리고 이 입력이 실제로 SC-63 만 FAIL 인 입력이라는 것을 같은 실행에서 단언한다**:
`legacy_sc63_mismatches_on_this_input = 20`. 이 숫자가 0 이면 분리를 시험하지 않은 것이고,
그때 두 PASS 는 아무것도 뜻하지 않는다.

**음성 대조도 넣었다**: B 가 본 A 의 궤적이 절반에서 되돌아가는 입력에서 `SC-61_verdict = FAIL`.
없으면 "분리 후 늘 PASS 를 인쇄하는 도구"와 구분되지 않는다.

### 2.2 `render_offset_mm` 전 행 0 — 세 경우를 **가르는 방법**

architect 의 지적대로 **CSV 값만으로는 갈리지 않는다.** 가르는 것은 `ObserverSession` 이
**세션 종료 시 한 번** 찍는 로그 줄이고(`ObserverSession.cs:160-172`), 그 파일의 주석 자신이
*"Observer 에는 HUD 도 `RenderLocalShip()` 도 없어 여기 말고는 감쇠 루프가 돌았는지 확인할 곳이
없다"* 고 적고 있다. **Play 를 정상 종료해야 찍힌다** — 절차서 §5-1 이 그 이유다.

```
starfall.observer.A: SC-56 (e) session-end render smoothing stats - render_smooth_band_total=…,
render_offset_nonzero_frames_total=…, render_offset_max_m=… (n=…), render_offset_decay_frames_total=…
```

| 관측 | 원인 | 처분 |
|---|---|---|
| `render_smooth_band_total == 0` | **(i) 보정이 한 번도 안 일어났다** | 구현 결함이 아니다. **"이 세션은 평활화 경로를 밟지 않았다"를 적는다** — 그 열이 이 세션에서 아무것도 증명하지 않았다는 뜻이다 |
| `band_total > 0` 인데 `nonzero_frames_total == 0` | 오프셋을 세우지 않는다 | client FAIL |
| `nonzero_frames_total > 0` 인데 `decay_frames_total == 0` | **(ii) `Update()` 감쇠 누락** (SC-56 (e) ④ 가 겨냥한 결함) | client FAIL |
| 로그 줄 자체가 없다 | **(iii) client 미구현** 또는 비정상 종료 | 정상 종료를 먼저 확인 |
| `nonzero_frames_total > 0` 인데 **CSV 는 전 행 0** | 프레임에는 오프셋이 서는데 **CSV 를 쓰는 순간에만 0** | **결함이다** — 그러면 SC-64·65 가 재는 것은 화면이 아니다(12차 개정이 막으려던 형태) |

도구도 이 관측을 낸다: `s3` 출력에 `render_offset_presence`(양쪽 행 수·비-0 행 수·최대값)를 추가했다.
**판정하지 않고 관측만 낸다** — 값으로 세 경우를 가를 수 없다는 것이 이 항목의 성질이기 때문이다.

### 발견 1 (판정에 걸린다) — **SC-62 에 수치 임계가 없다**

섞였을 것이다.

#### 반대 방향의 공백도 같은 훑기가 냈다

출처 게이트를 처음 돌리자 **11건**이 나왔는데, 라벨을 고친 뒤에도 6건이 남았다. 그 6건은

#### D-3 — **SC-90 을 신설했다 (항목 수 89 → 90, qa 25 → 26)**

append-only·멱등·UNIQUE 를 판정하는 SC 행이 이 슬라이스에 **0건**이었다. 신설한 이유:

`tests/e2e/check_item_sources.py` 를 만들었다. 계약 §1 행과 §3.2 표에서

architect 가 R15 에 경고한 훑기 함정과 같은 방향이다.

#### 내 "닫혔다"가 틀렸던 자리

*"이 가족은 닫혔다"* 는 **두 도구를 고친 사실**에서 나왔고 그 사실은 맞다. **틀린 건 범위다** —
고친 두 도구 밖을 안 봤다. **규칙 6 의 정신이 종료 선언 자체에도 걸린다**: *"닫혔다"를
주장하려면 닫혔는지 재는 검사를 돌려야 하고, 그 검사는 고친 자리만 보아선 안 된다.*
이번에 잡은 것은 꼼꼼함이 아니라 **한 줄짜리 훑기**였고, 규칙 7 이 그것을 상설화한다.

### 발견 7 — **출처 게이트 자신에 방어가 없었다. 넣었더니 빨간불이다 (계약 19차)**

#### E-2 — 분모를 찍는다

#### 이 건이 남긴 규율 — **분자의 출처도 묻는다**

분모를 찍게 한 것이 절반이었다(E-2). **나머지 절반은 분자다**: `90 / 90` 을 만든 것이
**"이번 라운드에 한 일을 이력에 적는 행위"** 였다 — **규율을 지키는 행동 자체가 게이트를 껐다.**

> **분자가 늘었을 때 "무엇이 그것을 늘렸는지" 를 확인하지 않으면 커버리지 지표는 자기 자신을 속인다.**

계약 §7b 규칙 7 주석에 넣었다. **비워 두기가 실제로 작동한 사례(SC-51·52)** 도 같이 적었다 —
규칙이 "겁주는 말"이 아니라 절차가 되려면 **걸린 사례만이 아니라 지켜서 이득을 본 사례**가 있어야 한다.

#### E-1 — SC-90 (e) 가 잘못된 제약으로 통과할 수 있었다

옛 판정은 `"duplicate key" in dup or "unique" in dup` — **어느 제약이든 위반되기만 하면 참이다.**
(d) 와 (e) 의 입력 차이는 `event_id` 뿐이라 **(e) 가 `event_id` PK 에 걸려도 같은 문자열이 나온다.**
그러면 두 절이 **같은 제약을 두 번 재고**, (e) 가 이름붙인 성질(`(world_id,tick,sequence)` 유일성)은
**한 번도 검사되지 않는다.**

고친 방식: `pg_constraint` 에서 그 유일 제약의 **이름을 읽어** 오류 메시지에 그 이름이 있는지 보고,
**PK 이름에 걸린 경우를 `hit_pk_instead` 로 따로 단언해 배제**한다. **이름을 하드코딩하지 않는다** —
마이그레이션과 갈리면 그 순간 이 절이 다시 무의미해진다.

드러난다**(`미지명=[59]`) · `도구 없음(사람 관찰)` 명시가 있으면 통과.
selftest 는 이제 **10케이스**(출처 7 + 분모 3)다.

#### 규칙 8 (만기) — 형식은 내가 정했다

`check_sequence_gaps.py` 의 라벨을 **라운드 4 에 "사소"로 적고 다음 라운드에 고치기로 했는데
규칙 7 이 생길 때까지 열네 라운드를 살아남았다.** **기록은 수정을 보장하지 않는다.**

> `미뤄둠(만기: <블록 또는 라운드>) — <무엇을> · <만기가 지나면 무엇이 되는가>`

- **만기는 날짜가 아니라 게이트다.** "다음 라운드"는 라운드가 늘면 따라 밀린다.
  **"블록 8 실행 전"** 처럼 *지나갔는지 기계적으로 판정되는 시점*을 쓴다.
- **만기가 없는 "사소"는 쓰지 않는다.** 미룰 만큼 작으면 만기를 적을 수 있고,
  **만기를 못 적으면 그것은 사소한 것이 아니다.**

### 발견 8 — **빨간불 둘이 같은 종료 코드를 쓰고 있었다 (F-1)**

architect R20: 출처 위반(0건)과 미지명(36건)이 **둘 다 exit 1** 이었다. 출력에서는 구분되지만
**종료 코드에서는 같다.** 미지명 때문에 상시 빨간불인 동안 **진짜 출처 위반이 새로 생겨도
종료 코드가 안 바뀐다** — CI·절차·사람 모두 "그 빨간불은 아는 것"으로 읽고 지나간다.

**§7b 규칙 5 와 글자 그대로 같은 논리다.** 거기선 한 불리언이 여러 항목을 삼켰고,
여기선 한 종료 코드가 두 실패 종류를 삼킨다. **게이트를 무르지 않는 것과 가려지지 않게 하는
것은 다른 일이고, 나는 앞의 것만 했다.**

**고쳤다**: **출처 위반 = exit 1 / 미지명만 = exit 3.** 대조 4건을 넣었다(위반만 → 1 ·
미지명만 → 3 · **둘 다 → 1**(출처 위반이 더 무겁다) · 둘 다 없음 → 0). selftest 는
**14케이스**(출처 7 + 분모 3 + 종료코드 4)다. 현재 게이트는 **exit 3** — 출처 위반 0, 미지명 36.

고치면 `| **SC-87** | …` 같은 실제 판정 행을 놓칠 위험이 생긴다. **리포트 쪽 표기 규약으로 둔다:
판정하지 않는 표의 첫 칸을 `SC-` 로 시작하지 않는다.**
