## 범위
포함:
- **월드 상태**: 1 성계, 함선 엔티티(위치·속도·자세). 서버 메모리가 권위, 좌표는 `f64` 성계 로컬
- **이동 명령**: 클라이언트가 조작 의도(추력·회전)를 보내고 **tick 루프에서만** 적분한다. 클라이언트가 보낸 위치는 쓰지 않는다
- **상태 동기화**: 주기적 스냅샷(또는 델타) 브로드캐스트, 입력 시퀀스와 서버 확인(ack)
- **클라이언트 예측·보정**: 자기 함선은 즉시 반응, 서버 확정값과 차이가 크면 보정. 타 함선은 스냅샷 보간
- **접속·이탈 시 함선 스폰/디스폰**
- 그레이박스 비주얼(단순 도형 + 카메라)로 눈으로 확인 가능할 것

제외(다음 슬라이스로):
- 채굴·인벤토리·거래·전투 (p1-02 이후)
- 역사 이벤트 판정 — 이동은 역사가 아니다(절대 원칙 4). 스폰/디스폰을 도메인 이벤트로 남길지는 architect 판단
- 워프·성계 간 이동, 다수 성계
- **Floating Origin과 스케일 공간** — 이번엔 플레이 영역을 좌표 정밀도가 문제되지 않는 범위로 제한하고, 그 한계를 스펙에 수치로 명시한다. 영역을 넓히는 슬라이스에서 techart가 담당
- 함선 외형·모듈 비주얼·VFX (techart 미투입)
- 관심 영역 필터링(interest management) — 엔티티 수가 적어 전체 브로드캐스트로 충분

## 이 슬라이스가 증명할 것
1. 클라이언트 조작이 **서버 판정을 거쳐** 월드 상태를 바꾼다 (클라이언트가 보낸 위치를 서버가 믿지 않는다)
2. 여러 클라이언트가 **같은 월드를 본다** (A가 움직이면 B의 화면에서도 움직인다)
3. 예측·보정으로 **조작이 즉각 반응하면서도** 서버 값과 어긋나지 않는다
4. p0-02의 성능 기준선(tick 초과 0.000%, 왕복 p99 50.4ms)이 **게임 로직이 들어간 뒤에도** 유지되는지 측정한다

## 사용자 결정 (2026-09-19, designer 제안 Q1~Q4)
1. **조작 모델: 비행 보조 6DoF** — 마우스가 목표 자세, 로컬 축 추력, 상시 보조 감쇠 + 브레이크. 감쇠를 0으로 두면 완전 뉴턴이 되는 상위집합이라 되돌릴 수 있다. 평면 이동은 p1-04 전투에서 되돌리는 비용이 크다는 근거로 배제.
2. **속도·공간: 최대 140 m/s / 경계 반지름 12,000 m** — 보이는 목표까지 10~30초 기준. 기준물이 4.2 km 안에 모여 있어 그 이상은 빈 공간이 된다. 첫 측정 후 데이터 파일만 고쳐 조정 가능.
3. **기준 마커 4개 넣는다** — 클라이언트 전용 정적 비주얼. 없으면 빈 공간에서 움직이는지 눈으로 확인할 수 없다.
4. **끊긴 함선 30초 잔류** — 0.5초 직진 → 관성 미끄러짐 → 30초 뒤 디스폰. 30초 안에 재접속하면 같은 함선·같은 자리에서 재개.
