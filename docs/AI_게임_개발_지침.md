# AI로 3D 게임을 만들 때의 지침

> 이 저장소에서 일하는 사람과 AI 에이전트는 **작업을 시작하기 전에 이 문서를 읽는다**(CLAUDE.md에서 링크).
> 1부는 원칙 원문이다. 2부는 그 원칙을 STARFALL DYNASTY에서 지키는 구체적인 방법이다.

---

## 1부. 원칙 (원문)

AI는 게임 개발 속도를 높일 수 있지만, 결과는 게임을 얼마나 명확하게 계획하고 프롬프트를 작성하며 테스트하는지에 따라 달라집니다. 몇 가지 간단한 습관만으로도 흔한 문제를 피하고 개발 과정을 관리하기 쉽게 유지할 수 있습니다. 3D 게임을 만들고 개선할 때 다음 사항을 염두에 두세요.

### 권장 사항

**단순하고 명확한 게임 아이디어로 시작하기**
처음부터 방대한 게임을 만들려 하기보다, 하나의 분명한 게임플레이 목표로 시작하세요. 집중된 아이디어일수록 만들고, 테스트하고, 개선하기가 쉽습니다.

**AI를 위한 상세한 프롬프트 작성하기**
배경, 게임플레이, 캐릭터, 시각적 스타일 등 원하는 내용을 AI에 정확히 알려주세요. 세부 사항이 명확할수록 원래 아이디어에 더 가까운 결과를 얻을 수 있습니다.

**게임플레이를 일찍, 자주 테스트하기**
모든 작업이 끝날 때까지 기다리지 말고 중요한 변경 사항을 적용한 뒤에는 게임을 플레이해 보세요. 조기에 테스트하면 제대로 작동하지 않는 조작, 혼란스러운 목표 및 기타 문제를 빠르게 발견할 수 있습니다.

**AI 생성 콘텐츠 검토 및 다듬기**
AI가 생성한 콘텐츠는 게임에 잘 어울리도록 수정이 필요할 수 있습니다. 각 요소를 꼼꼼히 확인하고, 구상과 맞지 않는 부분은 AI에 조정을 요청하세요.

### 피해야 할 사항

**대상 플랫폼을 정하지 않고 시작하지 않기**
게임을 만들기 전에 브라우저, 컴퓨터 또는 다른 플랫폼 중 어디에서 실행할 게임인지 결정하세요. 그러면 적절한 조작 방식, 시각 요소, 성능 설정을 선택하는 데 도움이 됩니다.

**너무 이른 단계에 기능을 지나치게 많이 추가하지 않기**
한꺼번에 많은 메커니즘을 추가하면 게임을 관리하고 테스트하기 어려워질 수 있습니다. 먼저 핵심 게임플레이를 구축한 다음, 새 기능을 점진적으로 도입하세요.

**테스트 없이 AI 결과물에 의존하지 않기**
AI는 예상대로 작동하지 않는 코드, 메커니즘, 콘텐츠를 생성할 수 있습니다. 기능이 완성되었다고 판단하기 전에 실제 게임에서 모든 것을 테스트하세요.

**성능 최적화를 무시하지 않기**
오브젝트, 효과 또는 용량이 큰 에셋이 너무 많으면 게임이 느려지고 플레이하기 어려워질 수 있습니다. 개발하는 동안 로딩 시간, 프레임 레이트, 전반적인 반응성을 계속 확인하세요.

## 2부. 이 프로젝트에서의 적용

### 기준 결정 (바꾸려면 리드 결정이 필요하다)

| 항목 | 결정 | 근거 |
|---|---|---|
| 대상 플랫폼 | **PC 스탠드얼론(Windows 우선)이 기준 성능 타깃.** 브라우저(WASM/WebGL)는 나중에 별도 최적화 타깃 | 기획안 §47 |
| 그래픽 API | wgpu: Windows 기본은 Vulkan, DX12 폴백. 레이 트레이싱은 Vulkan과 NVIDIA RTX에서만 쓰는 선택 계층 | 2026-10-17 RT 스파이크 |
| 조작 | 키보드와 마우스(6자유도: W/S, A/D, R/F, Q/E, Z/Ctrl, Alt+A/D, 우클릭 조종) | 게임 내 단축키 안내 |
| 핵심 플레이 목표 | **역사를 만드는 함장:** 탐험·전투·교역의 결과가 연대기에 남는다 | 기획안 §0 |
| 최종 목표 | 홈월드식 3D 자유도, 일관된 아트 디렉션 | 이 대화의 리드 결정 |

### 원칙별 실천

| 원칙 | 여기서 하는 일 | 확인 수단 |
|---|---|---|
| **단순한 목표부터** | 기능 하나를 *플레이어 루프 한 줄*로 먼저 쓴다(예: "첫 도달자가 항로를 연다"). 한 라운드에 한 가지 주제만 다룬다. | 보고서 첫 줄의 "설계 의도" |
| **상세한 프롬프트** | 게임플레이는 시나리오 JSON으로 기대 동작을 먼저 쓴다(sim-first). 비주얼은 `docs/ART_DIRECTION.md`의 마스터 블록과 카테고리 프롬프트로 시작한다. | `crates/sim/scenarios/*.json`, ART_DIRECTION §2 |
| **일찍, 자주 테스트** | 변경할 때마다 빠른 테스트 루프를 돈다. 플레이 QA는 사람 대신 봇 둘이 실제 서버에서 한다. 조작감과 미감만 사람이 본다. | `cargo test -p shared -p history -p sim -p view`, `cargo run -p bot --release --example qa` |
| **생성물 검토·다듬기** | AI가 만든 코드, 수치, 이미지는 결과를 *숫자와 스크린샷*으로 확인한 뒤에만 완료로 본다. 룩 변경은 참고 이미지와 비교해서 승인한다. | `tools/imgdiff.py`, `python tools/artcheck.py` |
| **플랫폼 먼저** | 새 기능은 PC 기준 조작·성능으로 설계한다. 브라우저 전용 제약(WebGL 한계)을 기본 가정으로 삼지 않는다. | 위 기준 결정 |
| **기능 과잉 금지** | 한 번에 하나의 메커니즘. 새 수치는 `tuning/*.ron`에 둔다. 리드 결정이 필요한 것은 A/B로 묻고 기다린다. | 커밋 단위, 결정 요청 |
| **테스트 없는 신뢰 금지** | "빌드됨"은 완료가 아니다. 테스트 통과, 시나리오 기대값, 다이제스트, 실제 클라이언트 화면까지 본다. 확인하지 못한 것은 보고에 "미확인"으로 쓴다. | 시나리오 다이제스트, 옛 기록 재생, 봇 e2e |
| **성능 상시 확인** | 무거운 단계는 `shared::prof::span`으로 감싼다. 변경 전후의 틱 비용과 프레임 시간을 수치로 비교한다. | `cargo run -p sim --release --example bench 1000`, `client --bench 15` |

### 성능 예산 (현재 기준)

- 서버: 플레이어 1,000명일 때 틱 평균 약 8 ms(예산 50 ms).
- 클라이언트: 함선 약 1,000척(`STARFALL_BENCH_SCALE=15`)에서 60 FPS 이상이 목표. 레이 트레이싱 계층도 같은 기준(DLSS 사용).
- 에셋: 함선 텍스처 2048²(대형 함선 4096²). 이보다 크게 하려면 근거와 측정이 필요하다.

### 작업 체크리스트 (모든 라운드)

1. 목표를 한 줄로 쓴다. 기준 결정을 벗어나지 않는지 확인한다.
2. 게임플레이면 시나리오 JSON을, 비주얼이면 프롬프트와 참고 이미지를 먼저 쓴다.
3. 구현한다. 수치는 `tuning/`에, 색은 `palette.rs`에 둔다.
4. 테스트한다: 로직 → 시나리오 → 밸런스 diff → 옛 기록 재생 → 봇 QA → (비주얼이면) artcheck와 스크린샷.
5. 성능을 측정한다(bench, prof).
6. 확인한 것과 못 한 것을 구분해 보고하고, 결정이 필요한 것은 A/B로 묻는다.
