# 개발 하네스 (Game-as-Harness)

## 근거

카일 쿡슈텔의 발표 「당신의 게임이 하네스다(Your Game Is A Harness)」(Indie Rodeo, 2026-09)를 박재홍이 정리한 글
「게임 개발용 AI 하네스를 설계하는 법」(https://wikidocs.net/blog/@jaehong/33381/ , 원문: *How to engineer an AI harness for game development*)을 근거로 한다.

글의 출발점은 다음 문장이다.

> LLM이 게임에서 제대로 일하게 만드는 것은 **컨텍스트 문제**다.

LLM은 코드는 잘 읽지만 3D 모델, 소리, 장면처럼 코드가 아닌 것은 보지 못한다. 그래서 게임 바깥에 도구를 더 쌓기보다,
**게임 자체를 에이전트가 읽고 조종하고 숫자로 검증할 수 있게 설계하는 것이 곧 하네스**라는 주장이다.
이렇게 하면 "고치고 확인하는" 루프를 몇 초 만에 돌 수 있으므로, 큰 변경 때만이 아니라 모든 변경에 검증을 돌릴 수 있다.

글이 제시하는 개발 플라이휠은 네 단계다.

1. 결정론적인 입력 — 같은 상태를 매번 정확히 다시 만든다.
2. 컴파일 없이 구조화된 방식으로 상태를 바꾼다 — 커맨드와 외부 데이터.
3. 외부와 떨어진 환경에서 검증한다 — 엔진 없는 시뮬레이션.
4. 영향을 숫자와 텍스트로 평가한다 — 이미지 디프 수치, 텍스트 프로파일러.

댓글의 통찰도 같이 기록해 둔다. 퐁처럼 단순한 게임을 몇 주 고칠 때 모델이 매번 다른 곳을 망가뜨렸다는 사례가 있다.
그래서 하네스가 필요한지는 게임의 크기보다, **이미 만든 게임을 얼마나 오래 고쳐 나가느냐**로 판단하는 편이 맞다.
STARFALL은 이미 서버·클라이언트·역사 엔진·1000명 교전까지 쌓였으므로 지금이 도입 시점이다.

## 이번에 적용한 핵심 (1단계)

글의 플라이휠 가운데 STARFALL에 **이미 있는 것**(분리된 시뮬레이션, 커맨드, 단일 객체 타입, 텍스트 측정)은 그대로 두었다.
**빠져 있던 연결 고리 두 개**만 메웠다.

### 1. 상태 재현: 커맨드 기록·재생과 결정론

한 번의 플레이를 폴더 하나로 남기고, 그 폴더가 스스로를 재현한다.

```
server --dev --record rec/bug42                                    # 플레이하며 기록 (평소처럼 접속)
cargo run -p sim --release --example replay -- rec/bug42 --twice
#  replayed 1500 ticks (75 s of play) in 0.35 s — 13445 commands, 15 digests checked, final state 823b…
#  REPLAY OK: every recorded digest matched
#  DETERMINISTIC: second replay ended in the same state
cargo run -p sim --release --example replay -- rec/bug42 --dump 7@1200   # 그 순간 성계 7의 엔티티 표(텍스트)
```

- **`rec/X/initial/`**: 기록을 시작할 때의 `profiles.json`, `history.jsonl`이다. 재생은 이 파일의 사본에서 출발하므로 기록본은 바뀌지 않는다.
- **`rec/X/session.jsonl`**: 첫 줄은 헤더(시작 시각, dev 여부)다. 이후 각 줄은 틱 하나로, 그 틱에 들어온 커맨드, 바뀐 시계, 발급된 토큰, 5초마다 찍는 상태 다이제스트를 담는다.
- **다이제스트**: 모든 엔티티(위치는 비트 단위), 계정·프로필·잔해·시장·동맹, 역사 기록을 FNV-1a로 지문화한 16자리 값이다. "내 수정이 결과를 바꿨나?"가 한 줄 비교가 된다.
- **보장 테스트**: `crates/sim/tests/harness.rs`는 War Zone 교전, 해적, 미사일, 접속 끊김 후 토큰 재접속을 기록한다. 재생 결과가 모든 다이제스트와 실제 최종 상태에 일치하고, 두 번 재생해도 같아야 통과한다.
- **실측**: 실제 서버에서 봇 40명이 75초 동안 교전한 기록을 재생했다. 커맨드 13,445개, 격침 97회였고, 재생은 0.35초 걸렸으며 다이제스트 15개가 모두 일치했다.

### 2. 영향 평가: 시각 변화를 숫자로

```
STARFALL_FIXED_FPS=60 STARFALL_HIDE_UI=1 client --showroom 7 --shot before.png --shot-at 8
#  … 코드 수정 후 같은 명령으로 after.png
python tools/imgdiff.py before.png after.png --crop 380,90,220,200 --out diff.png
#  similarity=…% changed=…% mean_delta=… changed_bbox=X,Y,W,H | before white=… lum=… sat=… | after white=… lum=… sat=…
python tools/imgdiff.py --stats after.png --crop 380,90,220,200    # 영역의 밝기/백색 비율/채도
```

- **`STARFALL_FIXED_FPS=60`**: 프레임마다 시간을 정확히 1/60초씩 진행한다. 회전체도 누적 대신 시각의 함수로 바꿨다. 그래서 같은 명령의 두 실행이 **유사도 100.00%**가 된다. 디프에 잡히는 차이는 전부 코드 변경 때문이다.
- **실제 사용 예 — 주력함 엔진 화염**: "흰 원뿔/유리구슬처럼 보인다"는 문제를 이 루프로 고쳤다. 화염 영역의 밝은 픽셀 비율과 채도를 매 수정마다 쟀다.

  | 시점 | 밝은 픽셀 비율 | 채도 |
  |---|---|---|
  | 측면, 수정 전 → 후 | 0.156 → 0.093 | 0.209 → 0.260 |
  | 후면, 수정 전 → 후 | 0.100 → 0.008 | — |

  한 번은 "변화 없음"이라는 수치 덕에 잘못된 가설(엔진 코어 재질)을 바로 버렸다.

## 에이전트·개발자 작업 루프

1. **재현**: 문제가 서버 상태에 있다면 `--record`로 남긴 폴더를 `replay`로 재현한다. `--dump`로 원하는 틱의 상태를 텍스트로 본다. 화면으로 봐야 하면 `client --replay DIR --from SECS --shot X.png --shot-at T`로 그 순간을 찍는다.
2. **안쪽 루프 (화면 없이)**: `cargo test -p sim -p shared -p history -p view`로 검증한다. 시뮬레이션은 엔진 없이 몇 초면 돈다. 바뀐 규칙이 결과를 바꾸는지는 재생 다이제스트로 확인한다. 의도한 변경이라면 다이제스트가 달라지는 것이 정상이다.
3. **바깥 루프 (화면에 영향이 있을 때만)**: 고정 프레임 스크린샷과 `imgdiff` 수치로 목표에 가까워졌는지 판단한다. 이미지는 마지막에 사람이 확인한다.
4. **성능**: `sim/examples/bench N`, `client --bench`, `bot/examples/swarm`의 텍스트 수치를 이전 값과 비교한다.

## 2단계: 게임을 실행하지 않는 결정론 개발 구조

목표는 **게임을 띄우지 않고도 개발과 검증이 끝나는 영역을 최대한 넓히는 것**이다. LLM에게 맡기면 효율적인 일, 즉 규칙·수치·상태 전이·네트워크 동작·좌표 계산은 이 영역으로 끌어온다. 게임을 실행해야만 판단할 수 있는 일(셰이더·모델의 느낌, 소리, 조작감)만 바깥 루프에 남긴다.

### 원칙: 시뮬레이션 우선(sim-first)

새 게임플레이 기능이나 규칙 변경은 이 순서로 진행한다.

1. **기대 동작을 시나리오 사양(JSON)으로 먼저 쓴다.** 누가 어디에 있고, 무엇을 하면, 언제 무엇이 참이어야 하는지 적는다. 처음에는 실패하는 사양이 된다.
2. `shared`/`sim`에서 규칙을 구현하고, `cargo run -p sim --release --example scenario -- FILE --trace 5`로 측정값을 텍스트로 보며 고친다. 수백 초를 시뮬레이션해도 수 밀리초면 끝난다.
3. 수치가 바뀌는 변경이면 `examples/balance`로 밸런스 시트를 다시 뽑아 `docs/BALANCE.md`의 diff로 영향을 확인한다.
4. 클라이언트는 받은 상태를 그리기만 한다. 화면은 마지막에 고정 프레임 스크린샷과 `imgdiff`로 확인한다.

### 시나리오 사양 (`crates/sim/scenarios/*.json`)

파일 하나가 테스트 하나다. `cargo test -p sim --test scenarios`가 전부 돌리고, 각 사양을 두 번 실행해 같은 상태로 끝나는지(결정성)도 검사한다. Rust 코드를 고치지 않고 파일만 추가하면 된다.

```json
{
  "name": "capital_vs_raiders",
  "description": "주력함(모듈 Lv9)의 포탑만으로 해적 습격대 4척을 격퇴한다",
  "captains": [ { "name": "Ares", "hull": "Bastion", "level": 9, "system": 7, "pos": [0, 0, 6000] } ],
  "npcs":     [ { "archetype": "Raider", "level": 3, "system": 7, "pos": [0, 0, 5200], "count": 4 } ],
  "script":   [ { "at": 0.5, "captain": "Ares", "target_nearest": "npc", "aim": true,
                  "msg": { "Controls": { "fire": true } }, "repeat_every": 0.1 } ],
  "run_secs": 60,
  "expect": [
    { "check": "alive", "captain": "Ares" },
    { "check": "count", "system": 7, "kind": "npc", "max": 0 },
    { "check": "kills", "captain": "Ares", "min": 4 },
    { "at": 30, "check": "hull", "captain": "Ares", "min": 0.8 }
  ]
}
```

- **captains**: `hull`, `level`(모든 모듈), `system`, `pos`, `heading`(도), `species`, `profession`, `undocked`, `credits`를 정한다. `near_poi`(`"Ruin"` 등)와 `offset`이면 그 성계의 첫 해당 지점 옆에 놓는다.
- **npcs**: `archetype`, `level`, `system`, `pos`, `count`, `spacing`을 정한다. `ambient_pirates: true`면 배경 해적 생성을 켠다(기본은 꺼져 있다).
- **script**: `at`초에 `captain`이 `msg`(임의의 `ClientMsg` JSON)를 보낸다.
  - `repeat_every`와 `until`로 반복 입력을 보낸다.
  - `target_nearest`(`npc`/`player`)로 가장 가까운 대상을 지정하고, `aim`으로 그 대상을 향해 조종한다.
  - `target_captain`은 이름으로 목표를 지정한다. 그 함장이 격침되면 이 단계는 건너뛴다.
  - `fill_nearest`는 메시지의 id를 가장 가까운 대상으로 채운다: `"poi:Ruin"`(→ `Scan`), `"wreck"`(→ `InvestigateWreck`), `"contract"`(가장 최근의 열린·진행 계약 → `AcceptContract`·`CancelContract`·`DeliverContract`). 사양에 엔티티·지점 id를 적지 않아도 된다.
- **expect**: `at`초에 검사한다(생략하면 끝에서). 검사 종류: `alive`, `hull`, `credits`, `kills`, `deaths`, `count`(`npc`/`player`/`escort`/`wreck`), `in_system`, `history`(연대기 종류, 대소문자 무시), `engagement`, `dealt`·`taken`(가한·받은 피해), `dps`, `ttk`(평균 격파 시간), `artifacts`(보유 유물 수), `reputation`, `influence`(`system`·`tag`), `controller`(`system`, `tag` 생략 시 무주지), `treasury`(`tag`), `institute`(`name`, `exhibits_min`, `visitors_min`/`max`). `fill_nearest`는 쉼표로 여러 개(`"artifact,institute"`)를 채울 수 있다. 함장에 `cargo`(광석 이름 → 단위)로 시작 화물을 줄 수 있다.
- **digest**(선택): 최종 상태 지문을 고정한다. 결과가 조금이라도 바뀌면 실패하므로, 회귀를 엄격히 잡을 때만 쓴다(`--print-digest`로 값을 얻는다).

실패하면 측정값이 함께 나오므로(`FAIL t=45.0s system 7 npc count 1 (want <= 0)`), 무엇을 고쳐야 할지 텍스트만으로 판단할 수 있다.

### 밸런스 시트 (`docs/BALANCE.md`)

`cargo run -p sim --release --example balance -- --write docs/BALANCE.md`는 함선 5종 × 모듈 Lv 1/5/9가 NPC 조우 5종과 싸우는 75판을 약 1초에 시뮬레이션해 표로 남긴다. 결정적이므로 수치 변경의 영향이 표의 diff로 드러난다.

첫 시트에서 보인 관찰과, 그에 따른 결정이다.

- **관찰**: 모듈 Lv5(순양함)부터는 Warlord를 뺀 모든 조우를 선체 피해 0%로 이겼다. 실드가 모든 피해를 흡수하고 다시 차오르는 사실상의 무적이었다.
- **결정**: 무적은 없다. 약한 기체가 강한 기체나 실드를 때려도, 차이가 크더라도 1포인트라도 깎여야 한다.
- **규칙**(`game/sim.rs`):
  - 모든 피격의 10%(`tuning/combat.ron`의 `shield_bleed`)는 실드를 통과해 선체에 들어간다. 나머지는 실드가 받고, 실드가 바닥나면 넘친 만큼 선체로 간다.
  - 명중한 공격은 최소 1포인트(`min_hull_damage`)의 선체 피해를 준다. 총 피해량은 그대로이고 배분만 바뀐다.
- **사양**: 이 순서대로 진행했다.
  1. `scenarios/no_invulnerability.json`(갓 만든 전투기가 Lv9 주력함을 쏘면 선체가 깎인다)을 먼저 써서 실패를 확인했다.
  2. 규칙을 바꿔 통과시켰다.
  3. `tests/game.rs`의 `no_ship_is_invulnerable`로 1포인트 하한과 10%/90% 배분을 직접 고정했다.
- **영향**(시트 diff): 명중이 있었던 모든 칸에서 선체가 깎인다. 예를 들어 Lv9 Bastion은 Warlord에게 125포인트, Lv5 Wren은 Raider 4척에게 77포인트를 잃는다. `−0`은 NPC가 한 발도 맞히기 전에 격파된 경우다.

### 이번 단계에서 추가한 것

- `sim::scenario`(사양 형식·실행기), `examples/scenario`(CLI, `--trace`, `--print-digest`), `tests/scenarios.rs`(전 사양 통과 + 결정성)
- 시나리오 5종: 주력함 대 해적 무리, 전투기 결투, Core 안전 지대, Wild 범죄·현상금, 연속 워프
- `examples/balance` → `docs/BALANCE.md`
- `tests/interest.rs`: 400척 성계의 관심 영역 관리를 소켓 없이 검증한다(스냅샷 예산, 4틱 안에 전체 파악, 이탈 엔티티 제거, 바이너리 왕복).
- `Controls`의 빠진 축을 0으로 기본값 처리해, 사양과 스크립트에 `{"fire": true}`처럼 필요한 것만 쓰게 했다.

## 3단계: 데이터를 코드 밖으로 (`tuning/*.ron`)

밸런스 수치는 코드가 아니라 작업 공간 루트의 `tuning/`에 있는 텍스트 파일이다. 실행할 때 읽으므로, **수치 파일을 고치고 → 밸런스 시트나 시나리오를 다시 돌리고 → diff를 읽는** 루프에 재컴파일이 끼지 않는다(75판 밸런스 시트가 1초 안팎).

| 파일 | 내용 |
|---|---|
| `ships.ron` | 선체 5종의 Lv1 능력치, 모듈 레벨당 성장률, 함급(소형함·순양함·주력함)의 시작 랭크·크기/체력 배율·포탑·주포·호위함 수, 포탑/주포 배율, 모듈 업그레이드 비용, 호위함 능력치 |
| `npcs.ron` | NPC 레벨 배율, 공통 사거리·재충전·포탑 수치, 아키타입 5종의 능력치·선회·포탑 수·현상금 |
| `combat.ron` | 실드 관통 비율, 명중당 최소 선체 피해, 조준 원뿔(전투기·락온 유지·AI·주포) |
| `history.ron` | 증거 위조 비용, 감정 비용(역사학자 무료), 위조 폭로 시 위조자·감정자 평판과 보상, 위조 증거를 인용한 연구에 남는 신뢰 비율, 기자의 송고료·독자당 원고료·독자 상한·정정 시 평판 |
| `social.ron` | 계약 최소 보상, 최장 기한, 의뢰인당 진행 계약 수, 완수·배신 시 평판, 활동별 영향력, 지배 기준치·역전 여유, 시간당 감쇠, 지배 동맹 보너스, 교전 승패 영향력, 세율, 과잉 확장 계수, 무료 성계 수, 유지비(기본·지수), 기관 설립비·관람 수입·전시 평판 |
| `artifacts.ron` | 유물 문화(인류·Veyr·Kharz·선구자)별 기본 가치와 이름 재료, 가치 편차, 감정 비용, 미감정 판매 비율, 기증 평판·사례금 |

- **찾는 순서**: `STARFALL_TUNING` 환경 변수 → 현재 디렉터리와 그 상위의 `tuning/` → 실행 파일 위치와 그 상위. 다른 수치로 비교 실험하려면 폴더를 복사해 고친 뒤 `STARFALL_TUNING=DIR`로 돌린다.
- **오타는 오류다**: 모르는 필드나 빠진 필드, 빠진 선체·모듈·함급·아키타입이 있으면 파일과 위치를 밝히며 로드에 실패한다. 조용히 기본값으로 돌아가지 않는다.
- **이름·설명 문구는 코드에 남는다**: 선체 이름, 모듈 설명, 랭크 이름, 최대 모듈 레벨(10)과 랭크 공식처럼 구조를 정하는 값은 데이터가 아니다.
- **서버가 기준이다**: 접속 시 `Welcome`에 서버의 수치가 실려 오고, 클라이언트는 그것을 설치해 HUD·워프 사거리를 서버와 같은 값으로 계산한다. 접속 전(캐릭터 생성 화면, 쇼룸)에는 로컬 `tuning/`을 읽는다.
- **기록은 수치를 함께 남긴다**: `server --record DIR`이 `DIR/tuning/`에 복사본을 두고, 재생은 그것을 설치한다. 수치를 고친 뒤에도 예전 기록이 그대로 재현된다. 이전 형식의 기록(복사본 없음)은 현재 수치로 재생하고, 기록보다 나중에 생긴 파일(예: `artifacts.ron`)은 현재 파일로 채운다.

옮길 때 부동소수 연산 순서를 그대로 유지해, 시나리오 6종의 다이제스트와 `docs/BALANCE.md`가 비트 단위로 같게 나왔다. `tests/tuning.rs`는 수치 하나를 바꾸면 시나리오 결과가 달라지고, 되돌리면 정확히 같은 상태로 돌아오는지 검사한다.

## 4단계: 클라이언트 순수 로직 분리 (`crates/view`)

클라이언트가 화면에 올리기 전에 하는 계산을 Bevy와 무관한 크레이트 `view`로 옮겼다. 의존성은 `shared`와 `egui`뿐이므로 Bevy를 컴파일하지 않고 `cargo test -p view`로 몇 초 만에 검사한다. 클라이언트는 결과를 엔티티와 화면에 옮기기만 한다.

| 모듈 | 내용 | 테스트가 고정하는 것 |
|---|---|---|
| `interp` | 스냅샷 보간(다른 함선은 0.1초 과거), 내 함선 추측항법 | 중간 지점 보간·회전 slerp, 추측 상한 0.12초, 뒤로 가지 않음, 새로 나타난 엔티티 |
| `relation` | 내 함선·아군·적대·중립·잔해 판정. HUD 브래킷과 우주 지도가 같은 규칙을 쓴다(이전에는 두 곳에 복사되어 있었다) | 호위함·함대·동맹, Core에서는 동맹 전쟁도 중립, Wild의 PvP |
| `mapview` | 우주 지도의 투영·역투영, 커서 기준 확대, 은하 전도↔성계 연속 전환, 상단 버튼 동작 | 왕복 오차, 북(-Z)이 위, 커서 아래 지점 고정, 한계를 넘으면 전환, 드래그하면 추적 해제, 다시 열면 내 위치 |
| `gauge` | 실드/선체 게이지의 '방금 잃은 부분' 잔상과 선체 피격 섬광 | 초당 0.35 감소, 회복은 즉시, 실드 피해는 섬광 없음, 멈춘 프레임은 최대 0.25초만 진행 |
| `dust` | 카메라를 감싸는 먼지장의 크기·감싸기·가장자리 페이드 | 함선 크기에 따른 상자 크기와 한계, 상자 단위 이동만, 가장자리와 카메라에서 0 |
| `hud` | 조준선 게이지, 손실 표시 막대, 함선 상태 패널(egui 그리기) | 아래 헤드리스 검사 |

**HUD 헤드리스 검사**(`crates/view/tests/hud.rs`): 창이나 GPU 없이 egui 컨텍스트에서 HUD 함수를 몇 프레임 실행하고, 나온 도형(글자와 그 화면 사각형, 채운 사각형과 색, 선과 색)을 검사한다. 페이드인 애니메이션은 꺼서 색이 그린 그대로 나온다.

- 조준선 게이지: `실드 50%`·`선체 80%` 글자가 원호 바깥, 조준선 높이에 있다. 잃은 부분은 주황 원호 하나로, 왼쪽(실드) 게이지 반지름 위에 그려진다. 선체가 낮으면 빨갛게 깜박인다.
- 손실 막대: 배경 200 px, 손실 120 px, 채움 60 px가 이 순서로 겹친다.
- 함선 상태 패널: `에너지 실드 150/300`처럼 `Ship::stats()`의 실제 수치가 나오고, 실드 막대가 선체 막대 위, 속도·화물 줄이 그 아래에 있으며, 모든 글자가 화면 안에 있다. 주력함은 포탑·주포·호위함 수를 보이고 성장 안내는 숨긴다.

옮기기 전후로 쇼룸 스크린샷(`--showroom 7`, `--hull Talon` 포함)이 `imgdiff` 100%로 같았다. 실서버에 접속해 HUD, 성계 지도, 은하 전도도 직접 찍어 확인했다.

## 5단계: 재생 시각화 (`client --replay DIR`)

기록 폴더를 3D 클라이언트로 재생한다. 기록된 시뮬레이션이 클라이언트 안에서 클라이언트 시계에 맞춰 돌고, 지켜보는 함장에게 보냈던 메시지가 **실제 전송 형식(바이너리 스냅샷·JSON)으로 인코딩·디코딩된 뒤 네트워크와 같은 채널로** 들어간다. 그래서 화면은 그 함장이 실시간으로 본 것과 같은 코드 경로로 그려진다.

```
client --replay rec/bug42                               # 처음 로그인한 함장의 시점으로 실시간 재생
client --replay rec/bug42 --as Ares --from 25 --speed 2 # Ares 시점, 25초부터 2배속
STARFALL_FIXED_FPS=60 client --replay rec/bug42 --from 25 --shot a.png --shot-at 10
#  [replay] end of recording at tick 800: REPLAY OK: every recorded digest matched (8 checked) — final state 3983…
```

- **상태와 화면을 한 번에**: 재생하면서 기록된 다이제스트를 대조하고, 기록이 끝나면 판정 한 줄(`REPLAY OK` / `REPLAY DIVERGED at tick T`)과 최종 다이제스트를 표준 출력에 낸다. 이 다이제스트는 `examples/replay`의 것과 같다. `STARFALL_FIXED_FPS`를 주면 같은 명령은 같은 이미지를 낸다(두 번 찍어 `imgdiff` 100%). 그래서 버그 보고 폴더 하나가 재현되는 상태이자 재현되는 그림이 된다. 코드를 고친 뒤 같은 명령으로 다시 찍어 `imgdiff`로 비교하면 화면 차이가 수치로 나온다.
- **입력은 무시한다**: 재생 중 조종·핑 같은 클라이언트 명령은 버린다. 카메라 전환(C), 지도(M), 함교(I) 같은 보기 조작은 그대로 된다.
- **토큰은 남기지 않는다**: 기록의 토큰은 가명이고, 재생은 빈 토큰을 넘기므로 클라이언트가 로그인 정보로 저장하지 않는다.
- **`--as`**: 함장 이름으로 시점을 고른다. 재접속으로 연결이 바뀌어도 그 함장을 따라간다. 끝까지 로그인하지 않으면 그 사실을 출력한다.
- **기반**: `harness::Replayer`가 기록을 한 틱씩 진행한다(`Session::replay`도 이것을 쓴다). 각 틱이 보낸 메시지를 다음 틱까지 `game.out`에 남겨 두어, 보는 쪽이 한 연결의 메시지만 골라 갈 수 있다. `tests/harness.rs`는 단계 재생이 실시간 상태와 같게 끝나고, 함장 연결에 환영 메시지 1개와 스냅샷이 전달되는지 검사한다.
- **주의**: 서버를 강제 종료(`taskkill /F`)하면 기록 파일의 마지막 다이제스트 이후 부분은 디스크에 남지 않는다. Ctrl+C로 끄면 끝까지 남는다.

## 6단계: 게임플레이 관측성 (`sim::metrics`)

전투가 어떻게 흘러갔는지를 시간축 수치로 남긴다. 화면을 보지 않고도 "이 함선은 이 적을 초당 얼마로 때리고, 얼마나 맞고, 몇 초 만에 격침하는가"를 텍스트로 비교한다.

- **수집**: `Game::metrics`가 `Some`이면 시뮬레이션이 명중마다(실드 흡수량·선체 피해, 쏜 쪽·맞은 쪽 함장), 격침마다(격파한 함장, 격파 시간), 현상금 지급마다 이벤트를 쌓는다. 시뮬레이션은 이 값을 읽지 않으므로 결과가 바뀌지 않는다(`tests/metrics.rs`가 수집 여부와 상관없이 다이제스트가 같은지 검사한다). 끄면 비용은 명중마다 `Option` 검사 하나다.
- **격파 시간(ttk)**: 그 함선이 30초 넘게 맞지 않다가 처음 맞은 때부터 격침까지의 시간이다.
- **집계**(`MetricsLog`): 함장별 누계와 JSONL 줄로 바꾼다. 함장의 쪽은 기함과 호위함을 합친다.

```text
{"t":2.0,"ev":"sample","player":"Wing","dealt":82.08,"taken":17.55,"dps_out":82.08,"dps_in":17.55,"hull":1.0,"shield":0.93,"kills":0,"credits":1500}
{"t":8.05,"ev":"kill","sys":7,"victim":"Gunship Lv1","killer":"Wing","ttk":7.5}
{"t":8.05,"ev":"reward","player":"Wing","credits":935}
```

| 어디서 | 어떻게 |
|---|---|
| 시나리오 | 항상 켜져 있다. 실행 결과에 함장별 요약 줄(`metrics Wing: dealt 636 (31 hits, 84.3 dps) · taken 193 · kills 1 · mean ttk 7.5 s · bounty 935 CR`)이 나오고, `--metrics DIR`이면 `DIR/<이름>.jsonl`을 쓴다. 검사 종류 `dealt`, `taken`, `dps`(첫 명중부터 마지막 명중까지의 평균), `ttk`(격파한 적의 평균 격파 시간)가 추가됐다. `fighter_duel_gunship`이 이 검사를 쓴다. |
| 밸런스 시트 | `docs/BALANCE.md`에 「교전 수치」 표가 추가됐다. 칸은 `가한 DPS/받은 DPS · 평균 격파 시간`이다. 수치를 고치면 승패 표와 함께 이 곡선이 diff로 바뀐다. |
| 실서버 | `server --metrics FILE.jsonl`. 교전 중인 함장만 초마다 한 줄을 남긴다(1000명 서버에서도 조용한 함장은 쓰지 않는다). 격침·보상 줄은 그대로 남는다. 20명 군집 전투(`bot` swarm)로 확인했다. |

첫 「교전 수치」 표에서 보이는 것: Lv1 함선은 Raider L3 x4에게 초당 93~107 피해를 받는다(Lv5는 48~68). Lv9끼리는 같은 적이라도 가한 DPS가 365(Talon, Raider L1)에서 1558(Bastion, Gunship L2)까지 벌어진다. 적이 너무 빨리 죽어 짧은 교전 시간으로 나뉘는 탓도 있으므로, 비교는 같은 열 안에서 한다.

## 7단계: 텍스트 프로파일러 (`shared::prof`)

**`samply` 대신 내장 구간 프로파일러로 정했다.** `samply`는 이 PC에 설치되어 있지 않았다. Windows에서는 ETW로 기록하므로 관리자 권한이 필요한데, 이 작업 세션은 관리자 권한이 아니었다. 결과도 Firefox Profiler용 JSON이라 텍스트로 읽으려면 변환기가 따로 필요하다. 그래서 의존성 없는 구간(span) 프로파일러를 `shared`에 넣었다. 권한 없이 어디서나 돌고, 결과가 바로 텍스트 표다.

- **쓰는 법**: `let _s = shared::prof::span("weapons");` — 범위가 끝날 때까지의 시간을, 그 스레드에서 열려 있는 구간 아래에 중첩해 기록한다. `prof::take().report(N, "tick")`이 호출 트리(호출 수, 총·자기 시간, 단위당 ms, 비율)와 자기 시간이 큰 구간 목록을 낸다.
- **비용**: 끄면 구간마다 원자적 읽기 한 번이다. 켜도 1000명 벤치 틱 시간이 측정 오차 안이었다(10.1–10.8 ms, 켜고 끈 두 번씩). 시간 값은 게임 상태로 돌아가지 않으므로 결정론과 무관하다(시나리오 다이제스트·밸런스 시트 동일).

| 어디서 | 명령 | 단위 |
|---|---|---|
| 서버 벤치 | `cargo run -p sim --release --example bench 1000` (항상 켜짐, `--no-prof`로 끔) | ms/tick |
| 실서버 | `server --prof` 또는 `STARFALL_PROF=1` — `[stats]`와 함께 10초마다 | ms/tick |
| 클라이언트 벤치 | `client --bench 15` (항상 켜짐, `STARFALL_PROF=0`으로 끔) — 워밍업 뒤부터 | ms/frame |

서버 틱 트리는 `tick` 아래에 `sessions`, `system`(`ai`, `flight`, `grid`, `weapons`, `missiles`, `damage`, `mining`, `deaths`), `engagements+dailies`, `snapshots`(`records`, `per-viewer`)로 나뉘고, 별도 루트로 `encode`가 있다. 클라이언트는 우리 시스템마다 `모듈::시스템` 구간이 있다.

첫 측정에서 보인 것:

- **서버 1000명**(틱 9.98 ms): 시청자별 스냅샷 구성 37.6%, 전송 인코딩 18.3%, 무장 16.3%, 스냅샷 레코드 10.0%. 네트워크 쪽이 시뮬레이션보다 크다.
- **클라이언트 약 1000척**(프레임 16.49 ms): 우리 시스템은 합쳐 1.33 ms다. 나머지는 엔진(렌더 추출, GPU 제출)이다. 그 안에서는 `ships::update_ship_fx` 0.36 ms, `ships::face_nozzle_glows` 0.23 ms, `ships::aim_turrets` 0.22 ms 순이다. 클라이언트 성능을 더 끌어올리려면 이 시스템들이 아니라 렌더 쪽(메시 수 31,020)을 봐야 한다.

## 8단계: 시뮬레이션 크레이트 분리 (`crates/sim`)

`server` 라이브러리였던 시뮬레이션을 `sim` 크레이트로 옮겼다. 게임 상태·규칙, 저장, 기록·재생, 시나리오, 지표가 모두 여기에 있다. 예제(`scenario`, `balance`, `replay`, `bench`), 테스트, 시나리오 사양(`crates/sim/scenarios/`)도 함께 옮겼다. `server`는 WebSocket과 20 Hz 루프만 있는 바이너리가 됐다.

- **의존성**: `sim`은 tokio·tungstenite·futures 없이 27개 크레이트만 쓴다(`server`는 67개). 그래서 빠른 루프 `cargo test -p shared -p history -p sim -p view`가 네트워크 스택을 컴파일하지 않는다. 클라이언트의 `--replay`도 서버가 아니라 `sim`에만 의존한다.
- **명령이 바뀌었다**: `-p server --example …`·`-p server --test …`는 이제 `-p sim …`이다. 서버 실행(`cargo run -p server --release`)과 봇 테스트 전 빌드(`cargo build -p server`)는 그대로다.
- **동작은 같다**: 파일은 `git mv`로 옮겨 이력이 이어진다. 시나리오 다이제스트 6종, 밸런스 시트, 기존 기록의 재생(헤드리스와 3D 모두 `REPLAY OK`, 같은 최종 다이제스트), 봇 E2E가 이전과 같다.

## 지켜야 할 불변식

- **시뮬레이션은 결정적이어야 한다.**
  - `Game` 안에서는 순회 순서가 결과에 영향을 줄 수 있는 맵에 `BTreeMap`/`BTreeSet`을 쓴다. `HashMap`은 조회 전용일 때만 쓴다.
  - 벽시계(`SystemTime`, `Instant`)는 시뮬레이션 상태를 바꾸는 데 쓰지 않는다. 시각은 `tick(dt, unix)`로만 들어온다. `Instant`는 프로파일링에만 쓴다.
  - OS 난수(`getrandom`)는 계정 토큰에만 쓰고, 토큰은 `issued_tokens`/`token_queue`로 기록·재생된다. 게임플레이 난수는 `shared::rng`의 시드 RNG만 쓴다.
- **모든 상태 변경은 `ClientMsg` → `Game::handle`로 들어온다.** 새 입력을 추가할 때도 같은 경로를 쓰면 자동으로 기록·재생된다.
- 클라이언트 연출에는 시간의 누적보다 시각의 함수를 쓴다(재현 가능한 스크린샷).
- 클라이언트의 계산은 `view`에 순수 함수로 두고 테스트한다. `client`에는 Bevy 엔티티·자산·입력을 다루는 코드만 남긴다.
- 밸런스 수치는 `tuning/*.ron`에 둔다. 시뮬레이션은 `shared::tuning::get()`(또는 `Game::tuning`)으로 읽고, 새 수치를 코드에 상수로 박지 않는다.
