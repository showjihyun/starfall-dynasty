# 0005. 실시간 전송 프로토콜과 메시지 프레이밍

- 상태: **accepted** (server·client 검토 반영, 2026-09-18)
- 날짜: 2026-09-18
- 슬라이스: p0-02-networking-spike
- 근거 기획안 절: TECH §7 (Reliable/Realtime 논리 분리), TECH §8 (WebSocket vs QUIC), TECH §26 (보안), GDD §33 (서버 판정)
- 관련: ADR-0002(계약 형식), ADR-0006(tick·큐), ADR-0008(개발용 인증)
- 검토: `_workspace/p0-02-networking-spike/01_server_spec_review.md`(B-6), `01_client_spec_review.md`(R2·R4·R5·R8). 반영 내역은 `01_architect_decisions.md`

## 맥락

p0-01은 계약이 Rust와 C#에서 같은 모양으로 읽힌다는 것까지 증명했다. 아직 **와이어 위로 한 바이트도 가지 않았다**. 지금 정해야 할 것은 "무엇을 타고 가는가"가 아니라(기획안이 MVP=WebSocket으로 이미 못박았다) **한 프레임에 무엇이 들어가고, 누가 무엇을 채우며, 잘못된 것이 오면 어떻게 되는가**다.

이 결정이 되돌리기 비싼 이유: 서버·클라이언트·봇 세 구현이 동시에 여기에 묶이고, 프레이밍을 바꾸면 세 곳을 같은 커밋에서 고쳐야 한다. 그리고 "서버가 채우는 필드"를 한 번이라도 클라이언트가 채우게 하면, 그 신뢰가 코드 전체에 퍼진 뒤에야 발견된다.

## 결정

### 1. 전송: WebSocket 하나, 논리 채널은 나중

MVP는 WebSocket(TCP)이다. QUIC/WebTransport는 **실시간 전투 규모 테스트에서 지연 분포가 측정된 뒤** 별도 ADR로 결정한다(TECH §8). 이번 슬라이스에 전투가 없으므로 측정 근거를 만들 수 없고, 따라서 지금 논의하지 않는다.

TECH §7의 Reliable/Realtime 분리는 **전송 2종이 아니라 계약 분류**로 시작한다. `contracts/registry/types.json`의 `kind`가 이미 그 축이고, 나중에 `kind`별로 다른 전송에 태울 수 있다. 지금 소켓을 두 개 열면 아무것도 증명하지 못한 채 연결·인증·수명 주기가 두 벌이 된다.

경로는 `GET /ws` 하나다. REST(`IApiClient`)는 이번 슬라이스에 새 엔드포인트를 만들지 않는다.

### 2. 프레이밍: 텍스트 프레임 1개 = 계약 메시지 1개

- **텍스트(UTF-8 JSON) 프레임만** 주고받는다. 바이너리 프레임을 받으면 프로토콜 위반으로 센다. 바이너리 포맷 전환은 ADR-0002 §1이 정한 대로 측정 후 결정이며, 그때 이 규칙을 바꾼다.
- **한 프레임에 계약 메시지 정확히 하나.** 배칭(여러 메시지를 배열로)을 하지 않는다. 배칭은 프레임 경계와 메시지 경계를 분리해 디버깅과 손실 계측을 어렵게 만들고, 이 슬라이스의 핵심 측정(명령 1건 ↔ COMMAND_RESULT 1건)을 흐린다. 프레임 수가 병목으로 **측정되면** 그때 도입한다.
- **인바운드 메시지 상한 16 KiB(앱 한도).** 초과하면 그 메시지를 버리고 프로토콜 위반으로 센다. 이번 슬라이스의 최대 명령(`PING_SERVER`)은 300바이트 미만이다. 상한이 없으면 메모리가 클라이언트의 선의에 달린다.
- **라이브러리 한도는 앱 한도보다 높게 둔다(64 KiB).** server 실측(B-6): axum 0.8.9의 `max_message_size`/`max_frame_size`를 16 KiB로 맞추면 tungstenite가 먼저 `Error::Capacity`로 **연결을 끊어** 앱이 위반을 셀 기회가 사라지고, "위반 예산 8회"는 영원히 관측되지 않는다. 한도를 두 겹으로 두어 **정책은 앱이, 방어는 라이브러리가** 담당한다.
- 조각난(continuation) 프레임은 axum이 재조립해 완성된 메시지로 준다. 상한 판정은 **재조립된 메시지 길이**로 한다.
- 서버는 15초마다 WebSocket Ping을 보낸다. **30초 안에 Pong도 데이터 프레임도 없으면** `IDLE_TIMEOUT`으로 닫는다. TCP만으로는 죽은 연결이 몇 분간 살아 있는 것처럼 보이고, 그러면 "동시 접속 수"가 거짓말이 된다.
- 정상 종료: 양쪽 모두 Close 프레임 교환 후 종료. 서버가 먼저 닫을 때는 아래 close code를 쓴다.

| 상황 | close code | `SESSION_CLOSED.close_reason` |
|------|-----------|------------------------------|
| 클라이언트가 정상 종료 | 1000 (피어가 보냄) | `CLIENT_CLOSED` |
| Pong 없음 | 1001 | `IDLE_TIMEOUT` |
| 프로토콜 위반 예산 초과 (크기 초과·바이너리 프레임·파싱 실패 포함) | 1002 | `PROTOCOL_VIOLATION` |
| 송신 큐 포화(느린 소비자) | 1011 | `SLOW_CONSUMER` |
| 서버 graceful shutdown | 1001 | `SERVER_SHUTDOWN` |
| 소켓 오류 | (없음) | `TRANSPORT_ERROR` |

close code는 진단용이고, **사실로 남는 것은 `close_reason`**이다. 둘을 하나로 합치지 않는다: WebSocket code는 전송 계층의 어휘이고 `close_reason`은 세계의 사실이다.

**크기 초과에 1009를 쓰지 않는다(B-6 반영).** 초안은 크기 초과를 즉시 1009로 끊고 다른 위반은 예산 8회로 셌는데, 두 규칙이 서로를 무효화했다(즉시 끊으면 셀 수 없고, 세면 1009가 죽은 규칙이 된다). **모든 위반을 같은 예산으로 세고 초과 시 1002**로 통일한다. 예산이 있는 편이 "한 번 실수한 클라이언트"와 "프로토콜을 못 지키는 클라이언트"를 구분한다.

### 3. 연결 수명 주기와 메시지 순서

```
클라이언트                         서버
  |-- GET /ws + Authorization ---->|  업그레이드 전에 인증(ADR-0008)
  |<---------- 101 ----------------|  또는 401 / 503 (업그레이드 안 함)
  |                                |  다음 tick: 세션 수락, SESSION_OPENED 발행
  |<------- SESSION_READY ---------|  (세션의 첫 메시지, 반드시 첫 번째)
  |-- PING_SERVER ---------------->|  게이트웨이는 큐에 넣기만 한다
  |<------- COMMAND_RESULT --------|  판정한 tick에서
  |<------- PING_REPLY ------------|  같은 tick, COMMAND_RESULT 뒤
  |-- Close --------------------->|
  |                                |  다음 tick: SESSION_CLOSED 발행
```

불변식으로 고정하는 것:

- **SESSION_READY는 그 연결의 첫 계약 메시지다.** 그 전에는 어떤 메시지도 보내지 않는다. 클라이언트는 SESSION_READY 전에 보낸 명령이 처리된다고 가정하지 않는다(보내도 되지만 순서 보장이 없다 — 보내지 않는 것을 권장한다).
- **같은 `command_id`에 대해 COMMAND_RESULT가 타입별 결과보다 먼저 간다.** 클라이언트가 "결과가 왔으니 접수도 됐겠지"로 상태 기계를 만들면 거부 경로가 영원히 테스트되지 않는다.
- **한 연결의 메시지 순서는 보존된다**(TCP + 단일 송신 태스크). 여러 연결 사이의 순서는 보장하지 않는다 — 전역 순서는 `tick`과 `sequence`가 정하지 전송이 정하지 않는다.
- **세션 재개(resume)는 없다.** 재연결은 새 `session_id`, 새 `correlation_id`, 새 SESSION_OPENED/SESSION_CLOSED 쌍이다. 재개를 지원하려면 서버가 세션 상태와 미전달 메시지를 보관해야 하고, 그것은 영속화 설계(p1)가 결정할 문제다. 지금 절반만 만들면 "가끔 복구되는" 재개가 되어 버그를 숨긴다.

### 4. 계약 표현의 제약 (ADR-0002 §4 보강, 대체 아님)

`tools/codegen`은 **명시된 키워드 allowlist 밖에서 실패**한다(ADR-0002 §4). 이 슬라이스에서 두 가지가 그 제약에 부딪혔고, 다음과 같이 정한다.

1. **`if`/`then`/`oneOf`/`not`을 계약에 쓰지 않는다.** 그래서 `COMMAND_RESULT`의 "ACCEPTED면 `reason_code`는 null" 같은 **필드 간 상관 규칙은 스키마에 넣지 않고** 스펙의 불변식과 서버 타입으로 강제한다. 스키마가 모든 것을 막아야 한다는 기대를 버리는 대신, 무엇을 막지 **않는지**를 명시한다.
2. **문자열 `enum`은 Rust에서는 닫힌 열거형, C#에서는 `string`으로 매핑한다.** 비대칭은 의도적이다. 서버는 모르는 값을 **거부**해야 하고(클라이언트를 믿지 않는다), 클라이언트는 모르는 값을 받아도 **죽지 않아야 한다**(서버가 먼저 배포된다 — ADR-0002 §4의 Strict/Runtime 비대칭과 같은 이유). C# `enum`으로 생성하면 값이 하나 추가되는 순간 구버전 클라이언트가 메시지를 통째로 떨군다.
   - 따라서 `reason_code`·`close_reason`·`transport`·`status`의 값 추가는 **호환 변경**(같은 `schema_version`)이고, 값 제거·의미 변경은 비호환이다.
   - **client 실측 결과 생성기가 이미 이대로 동작한다(U-1 PASS).** 네 필드 모두 `System.String`으로 나왔다. 다만 `enum`이 allowlist의 "구조(출력에 영향)" 분류에 들어 있는데 실제로는 읽히지 않고 무시된다 — 분류를 "제약(C# 출력에는 영향 없음)"으로 옮긴다(동작 무변화, 주석 정정).

3. **envelope 필드의 널 가능성을 타입 스키마가 좁히면, 생성기도 그 좁힘을 따라야 한다.** `SESSION_OPENED`/`SESSION_CLOSED`는 `actor_id`를 비-null로 좁힌다.
   - **client 실측 결과 생성기가 이 좁힘을 무시한다(U-2 FAIL).** envelope의 `anyOf`가 병합 후 살아남고 `Normalize`가 그것을 먼저 읽어 무조건 nullable로 만든다(`ContractsCodegen.cs:460`, `:531`). 결과는 `Guid?` + `Required.AllowNull`이고, `actor-id-null.json` 반례가 C#에서 **통과한다**. 주석은 "never null"인데 타입은 널을 받는 — **계약이 거짓말하는** 상태다.
   - **결정: 생성기를 고친다(client T7, A안).** 스키마가 아니라 생성기가 틀렸다. 이것이 프로젝트의 **첫 좁힘**이라, 지금 고치지 않으면 앞으로 모든 좁힘이 같은 방식으로 조용히 무시된다. 병합에서 override가 구체 `type`을 들고 오면 상속된 `anyOf`를 버린다. 기존 유효 fixture 12건은 `actor_id`가 전부 비-null이라 깨지지 않음을 client가 확인했다.
   - 대칭 검증을 위해 `SESSION_CLOSED/invalid/actor-id-null.json`을 추가했다(반례 15 → 16). 두 타입 중 하나만 고쳐지는 회귀를 막는다.

### 5. 클라이언트 전송 계층

- `IRealtimeTransport`(연결·송신·수신 콜백·종료·상태)를 두고 **PC 구현만** 만든다(`System.Net.WebSockets.ClientWebSocket`). WebGL 구현은 추상화 뒤 자리만 비워 둔다.
- 수신은 백그라운드에서 오므로 스레드 안전 큐에 넣고 메인 스레드에서 디스패치한다. `message_type`을 모르면 **경고 로그 후 계속**한다.
- 역직렬화는 `Runtime` 프로필을 쓴다. `Strict`는 테스트 전용이다(ADR-0002 §4).
  - **`Runtime`이 관용하는 것은 "모르는 멤버" 하나뿐이다.** 필수 필드 누락과 널 불가 필드의 널은 `Runtime`에서도 **예외**다(R3). 이 한 줄이 없으면 "관용 프로필"이 "무검증 프로필"로 구현된다 — client 실측: `MissingMemberHandling.Error` + 무조건 `Handled = true`인 구현이 `missing-session-id.json`을 통과시키고 `session_id`를 빈 Guid로 만든다.
  - client 실측: `MissingMemberHandling.Ignore` 단독은 콜백이 없어 경고를 남길 수 없고, `ITraceWriter`는 메시지 1건에 6줄을 만들어 핫 경로에 못 쓴다. **`Error` 핸들러에서 `Error.Message.StartsWith("Could not find member")`일 때만 `Handled = true`**가 유일하게 쓸 만한 방법이다(`ErrorContext.Member`·`.Path`는 두 경우를 구분하지 못한다). 이 접두사 의존은 **테스트로 고정**해 Newtonsoft 업그레이드가 런타임이 아니라 테스트를 깨게 한다.
- **재연결은 지수 백오프 + full jitter**: `delay = random(0, min(cap, base * 2^min(n, 5)))`, `base = 500ms`, `cap = 10s`, 시도 횟수 무제한. full jitter를 쓰는 이유는 이 슬라이스가 **30개 클라이언트 동시 재연결**을 만들기 때문이다 — 고정 백오프는 재연결 폭풍을 동기화한다.
  - **지수는 cap에 도달하는 최소값(여기서는 5)에서 클램프한다**(R4-2). C#의 `<<`는 시프트 수를 64로 마스킹하므로 클램프가 없으면 `500L << 62 == 0`이 되어 **지연이 0 ms가 된다**(client 실측). cap 10초에서 62회 시도는 약 10분 — 밤새 켜 둔 클라이언트가 실제로 도달한다.
  - **시도 카운터는 `SESSION_READY`를 받았을 때만 0으로 리셋한다**(R4-1). TCP 연결 성공은 리셋 조건이 **아니다**. 소켓이 붙자마자 닫히는 상태(서버 재기동 루프)에서 "연결 성공 시 리셋"이면 30개 클라이언트가 영원히 500 ms 간격으로 재접속한다.
  - **업그레이드 실패의 원인을 클라이언트는 구분하지 않는다.** 401(토큰 무효)·503(미설정/백로그)·네트워크 오류를 전부 같은 백오프로 재시도한다. 이유는 §6 — Unity의 API로는 구분할 수 없고, 예외 메시지 문자열 파싱은 하지 않는다. **원인 판정의 증거는 서버 로그·메트릭이다**(AC-4는 이미 서버 측 증거로 판정한다).
- **재연결 시 미완료 명령을 다시 보내지 않는다.** 로컬에서 `ConnectionLost`로 실패 처리하고 호출자에게 알리며, grep 가능한 한 줄(`starfall.net: dropping N in-flight command(s) on disconnect (no resend, I-23)`)을 남긴다 — 이 문구가 AC-13의 증거다. 재전송은 서버의 지속 멱등성(`command_id` 영속 저장)이 있어야 안전한데 그것은 p1이다. ADR-0006 §6의 세션 내 중복 제거는 **연결이 살아 있는 동안만** 유효하다.
- **도메인 리로드·PlayMode 종료·앱 종료 훅에서 정상 Close를 보낸다.** 보내지 않으면 서버가 `TRANSPORT_ERROR`로 기록하고 AC-12(c)의 `CLIENT_CLOSED` 기대가 깨진다. Editor에서 이 훅은 선택이 아니라 필수다.

### 6. 클라이언트가 전송 계층에 대해 알 수 없는 것 (지금은 기록만)

**지금 이미 참인 제약 (client 실측, U-5c):** Unity 6000.6.1f1 Editor는 Mono로 돌고 프로젝트는 `apiCompatibilityLevel: 6`(.NET Standard 2.1)이다. 그 표면과 Mono `System.dll` 양쪽에 **`ClientWebSocketOptions.CollectHttpResponseDetails`가 없다**(.NET 7+ API). 따라서 **클라이언트는 업그레이드 실패의 HTTP 상태 코드를 읽을 수 없고**, 401·503·네트워크 오류가 전부 `WebSocketException` 하나로 보인다. `SetRequestHeader`·`KeepAliveInterval`·`AddSubProtocol`은 양쪽에 있다.

이 제약을 우회하려고 REST로 `/readyz`를 찔러 보는 경로는 **채택하지 않는다** — 이번 슬라이스에 없는 REST 경로를 새로 만들게 되고, 401은 여전히 구분되지 않는다. 비용 대비 소득이 없다.

**WebGL이 나중에 부딪힐 것:** 브라우저 WebSocket API는 임의 헤더를 설정할 수 없어 `Authorization` 헤더로 인증할 수 없다. 알려진 경로는 (a) REST로 단기 티켓을 받아 `Sec-WebSocket-Protocol`에 싣기, (b) 쿼리 문자열(접근 로그에 남아 권장하지 않음)이다. **이번 슬라이스는 (a)(b) 어느 것도 구현하지 않는다.**

두 제약이 같은 계열인 것이 요점이다: **클라이언트는 HTTP 업그레이드의 세부에 닿을 수 없다.** 그래서 서버 코드의 자격 증명 추출은 교체 가능한 한 지점에 두고, 인증·거부의 증거는 **언제나 서버 쪽에서** 만든다.

## 검토한 대안과 버린 이유

- **QUIC/WebTransport로 시작**: 기획안이 명시적으로 반대한다(TECH §8). 방화벽·브라우저·라이브러리 성숙도 비용을 측정 근거 없이 지불하게 된다.
- **바이너리(Protobuf/MessagePack) 프레임**: JSON 텍스트는 30 연결 규모에서 병목이 아니고, 텍스트 프레임은 `wscat`·브라우저 devtools로 그냥 읽힌다. 스파이크의 목적은 디버깅 가능성이다.
- **프레임 배칭**: 손실 계측(명령 1 ↔ 결과 1)을 흐린다. 측정된 병목이 나오면 도입.
- **Reliable/Realtime 소켓 2개**: 이번 슬라이스에 realtime 트래픽이 없다. 연결·인증·수명 주기 코드가 두 벌이 되고 둘 다 검증되지 않는다.
- **세션 재개(resume token)**: 절반짜리 재개는 "가끔 되는" 동작이 되어 재현 불가능한 버그를 만든다. 재개가 필요한 근거(모바일 네트워크 전환 등)가 생기면 영속 세션 설계와 함께 결정한다.
- **메시지 배열 대신 여러 프레임을 한 tick에 몰아 보내기**: 그렇게 한다. 이것이 기본 동작이며 별도 결정이 아니다.

## 결과

- 좋은 점: 서버·클라이언트·봇이 같은 프레이밍 규칙 한 장을 보고 구현한다. 프레임 상한·idle 타임아웃·close 코드 표가 있어 "연결 수"라는 숫자가 실제 살아 있는 연결을 뜻한다. 계약 표현의 한계(§4)가 문서에 있어 "스키마가 막아 줄 것"이라는 잘못된 기대가 생기지 않는다.
- 감수할 점: JSON 텍스트라 대역폭이 크다(30 연결에서는 무의미하지만 전투에서는 측정 대상). `if`/`oneOf`를 못 써서 일부 규칙이 스키마 밖(불변식 + 서버 타입)에 있다 — 그래서 §4를 읽지 않은 구현자가 스키마만 믿으면 틀린다.
- 다시 검토할 조건: (a) 전투 규모 테스트에서 지연 p99가 목표를 넘고 원인이 TCP head-of-line blocking으로 **측정**될 때 → QUIC ADR, (b) 프레임 수 또는 JSON 직렬화가 프로파일에서 상위로 올라올 때 → 배칭·바이너리 ADR, (c) WebGL 빌드를 실제로 만드는 슬라이스 → §6의 자격 증명 경로 결정.
