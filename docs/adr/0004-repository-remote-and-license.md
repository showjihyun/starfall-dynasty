# 0004. 원격 저장소·공개 범위·라이선스·LFS

- 상태: accepted (사용자 결정, 2026-09-18)
- 날짜: 2026-09-18
- 슬라이스: p0-01-bootstrap
- 근거: `_workspace/p0-01-bootstrap/00_request.md` "사용자 결정" 절

## 맥락

부트스트랩 스펙의 열린 질문 Q2~Q4(원격 저장소, Git LFS, 커밋 시점)에 사용자가 답했다. 이 결정들은 **첫 커밋 이후에는 되돌리기 비싸다**: 공개 범위는 이미 퍼진 코드를 되돌릴 수 없고, 라이선스는 이전 커밋에 적용된 조건이 남으며, LFS는 나중에 도입하면 히스토리 재작성이 필요하다. 그래서 커밋이 0건인 지금 한 번에 정한다.

## 결정

### 1. 원격 저장소와 브랜치

- `origin` = `https://github.com/showjihyun/starfall-dynasty.git`
- 기본 브랜치는 `main` 하나(원격 `master` → `main` 이름 변경 완료). 로컬도 `main`.
- **이 슬라이스에서는 커밋·푸시하지 않는다.** 원격에는 초기 커밋(LICENSE) 1건만 있고 그 위에 로컬 `main`이 올라가 있다. 커밋은 사용자가 요청할 때만 한다.
- 브랜치 전략(기능 브랜치·PR 필요 여부)은 CI 슬라이스에서 정한다. 지금은 `main` 직접 작업이다.

### 2. 공개 범위: Public 유지

저장소는 공개다. 따라서 **다음이 전부 공개된다는 전제로 작업한다**: 기획안 3종, 서버 판정 로직, 밸런스 수치와 `data/` 테이블, 계약 스키마, 역사 판정 규칙, 스펙·ADR·QA 리포트.

이 전제에서 지금부터 지키는 것:

- **비밀은 저장소에 절대 들어가지 않는다.** `.env`는 추적하지 않고(`.gitignore`), `.env.example`에는 dev 전용 값만 둔다. 어떤 토큰·키·실제 자격 증명도 커밋하지 않는다. 한 번 푸시된 비밀은 삭제 커밋으로 사라지지 않는다.
- **서버 권위 구조가 공개를 견딘다.** 클라이언트를 믿지 않는 설계(원칙 1)라 로직이 공개되어도 치팅 경로가 새로 열리지는 않는다. 오히려 "클라이언트만 고치면 되는" 설계였다면 공개가 치명적이었을 것이다 — 공개는 원칙 1을 지키는 추가 압력이다.
- **공개가 불리해지는 것들**(반치팅 임계값, 봇 탐지 규칙, 운영 계정 정보, 실서비스 시드·난수 시드)은 **지금 만들지 않는다**. 필요해지면 "민감 데이터·규칙 분리"를 별도 ADR로 결정한다(비공개 서브모듈, 런타임 설정 주입 등). 이번 슬라이스에는 해당 항목이 하나도 없다.
- 이슈·PR·QA 리포트도 공개된다. `_workspace/`의 평가 리포트에 개인 정보나 자격 증명을 쓰지 않는다.

### 3. 라이선스: 독점(All Rights Reserved)

루트 `LICENSE`를 AGPL-3.0에서 독점 고지로 교체했다. 핵심: 저장소는 **읽기·참조용으로만** 공개되며, 사용·복제·수정·배포·2차 저작물 제작은 사전 서면 허가가 필요하다. 기여자는 기여분에 대해 프로젝트가 쓸 수 있는 권리를 부여한다. 제3자 구성요소(엔진·라이브러리·패키지)는 각자의 라이선스를 그대로 따른다.

AGPL-3.0을 버린 이유: AGPL은 네트워크 서비스로 제공하기만 해도 소스 공개 의무가 따라붙는다. 상업 운영을 전제로 한 온라인 게임에서 이는 **원하지 않는 의무**다. 공개 저장소 + 독점 라이선스는 "읽을 수는 있으나 쓰려면 허가받는" 형태다.

> **법률 자문이 아니다.** 이 조합(공개 + 독점)은 기여 처리, 제3자 라이선스 호환성(특히 Unity·Rust 생태계 패키지와 에셋 스토어 구매물), 상표·에셋 권리에서 검토가 필요하다. **상업 출시 전 변호사 검토를 받는다.** 그 전에 외부 기여를 받기 시작하면 기여자 약정(CLA/DCO)을 별도로 정한다.

### 4. Git LFS: 지금 설정

`.gitattributes`에 LFS 패턴을 등록했다(모델·텍스처·오디오·비디오·폰트·네이티브 바이너리). `git-lfs 3.6.0` 설치 확인됨.

- **지금 하는 이유**: 커밋이 0건인 지금이 가장 싸다. 바이너리가 일반 blob으로 한 번 들어가면 LFS 전환에 히스토리 재작성이 필요하고, 그때는 이미 여러 클론이 존재한다.
- 바이너리를 커밋하기 전에 `git lfs install`이 되어 있어야 한다. 안 되어 있으면 패턴이 있어도 실제 바이트가 그대로 들어간다.
- 텍스트로 남기는 것: 씬·프리팹·머티리얼 등 Unity YAML(Force Text 전제)과 `.meta`. **`.meta`는 절대 무시하지 않는다**(GUID 참조).
- GitHub 무료 LFS 저장/대역 쿼터가 있다. 아트가 늘어나면 쿼터와 비용을 다시 본다.
- Unity YAML 병합기(`unityyamlmerge`)는 로컬 git 설정이 필요하다. 설정하지 않으면 일반 3-way 병합으로 처리된다 — 씬·프리팹을 여러 명이 동시에 고치기 시작하는 슬라이스에서 설정 절차를 문서화한다.

## 검토한 대안과 버린 이유

- **Private 저장소**: 비밀 유출 위험은 줄지만 사용자가 공개를 선택했다. 공개의 실익(공유·참조·투명한 개발 기록)을 택했고, 대신 "비밀은 저장소 밖" 규율을 강화한다.
- **AGPL-3.0 유지**: 네트워크 서비스 제공 시 소스 공개 의무가 상업 운영과 충돌한다.
- **MIT/Apache-2.0**: 게임 콘텐츠·밸런스·서사까지 자유 사용을 허용하게 된다. 의도와 다르다.
- **LFS를 나중에**: 히스토리 재작성 비용을 미래로 미루는 선택. 지금 비용이 거의 0이므로 미룰 이유가 없다.
- **`master` 브랜치 유지**: 도구·문서 기본값이 `main`으로 수렴했고, 원격·로컬을 섞어 쓰면 푸시 사고가 난다.

## 결과

- 좋은 점: 첫 커밋 전에 되돌리기 비싼 결정이 전부 정해졌다. 공개 전제가 "비밀은 저장소 밖" 규율과 서버 권위 설계를 강화한다.
- 감수할 점: 공개 저장소이므로 밸런스·로직이 노출되고, 반치팅 성격의 규칙은 나중에 분리 설계가 필요하다. 독점 라이선스는 외부 기여를 받기 어렵게 만든다(의도된 선택이지만, 기여 제안이 오면 약정 정비가 필요하다). 법률 검토는 미완이다.
- 다시 검토할 조건: (a) 상업 출시 준비 시작 시 라이선스·기여 약정 법률 검토, (b) 반치팅·운영 규칙처럼 공개가 불리한 데이터가 생길 때 분리 ADR, (c) LFS 쿼터 초과 또는 아트 용량 급증, (d) 기여자가 생겨 브랜치·리뷰 규칙이 필요해질 때(CI 슬라이스와 함께).
