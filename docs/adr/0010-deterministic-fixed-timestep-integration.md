# 0010. 결정적 고정 timestep 적분 — 비행 보조 6DoF의 공통 법칙

- 날짜: 2026-09-19 (검토 반영 2026-09-20, §3.1 추가 2026-09-20)

- 근거 기획안 절: TECH §12(Simulation Tick), TECH §13(Deterministic Simulation), HSE §32(결정성), GDD §33(서버 판정)
- 근거 디자인: `docs/design/p1-01-ship-movement-design.md` §3(조작 모델), §4(수치), §6.3(tick 순서), §6.5(삼각함수 금지)

- 관련: ADR-0006(tick 주기·게임 시간), ADR-0009(좌표계·단위), ADR-0011(입력 규약), ADR-0012(예측·보정), CLAUDE.md 원칙 1·9

## 맥락

이 슬라이스는 **같은 계산을 두 곳에서 한다.** 서버는 권위 상태를 만들고, 클라이언트는 자기 함선을 예측한다(ADR-0012). 두 계산이 조금이라도 다르면 예측 오차가 0으로 수렴하지 않고, 플레이어는 "조작이 미끄러진다"고 느낀다. 그 차이는 대개 알고리즘이 아니라 **연산 순서와 함수 선택**에서 나온다.

그래서 적분은 구현 세부가 아니라 **계약이다.** 여기 적힌 순서가 서버와 클라이언트가 함께 지켜야 할 법이고, 어느 한쪽이 "수학적으로 같은" 다른 형태로 바꾸면 그 순간 예측이 깨진다.

**조작 모델은 사용자가 골랐다 (2026-09-19): 비행 보조 6DoF.** designer가 버린 대안과 그 이유는 디자인 문서 §3.2에 있고 여기서 다시 논쟁하지 않는다. 이 ADR이 하는 일은 **그 모델을 두 언어가 같은 비트로 계산할 수 있는 형태로 못박는 것**이다.

## 결정

### 1. 1 tick = 1 입력 = `dt = 1 / tick_hz`

- tick 주기는 ADR-0006이 정한 20 Hz다. `dt`는 리터럴 `0.05`가 아니라 **`1.0 / tick_hz`로 계산한다** — 양쪽이 같은 방식으로 얻는 같은 비트여야 한다.
- **가변 timestep을 쓰지 않는다.** 클라이언트가 `dt`를 보내는 형태는 클라이언트가 물리 시간을 통제하게 되어 전형적인 속도 핵 통로가 된다.
- 렌더 프레임 수는 이 계산에 들어오지 않는다. **클라이언트는 프레임률과 무관하게 입력 1건 = 1 tick을 적분하고**, 화면에는 마지막 두 예측 상태 사이를 보간해 그린다(디자인 §5.6).

### 1.1 함선의 각속도는 **둘**이다 — 이것이 계약 모양을 정한다

| 상태 | 형태 | 슬루 한계 | 적분 단계 |
|------|------|---|---|
| `ω_aim` | 3성분 벡터, **월드 프레임** | `turn_accel_deg_s2` | 4단계 |
| `ω_roll` | 스칼라, 함선 전방축 둘레 | `roll_accel_deg_s2` | 5단계 |

**둘의 합에서 둘을 복원할 수 없다.** `ω_aim`은 자세 오차에서 나오므로 전방축 성분을 갖지 않는다는 보장이 없고, 4·5단계가 **두 번의 1차 적분**이라 같은 합이라도 분해가 다르면 결과가 다르다(2차항 `0.25·dt²·W₂W₁`, 최대 각속도에서 tick당 약 0.06° — ADR-0012의 자세 임계 0.02°의 3배). 두 축의 슬루 한계도 다르므로 이후 tick에서 발산이 누적된다.

**그래서 `WORLD_SNAPSHOT`은 둘을 따로 싣는다**(`angular_velocity_{x,y,z}_mdeg_s` + `angular_velocity_roll_mdeg_s`). 이것은 편의가 아니라 **재조정이 원리적으로 가능하기 위한 최소 조건**이다(server B-1 실측 근거).

### 2. 적분 순서 — 이 순서가 계약이다

한 tick, 한 함선. 함선은 **`ship_id` 오름차순**으로 처리한다.
표기: `⊗` Hamilton 곱, `|v|` = `sqrt(x²+y²+z²)`, `vec(q)` = 쿼터니언의 (x,y,z), `conj(q)` = 켤레, `rot(q,v)` = `vec(q ⊗ (v,0) ⊗ conj(q))`, `q_pure(w)` = `(w.x, w.y, w.z, 0)`.
쿼터니언 성분 순서는 `(x,y,z,w)`. 상태는 `p`(m), `v`(m/s), `q`(단위 쿼터니언), `ω_aim`(deg/s, 월드), `ω_roll`(deg/s, 스칼라).

입력(전부 `f64`, ADR-0009 §2의 역양자화를 거친 값): `t = (thrust_x, thrust_y, thrust_z)/1000`, `roll = roll_milli/1000`, `q_aim_raw = (aim_*)/1e6`, `brake`, `assist`.
함선 클래스 값은 `data/ships/*.json`의 SI 값을 그대로 쓴다(변환 없음).

```
 0. 입력 확정  : 이번 tick 입력 or 이월 (ADR-0011 §4)

 1. 목표 자세 정규화
       n = |q_aim_raw|
       q_aim = (n < AIM_MIN_NORM) ? q : q_aim_raw / n      # AIM_MIN_NORM = 0.1
                                                           # 퇴화 → 현재 자세, aim_degenerate_total++

 2. 자세 오차 → 목표 각속도 (삼각함수 없음)
       q_err = q_aim ⊗ conj(q)
       if q_err.w < 0 : q_err = -q_err                     # 최단 경로
       e = vec(q_err) ;  s = |e|                           # s = sin(θ/2)
       if s < turn_deadzone_sin_half : ω_t = (0,0,0)
       else : ω_t = (e / s) * min(turn_rate_max_deg_s, turn_gain_deg_s_per_sin_half * s)
       # ── 롤 축 권한 분리 (server B-3). 자세 제어기는 전방축에 손대지 않는다.
       f  = rot(q, (0,0,1))
       ω_t = ω_t - f * dot(ω_t, f)

 3. 각속도 슬루 (가속 제한)
       Δ = ω_t - ω_aim ;  m = |Δ|
       if m > turn_accel_deg_s2 * dt : Δ = Δ * (turn_accel_deg_s2 * dt / m)
       ω_aim = ω_aim + Δ

 4. 자세 적분 (1차 + 재정규화)
       w1 = ω_aim * (PI / 180)                             # rad/s, 월드 프레임
       q  = q + (q_pure(w1) ⊗ q) * (0.5 * dt)
       q  = q / |q|

 5. 롤 / 오토레벨 (둘 중 하나. 결과는 전방축 둘레의 회전 하나)
       fwd = rot(q, (0,0,1))
       if roll != 0 or assist == false :
           ω_roll_t = roll * roll_rate_max_deg_s
       else :
           u = WORLD_UP - fwd * dot(WORLD_UP, fwd)         # WORLD_UP = (0,1,0)
           nu = |u|
           if nu < auto_level_deadzone_sin : ω_roll_t = 0  # 기수가 성계 up 과 나란함 → 롤 기준 없음
           else :
               up_s    = rot(q, (0,1,0))
               sin_err = dot( cross(up_s, u / nu), fwd )   # [-1,1], 부호 포함  ← §2.1 주의
               ω_roll_t = (|sin_err| < auto_level_deadzone_sin) ? 0
                                                          : auto_level_rate_deg_s * sin_err
       d = ω_roll_t - ω_roll
       lim = roll_accel_deg_s2 * dt
       if |d| > lim : d = (d > 0.0 ? 1.0 : -1.0) * lim     # signum 을 쓰지 않는다 (§3)
       ω_roll = ω_roll + d
       w2 = fwd * (ω_roll * (PI / 180))
       q  = q + (q_pure(w2) ⊗ q) * (0.5 * dt)
       q  = q / |q|

 6. 추력 → 월드 가속
       a_local = ( t.x * lateral_thrust_mps2,
                   t.y * lateral_thrust_mps2,
                   t.z >= 0 ? t.z * main_thrust_mps2 : t.z * reverse_thrust_mps2 )
       if brake : a_local = (0,0,0)                        # 브레이크 중 추력 무시
       la = |a_local|
       if la > main_thrust_mps2 : a_local = a_local * (main_thrust_mps2 / la)   # 대각선 클램프
       a_thrust = rot(q, a_local)                          # 5단계 후의 자세로 변환

 7. 경계 당김
       r = |p|
       a_bound = (r > soft_boundary_radius) ? -(p / r) * boundary_pull_mps2 : (0,0,0)

 8. 속도 적분
       v = v + (a_thrust + a_bound) * dt

 9. 감쇠 — 한 tick에 정확히 하나만, 0을 지나치지 않게
       EPS = 1e-9
       if brake                          : u = v                      ; lim = brake_decel_mps2 * dt
       elif assist and |a_thrust| > EPS  : d = a_thrust / |a_thrust|
                                           u = v - d * dot(v, d)      ; lim = assist_lateral_decel_mps2 * dt
       elif assist                       : u = v                      ; lim = assist_linear_decel_mps2 * dt
       else                              : u = (0,0,0)                ; lim = 0
       if |u| > EPS : v = v - (u / |u|) * min(lim, |u|)

10. 속도 상한
       sv = |v| ; if sv > max_speed_mps : v = v * (max_speed_mps / sv)

11. 위치 적분
       p = p + v * dt

12. 하드 경계
       r = |p|
       if r > hard_boundary_radius :
           n = p / r ; p = n * hard_boundary_radius
           vr = dot(v, n) ; if vr > 0 : v = v - n * vr
```

고정 사항:

- **`PI`는 각 언어의 `f64` π 상수**(`std::f64::consts::PI`, `System.Math.PI`)를 `180.0`으로 나눈 값이다. 둘 다 π의 올바르게 반올림된 double이므로 같은 비트다(client 실측: `400921fb54442d18` 동일). 리터럴을 손으로 적지 않고 `to_radians`도 쓰지 않는다(§3).
- **2단계 끝의 롤 성분 제거는 동작 변경이 아니라 권한 분리다**(server B-3). 자세 제어기(2~4)와 롤·오토레벨(5)이 같은 축에 권한을 가지면, 오토레벨이 롤을 바꿀 때마다 `q_err`에 롤 오차가 생겨 자세 제어기가 그것을 **되돌린다** — 두 제어기가 서로를 지우고 AC-4(g)가 그 형태로 실패한다. 이 한 줄이 없으면 **"클라이언트가 `q_aim`에 현재 롤을 합성해 넣어야 한다"는 어디에도 적히지 않은 의무**가 생긴다. 적히지 않은 의무는 지켜지지 않는다.
  - 비용: 내적 1 + 곱 3 + 뺄셈 3. 초월함수 없음.
  - **규약을 지키는 클라이언트에게는 no-op이다**(롤 오차가 이미 0이므로). 즉 규약을 어긴 클라이언트로부터 서버를 지키는 변경이다. 세 입력 채널(조준=피치·요 / 수동 롤 / 오토레벨)이 세 축에 1:1로 대응하게 된다.
  - **이것이 B-1(각속도 2필드)을 대체하지 않는다.** `fwd`가 매 tick 최대 3.75° 회전하므로 `ω_aim ⊥ fwd`는 계산 시점에만 성립하고 잔차가 남으며, 그 잔차는 다시 0.02° 임계와 같은 자릿수다.
- **9단계의 감쇠는 정확히 하나만 적용한다.** 브레이크 중에 보조 감쇠가 겹치면 `brake_decel_mps2`가 거짓 수치가 된다(디자인 §6.3).
- **9단계는 8단계 뒤의 `v`로 계산한다.** 순서를 바꾸면 가속과 감쇠가 같은 tick에서 다른 값을 본다.
- **9단계 감쇠는 `a_bound`를 기준으로 삼지 않는다.** 경계 당김은 조종사 의도가 아니다. 보조 감쇠가 당김 방향을 "추력 방향"으로 오인하면 경계에서 옆으로 미끄러지지 않고 붙어 버린다.
- **0 나눗셈 가드는 `> 0`이 아니라 `> EPS`(1e-9)다**(server 지적). 비정규수에서 `> 0`은 문자 그대로는 발산을 허용한다. 양쪽이 같은 상수를 쓰므로 결정성 영향은 없다.
- **6단계의 대각선 클램프를 빠뜨리면 반드시 버그가 난다**: 세 축 최대는 `sqrt(18² + 18² + 35²) = 43.28 m/s²`로 전방 단독보다 24 % 빠르다(server 실측: 43.28 → 35.0으로 클램프). 발견되면 모든 플레이어가 대각선으로 날아다닌다. **클램프 상수가 항상 최대값이려면 `main ≥ lateral`·`main ≥ reverse`여야 하고, 기동 시 검산한다**(I-38).
  - 부수 결과(설계이지 버그가 아니다): 순수 측면 대각선 `(1,1,0)`은 25.46 m/s²로 클램프에 걸리지 않는다 — **측면 실효 최대는 `lateral × √2`**다.
- **속도 상한은 `|v|` 하나만** 건다. 방향별 상한을 두지 않는다.
- **쿼터니언 적분은 1차 + 재정규화다**(4·5단계). 최대 각속도에서 tick당 각도 오차는 약 0.03°이고, **자세 제어가 폐루프라 자동으로 보정된다** — 도착이 약 1 % 늦어질 뿐이다(U-21이 AC-4(g)로 확인).
- **순서는 바꾸지 않는다.** server가 12단계를 전수 검토해 **바꿀 곳이 없음을 확인했다**(리뷰 §"적분 12단계 순서 검토"). 특히 4·5의 `q_pure(w) ⊗ q`(월드 프레임이므로 좌곱이 맞다), 6이 5단계 후의 자세를 쓰는 것, 10 → 11 → 12의 순서(12는 `|v|`를 줄이기만 하므로 10의 클램프를 깨지 않는다)가 각각 이유가 있다.

#### 2.1 5단계의 부호가 손 방향이 새는 **유일한** 지점이다

`sin_err = dot(cross(up_s, u/nu), fwd)`는 외적의 부호에 의존한다. 외적을 표준 성분 공식으로 계산하면 왼손 좌표계에서 시각적 회전 방향이 오른손 직관과 반대가 된다. **서버와 클라이언트가 같은 공식을 쓰면 두 쪽이 일관되게 틀린다** — 예측 오차 0, fixture 왕복 통과, 결정성 통과, 모든 자동 검증 통과.

**오토레벨이 반대로 도는 버그는 AC-14(d)(사람의 눈)만 잡을 수 있다. 틀렸으면 고치는 것은 `sin_err`의 부호 하나다.**

**architect가 채운 빈칸 하나 (designer 통보 D-8).** 디자인 문서는 오토레벨의 속도(`40 °/s`)와 불감대(`0.002`)를 주었지만 **오차에서 각속도로 가는 법칙**은 주지 않았다. 위 5단계는 `auto_level_rate_deg_s × sin_err`, 즉 **오차의 사인에 비례하고 그 속도로 상한이 걸리는** 형태다. 상수를 새로 만들지 않고, 오차가 0으로 갈 때 각속도도 0으로 가므로 불감대 주변에서 진동하지 않는다. 고정 속도(bang-bang)로 하면 불감대 경계에서 떨린다.

### 3. 결정성의 범위 — 무엇을 보장하고 무엇을 보장하지 않는가

**보장한다**: 같은 서버 바이너리가 같은 초기 상태에 같은 입력열을 적용하면 **같은 `f64` 비트**, 따라서 같은 양자화 정수, 따라서 같은 스냅샷 바이트(I-37).

근거:

- Rust는 기본적으로 부동소수 재결합이나 FMA 축약을 하지 않는다. `+ - * /`와 `sqrt`는 IEEE-754가 정확히 규정한다.
- **아래 함수를 시뮬레이션 안에서 쓰지 않는다.** §2의 12단계는 이 중 하나도 부르지 않는다.

| 금지 | 왜 |
|------|-----|
| `sin` `cos` `tan` `asin` `acos` `atan` `atan2` | 표준이 정확도를 규정하지 않는다. 그래서 자세 오차를 각도로 바꾸지 않고 `sin(θ/2)`인 `s`를 그대로 쓴다 — 게인 단위가 `sin(θ/2)`당인 이유다 |
| `exp` `exp2` `ln` `log` `log2` `log10` `powf` `powi` `cbrt` `sinh` `cosh` `tanh` | 같은 이유. 감쇠를 `exp(-d·dt)`가 아니라 선형 캡으로 쓴 것은 물리가 더 나아서가 아니라 `exp`가 경계를 넘기 때문이다 |
| **`mul_add` (FMA)** | **가장 위험하다.** 중간 반올림이 없어 `a*b+c`와 **다른 비트**를 낸다. Rust는 쓰면 쓰는 대로, C#은 `Math.FusedMultiplyAdd`가 별도 함수라 **한쪽만 쓰면 즉시 어긋난다.** 손이 미끄러지기 쉬운 자리(내적·적분)가 정확히 12단계가 도는 곳이다 |
| `hypot` | IEEE로 정확히 규정되지 않았다. §2는 `sqrt(x²+y²+z²)`를 명시했지만, **금지 목록에 이름이 있어야 grep이 잡는다** |
| `to_radians` / `to_degrees` | Rust는 사실상 `* (PI/180.0)`이지만, **양쪽이 같은 표현을 쓰는지가 눈에 보여야** 대조가 된다. `* (PI/180.0)`을 쓴다 |
| `signum` / `Math.Sign` | **`0`에서 갈라진다**: Rust `f64::signum(0.0) = 1.0`, C# `Math.Sign(0.0) = 0`. §2 5단계는 `|d| > lim > 0`일 때만 부호가 필요하지만 **그 안전이 조건문에 숨어 있다.** `d > 0.0 ? 1.0 : -1.0`으로 풀어 쓴다 |

**금지는 아니지만 기록**: `f64::max/min/clamp`와 `Math.Max/Min`은 **NaN 처리가 다르다**(Rust는 NaN이 아닌 쪽, C#은 NaN). NaN이 없어야 정상이지만, 그 가정이 깨졌을 때 **두 구현이 다르게 망가진다.**

**검사 방법 (server 실측).** 순진한 grep은 p0-02 코드에서 **오탐 13건**을 낸다(최대 원인: `.expect(`가 `exp`에 걸린다). 메서드 호출 형태로 좁히면 0건이다.

```bash
grep -rInE "\.(sin|cos|tan|asin|acos|atan|atan2|exp|exp2|ln|log|log2|log10|powf|powi|hypot|cbrt|sinh|cosh|tanh|mul_add|to_radians|to_degrees|signum)\s*\(|f64::(sin|cos|tan|asin|acos|atan|atan2|exp|ln|log|powf|powi|hypot|mul_add|signum)" \
     crates/sim/src
```

**오탐 13 → 0을 함께 보이는 것이 "검사가 실제로 무언가를 검사한다"의 증거다**(AC-1).

- 순회 순서가 결과에 영향을 주는 곳(함선 목록)은 `BTreeMap`으로 `ship_id` 순을 강제한다.
- **난수가 없다.** 스폰 위치조차 `actor_id`의 시드 해시로 시작 인덱스를 고르고 간격 탐색으로 걸어간다(§4).

**보장하지 않는다**: 서로 다른 CPU 아키텍처·컴파일러 버전·최적화 수준 사이의 비트 동일성. 그것이 필요해지면 고정소수점으로 가야 하고, 그때 이 ADR을 대체한다.

**보장의 입력은 `f64` 상태다 — 와이어 정수가 아니다** *(2026-09-22 추가. QA R3 §6.5가 드러낸 스프린트 계약 SC-11(3)의 결함을 계기로 적는다.)* 위 보장의 전제는 "같은 **`f64`** 초기 상태 + 같은 입력열"이다. 스냅샷의 정수는 그 상태를 **손실 있게 투영한 값**이다. 양자화는 메시지를 만들 때 한 번만 일어나고 상태로 되돌리지 않으므로(ADR-0009 §5), 같은 정수로 반올림되는 `f64` 상태는 무수히 많다. 그래서 **스냅샷 정수에서 출발한 계산은 이 보장의 범위 밖이다.** 적분이 N tick 동안 그 차이를 키우기 때문에 정직한 서버와도 정수가 다를 수 있다(실측: 122 tick 뒤 위치 봉투 폭 최대 8 mm).

- **비트 일치는 `f64` 상태를 직접 보는 곳에서만 요구한다.** in-process 테스트(스펙 AC-3(d1))와, 두 언어가 같은 `f64` 입력 파일을 여는 재생 대조(§3.1, AC-8·AC-12)가 그 자리다.
- **와이어 수준 대조의 기준은 양자화 봉투다.** 시작 정수를 ±0.5 양자 범위에서 흔들었을 때 나올 수 있는 결과의 범위이고(스펙 AC-3(d2)), 반드시 음성 대조와 함께 쓴다. 이것은 허용 오차를 고르는 것이 아니라, 양자화가 버린 정보를 되돌려 놓는 것이다.
- **이것은 "같은 비트" 가정의 반증이 아니라 그 범위를 적은 것이다.** QA 측정에서 서버의 재개 직후 상태는 봉투 안에 있었고(독립 계산과의 편차 2 mm, 봉투 폭 8 mm), ADR-0012의 재검토 조건 (a)("정상 상태 오차가 양자화 한계보다 크게 측정됨")에 해당하지 않는다. 클라이언트 예측은 처음부터 이 구분 위에 서 있다. 확정 기준점이 스냅샷 정수이고(I-35), 수용 기준이 비트 일치가 아니라 "≤ 5 mm"다(ADR-0012).

**클라이언트가 같은 비트를 내는가 — 실측으로 확인됐다 (client, 2026-09-20).**

§2가 쓰는 산술만 뽑아 같은 순서로 두 언어에 옮기고 **300 tick** 돌린 뒤 IEEE-754 비트로 비교했다. 클라이언트 쪽은 **Unity 동봉 `mcs`로 빌드해 Unity 동봉 `mono.exe`에서** 실행했다(클라이언트가 실제로 쓰는 런타임).

> **비교한 15개 값 전부 비트 동일. 양자화 정수도 동일.**

**한계 두 가지를 그대로 기록한다.** (a) 측정한 것은 **Editor의 Mono/x64**이고 **IL2CPP는 미측정**이다 — 플레이어 빌드가 생기는 슬라이스에서 다시 잰다. (b) 12단계 전체가 아니라 **그 단계들이 쓰는 산술 종류**를 덮었다. **이 결과는 AC-12를 느슨하게 만들지 않는다** — AC-12가 초과하면 원인은 "런타임이 다르다"가 아니라 "두 구현이 다르다"이고, 그때도 임계값을 늘리지 않고 보고한다. 이 측정이 한 일은 **선행 위험을 제거한 것**이다.

### 3.1 재생 산출물은 **추적한다** — 두 언어가 같은 절차를 도는 것과 같은 파일을 여는 것은 다르다

*(2026-09-20 추가. QA 라운드 1 §6.5가 드러낸 사안을 architect가 판단해 기록한다. 계약은 바뀌지 않는다.)*

**사안.** `server/crates/sim/tests/data/replay/`의 3파일 — `initial.json`(2,041 B), `inputs.jsonl`(2,708 B), `snapshots.jsonl`(525,272 B / 300줄, `snapshot_interval_ticks = 2`로 600 tick에서 나온다) — 은 지금 **git이 추적하지 않고** `cargo test -p starfall-sim --test determinism`이 매 실행마다 새로 쓴다. client의 SC-51·52는 게이트 G-k에 따라 이 경로를 **복사하지 않고 상대 경로로 참조**한다. 그래서 **언어를 가로지르는 암묵적 빌드 의존**이 생겼다: 새 클론·CI·Unity 단독 환경에서는 Rust 테스트를 먼저 돌리기 전까지 디렉토리가 없다. QA 라운드 1이 이것을 실제로 잡았다(EditMode가 `Inconclusive` 1건으로 종료 코드 비-0 — SC-46).

**결정: 3파일을 레포에 추적한다.** 그리고 재생 테스트는 추적본을 **덮어쓰지 않고 대조한다** — 다르면 실패하고, 갱신은 명시적 재생성으로만 한다.

이유 셋:

1. **원칙 9가 요구하는 것은 결정성만이 아니라 감사 가능성이다.** 추적본이 있으면 서버 물리가 의도치 않게 바뀐 순간이 **리뷰에 보이는 diff**로 나타난다. 추적하지 않으면 같은 변화가 흔적 없이 지나간다 — 기준이 "마지막으로 로컬에서 테스트를 돌린 사람의 파일"이 되기 때문이다.
2. **§3의 "같은 비트" 가정이 전제하는 것은 두 구현이 같은 입력·같은 초기 상태를 본다는 것이다.** 그 전제를 지키는 방법은 "두 곳이 같은 절차로 파일을 만든다"가 아니라 **"두 곳이 같은 파일을 연다"**이다. 추적이 그것을 보장한다. SC-51·52가 초과했을 때 "두 구현이 다르다"로 읽으려면, 먼저 **입력이 같았음이 의심의 여지 없어야** 한다.
3. **gitignore + 전제 조건 명시(대안 b)는 갈라짐을 없애지 못하고 보이지 않게 만든다.** 그 대가로 Unity 단독 환경에서 EditMode 전체가 빨간불이 되는 것까지 얹는다. 생성을 별도 단계로 승격하는 것(대안 c)도 "추적할 것인가"라는 같은 질문을 그대로 남기고 툴체인 한 겹만 늘린다.

**추적의 대가와 그 처리.** 525 KB 텍스트가 들어오고, 물리나 `ShipState` 모양이 바뀔 때마다 큰 diff가 난다. **이것은 비용이 아니라 신호다** — 물리를 바꿨는데 재생 결과가 그대로라면 그쪽이 이상하다. (JSONL은 줄 구조가 반복적이라 git 압축이 잘 듣고, 지금 `.git`은 4.9 MB다.) "커밋본과 재생 결과가 갈라지면 아무도 모른다"는 지적은 **대조가 없을 때만** 맞다 — 그래서 대조를 함께 정한다.

**대조 규칙** (server가 구현한다. 이 ADR은 메커니즘만 정하고 이름·플래그는 server가 고른다):

| 규칙 | 내용 |
|------|------|
| R-1 | 재생 워커의 출력은 지금처럼 **스크래치**에 쓴다. 부모는 run1·run2 바이트 동일을 먼저 단언한다(현행 유지 — 이것이 결정성 그 자체의 단언이다) |
| R-2 | 그다음 **run1 산출물과 `tests/data/replay/`의 추적본을 바이트 비교**한다. 다르면 **실패**하고, 실패 메시지에 재생성 방법을 적는다 |
| R-3 | `inputs.jsonl`도 같다. `maneuver_plan()`이 만든 내용을 추적본에 **직접 쓰지 말고** 스크래치에 쓴 뒤 대조한다. **코드가 정본이고 파일은 그 코드의 고정된 증거다** |
| R-4 | 갱신은 환경 변수 하나(예: `STARFALL_REPLAY_BLESS=1`)가 있을 때**만** 추적본을 덮어쓴다 |
| R-5 | `.gitignore`에 이 경로를 **넣지 않는다.** `Cargo.lock`·`server/.sqlx/`와 같은 이유이므로 같은 형식의 주석을 `.gitignore`에 남긴다(ADR-0001) |

R-1~R-4가 하는 일은 하나다: **테스트를 돌리는 것만으로 추적 파일이 조용히 바뀌는 일이 없어진다.** 물리를 바꾼 사람은 의도적으로 재생성하고 그 diff를 커밋에 담게 된다.

**client 쪽 귀결.** 파일이 추적되므로 EditMode는 더 이상 "아직 없을 수 있다"를 가정하지 않는다. 파일이 없으면 그것은 **깨진 체크아웃**이므로 `Ignore`/`Inconclusive`가 아니라 **실패**로 신고한다(경로와 `cargo test -p starfall-sim --test determinism` 재생성 명령을 메시지에 적는다). G-k는 그대로다 — **복사하지 않고 상대 경로로 참조한다.**

### 4. 스폰 — 시드 해시 + 간격 탐색, 난수 없음

designer 설계(§6.6)를 그대로 받는다.

```
seed   = world_id 의 하위 8바이트를 리틀엔디언 u64 로 읽은 값        # §4.1
index0 = H(seed ‖ actor_id_16bytes) mod point_count
round  = 0
loop:
    for k in 0 .. point_count-1:                                   # 링을 한 바퀴
        i = (index0 + k) mod point_count
        후보 = points_m[i] 를 반경 바깥으로 radial_offset_step_m × round 만큼 민 위치
        if 활성·잔류 함선이 clearance_m + hull_radius_m 안에 없다 : 그 후보를 쓴다
    # 한 바퀴가 다 막혔다 → 한 번만 밀어내고 끝낸다 (아래 "밀어내기 규칙")
    cycles = ceil( (월드의 현재 함선 수 + 1) / point_count )
    return index0 지점을 반경 바깥으로 radial_offset_step_m × cycles 만큼 민 위치
초기 속도 = (0,0,0),  초기 ω_aim = (0,0,0),  초기 ω_roll = 0,  초기 자세 = 성계 원점을 바라봄
```

**밀어내기 규칙: "시도수"는 월드의 현재 함선 수다** (2026-09-20 확정 — **앞선 결정을 뒤집었다**).

- 초안은 "시도수 = 링을 돈 바퀴 수"로 정하고 바퀴마다 더 밀며 재탐색하게 했다. **그 규칙에 결함이 있다.** 현재 데이터는 `max_probe_attempts(12) == point_count(12)`이므로 **바퀴 수가 언제나 1에서 끝나고**, 결과적으로 **모든 오버플로 스폰이 정확히 같은 지점(=`index0`를 한 칸 민 자리)에 쌓인다.** 링이 막혔을 때 겹침을 흩뜨리려던 규칙이 정반대로 **겹침을 한 점에 모은다.**
- 구현이 택한 규칙은 그 결함이 없다: `cycles = ceil((현재 함선 수 + 1) / point_count)`는 **월드가 찰수록 더 바깥으로 미는 단조 함수**라, 연속된 오버플로 스폰이 서로 `radial_offset_step_m`씩 벌어진다. 결정적이고(월드 상태는 결정적이다), 탐침이 `point_count`회로 **유계**이며, "왜 저기 났는가"가 "그때 월드에 N척이 있었고 링이 전부 막혀 있었다"로 설명된다.
- **그래서 구현 쪽 규칙을 계약으로 채택한다.** 코드가 이미 그렇게 되어 있어서가 아니라 **내가 쓴 규칙이 틀렸기 때문이다.** 되돌리려는 사람을 위해 결함을 여기 남긴다.
- **받아들이는 한계 둘.** (a) 밀어낸 위치는 **간격 검사를 하지 않는다** — 이번 슬라이스에 충돌 판정이 없어 피해가 시각뿐이고, 단조 밀어내기가 연속 겹침을 막는다. (b) 구현은 탐침 수를 `min(max_probe_attempts, point_count)`로 묶으므로 **`max_probe_attempts`가 `point_count`보다 커도 효과가 없다** — 데이터 필드의 의미가 "한 바퀴 안에서의 상한"이다. 둘 다 정원(I-44)이 함선 수를 묶어 주기 때문에 감당할 수 있다.
- **`H`는 splitmix64다**(구현 확정). 알고리즘 선택은 임의이고, 요구는 **레포 안에 명세가 있고 고정 입력의 출력을 테스트가 박아 둔다**는 것뿐이다.
- 같은 `actor_id`는 같은 월드에서 **항상 같은 지점**에서 시작한다(다른 함선이 없다면).
- **`H`는 `starfall-sim` 안에 손으로 쓴 결정적 정수 해시다.** 해시 크레이트를 결정적 코어에 들이면 결정성 보장을 그 크레이트의 릴리스 정책에 위임하게 된다. 알고리즘이 무엇이든(splitmix64류) **명세가 레포 안에 있고 고정 입력의 출력을 테스트가 박아 두면** 충분하다. 선택은 server가 하고 테스트로 고정한다.
- #### 4.1 `spawn_world_seed`는 `world_id`의 하위 8바이트다

`data/`에 전용 시드 필드가 없어 server가 택한 방법이고, **결정성에 직결되므로 여기 박는다.**

```
spawn_world_seed = u64::from_le_bytes(world_id.as_bytes()[8..16])
```

- **`world_id`는 월드 수명 동안 불변이다**(I-19와 같은 성격). 시드가 그것에서만 파생되면 시드도 자동으로 월드 상수가 되고, 별도 필드를 두었을 때 생기는 **"시드와 `world_id`가 따로 놀 수 있다"는 상태가 아예 존재하지 않는다.**
- **시드를 바꾸면 모든 actor의 스폰 지점이 재배치된다.** 그래서 시드를 바꾸는 것은 새 월드를 만드는 것과 같고, 실제로 그렇게만 할 수 있다 — `world_id`를 바꾸는 것이 유일한 방법이다(원칙 5).
- 나중에 `data/`에 전용 시드 필드가 생기더라도 **기존 월드에 적용하지 않는다.** 적용하려면 새 `world_id`다.
- 하위 8바이트를 쓰는 이유: UUIDv7의 상위 48비트는 타임스탬프라 **같은 시각에 만든 월드끼리 상관이 생긴다.** 하위 8바이트는 CSPRNG 구간이다.

#### 4.2 함선 클래스 선택 규칙이 없다 — 가정을 기록한다

**이 슬라이스는 모든 스폰에 성계 데이터의 `default_ship_class_id`를 준다.** 선택 규칙이 없는 것이 아니라 **선택지가 하나뿐이라 규칙이 필요 없다**(GDD §36의 MVP-1은 1인 함선 한 종이다).

기록하는 이유는 클래스가 둘이 되는 순간 **"누가 무엇을 근거로 고르는가"가 새 설계 항목**이 되기 때문이다 — 플레이어 선택이라면 그것은 **명령**이고 서버가 자격을 검증해야 하며(원칙 1), 소유라면 그것은 **영속 상태**라 함선 상태 영속화 ADR이 먼저 필요하다. **둘 다 이 슬라이스에 없다.** `SHIP_SPAWNED`가 `ship_class_id`를 이미 기록하므로 규칙이 생겨도 과거 이벤트는 그대로 읽힌다.

**"성계 원점을 바라봄"의 대체 규칙을 수식으로 못박는다**(server B-5). 기준 전방축 `f0 = (0,0,1)`에서 `fwd = normalize(origin − p)`로 가는 최소 회전:

```
c = 1 + dot(f0, fwd)
if c >= 1e-6 :
    q = normalize( (cross(f0, fwd).x, .y, .z, c) )
else :                                             # 대척점 — 최소 회전이 유일하지 않다
    axis = normalize( |f0.y| < 0.9 ? cross(f0, (0,1,0)) : cross(f0, (1,0,0)) )
    q    = (axis.x, axis.y, axis.z, 0)             # 그 축 둘레 180°
```

**"임의의 축"은 두 구현이 다른 것을 고른다는 뜻이다.** 어떤 축이든 상관없다 — **적혀 있기만 하면 된다.** 그리고 이 경로는 실제 데이터로 이미 가까이 간다(server 실측: `cradle.json`의 `[0, -250, 2500]`이 `dot = -0.995`, `1 + dot = 0.005`). 지금 퇴화하지 않는 것은 `y_alternation_m = ±250` 덕분이고, **`data/`는 designer 소유라 그 보호는 우연이다.**

### 5. 서버 판정 8단계에서 이번에 존재하는 것

GDD §33의 8단계 중 이 슬라이스가 실제로 실행하는 것은 다음이다. **없는 단계를 빈 함수로 만들어 두지 않는다.**

| 단계 | 이번 슬라이스 |
|---|---|
| 1 행위자 확인 | 세션의 `actor_id`, `command_id` 중복 제거 (p0-02에서 이미 동작) |
| 2 위치·상태 확인 | **이번에 처음 생긴다.** 그 행위자의 함선이 존재하는가. 클라이언트가 보낸 위치·현재 자세는 **존재하지 않으므로** 쓸 수 없다(I-26) |
| 3 대상 존재 확인 | 대상이 없는 명령이다 — 해당 없음 |
| 4 장비·자격 확인 | 함선 클래스의 추력·최대 속도·선회율이 한계를 정한다(§2) |
| 5 규칙 검증 | 입력 범위(I-33), 입력 속도 제한(ADR-0011 §4), `input_seq` 단조성 |
| 6 경제·자원 반영 | 해당 없음 |
| 7 상태 변경 | §2의 12단계. **tick 안에서만**(I-13, I-27) |
| 8 도메인 이벤트 | **이동은 이벤트를 만들지 않는다**(I-31). 스폰·디스폰만 만든다 |

## 검토한 대안과 버린 이유

- **각속도 명령(rate control)**: 적분기가 더 단순하다. designer가 버렸다(§3.2) — 지평선 없는 공간에서 방향 감각을 잃고, 무엇보다 **패킷이 빠졌을 때 이월하면 함선이 계속 돈다.**
- **평면 이동(황도면 고정)**: 되돌리는 비용이 p1-04 전투에서 청구된다.
- **각속도를 합 하나로 보내고 클라이언트가 분해**: 프레임당 26 B를 아낀다. **손실 분해라 선회 중 재조정이 원리적으로 정확할 수 없고**, 그 오차가 U-15 판정까지 가린다(server B-1).
- **B-3을 클라이언트 의무 명문화로 해결**: 코드 변경 0. 규약을 어긴 클라이언트의 진동이 **서버 지표로는 보이지 않는다**(두 구현이 똑같이 진동하므로 예측 오차 0). 문서로만 막는 규약 중 가장 깨지기 쉬운 형태다.
- **Verlet/RK4**: 정확도는 높지만 클라이언트 복제 부담이 크고 20 Hz·저속 기동에서 차이가 감각으로 드러나지 않는다(원칙 8).
- **지수 감쇠 `v *= exp(-d·dt)`** / **자세 오차를 `acos`로 환산**: 결정성 경계를 넘는다. 게인 단위가 읽기 불편한 것이 그 대가다.
- **오토레벨을 고정 속도(bang-bang)로**: 불감대 경계에서 떨린다.
- **범위 밖 조작 값을 클램프**(designer 제안): **이월 규칙이 이미 해결한다**(ADR-0011 §4). 거부를 유지한다(I-33).
- **수학·해시 크레이트 도입**: 편하지만 결정성 보장이 그 크레이트의 버전 정책에 묶인다. server가 손으로 쓰기로 했고 **크레이트 요청이 없다.**

## 결과

- 좋은 점: 서버와 클라이언트가 **문장 하나하나를 대조할 수 있는 같은 법**을 가진다. 초월함수 배제 + 금지 목록의 grep 가능성으로 "결정적"이 검증 가능한 주장이 된다. 비행 보조를 0으로 두면 그대로 완전 뉴턴 비행이 되므로 **"Flight Assist Off"가 새 코드 없이 이미 존재한다.** 롤 축 권한이 분리되어 세 입력 채널이 세 축에 1:1로 대응한다.
- 감수할 점: 12단계는 p0-02의 어떤 코드보다 길고 **두 언어에 두 번 존재한다.** 게인 단위가 `sin(θ/2)`당이라 직관적으로 읽히지 않는다. 각속도를 둘로 나눠 실어 프레임이 커진다(함선당 +37 B).
- 다시 검토할 조건: (a) AC-12가 초과할 때(→ 고정소수점 또는 허용 오차 기반), (b) IL2CPP 빌드가 생길 때 U-15b 재측정, (c) 각속도가 커서 1차 적분 오차가 눈에 보일 때, (d) 함선 간 충돌이 들어올 때(적분 뒤 해소 단계 추가).
