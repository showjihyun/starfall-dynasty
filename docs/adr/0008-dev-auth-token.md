# 0008. 개발용 인증 토큰 — 지금 무엇을 믿고, 무엇을 믿지 않는가

- 상태: **accepted** (server·client 검토 반영, 2026-09-18)
- 날짜: 2026-09-18
- 슬라이스: p0-02-networking-spike
- 검토: `_workspace/p0-02-networking-spike/01_server_spec_review.md`(§1.7 사실 정정), `01_client_spec_review.md`(R5, C-14). 반영 내역은 `01_architect_decisions.md`
- 근거 기획안 절: TECH §26 (Security — Server Authority, Signed/validated commands), GDD §33 (서버 판정 1단계 "행위자 확인")
- 관련: ADR-0004 §2(저장소 공개 전제), ADR-0005(업그레이드 전 인증), ADR-0007 §1(인증 실패는 도메인 이벤트가 아니다)

## 맥락

서버 판정의 1단계는 "행위자 확인"이다. 행위자가 없으면 나머지 7단계는 의미가 없고, `actor_id`가 들어간 도메인 이벤트도 아무것도 뜻하지 않는다. 그런데 계정·OIDC·세션 저장소는 이 슬라이스 범위 밖이다(`00_request.md`).

그래서 정할 것은 "어떻게 인증하는가"가 아니라 **"검증되지 않은 자리를 어떤 모양으로 비워 두면 나중에 진짜 인증으로 바꿀 때 한 곳만 고치면 되는가"**다. 동시에 이 슬라이스가 증명해야 하는 성질 하나는 지금 성립해야 한다: **클라이언트는 자기가 누구인지 주장할 수 없다.**

저장소가 공개라는 것(ADR-0004 §2)이 이 결정의 배경이다. 어떤 실제 자격 증명도 레포에 들어가지 않는다.

## 결정

### 1. 토큰 형식 — HMAC로 서명된 주체 id

```
token = "<subject_uuid_v7>.<hex(HMAC_SHA256(key = STARFALL_DEV_AUTH_SECRET, msg = subject_uuid_v7))>"
```

- `subject_uuid_v7`은 이 개발용 신원의 식별자이고, 검증에 성공하면 **그대로 세션의 `actor_id`가 된다.**
- 서버는 HMAC을 **상수 시간 비교**로 검증한다. 실패하면 업그레이드 전에 `401`을 주고 소켓을 열지 않는다.
- **추가되는 크레이트는 0개다**(server 실측 정정). `sqlx-postgres`가 SCRAM 인증 때문에 `hmac`·`sha2`·`subtle`을 이미 의존 트리에 갖고 있다. 상수 시간 비교도 `subtle::ConstantTimeEq`를 그대로 쓸 수 있다. (초안은 "작은 의존성이 추가된다"고 적었으나 틀렸다.)
- 토큰 발급은 서버가 하지 않는다. 같은 비밀을 아는 사람이 계산한다. 봇 하네스는 `world-local` 방식으로 `bot-000` ~ `bot-029`에 대응하는 결정적 UUIDv7을 만들어 30개 신원을 즉석에서 생성한다.

**왜 서명 없는 "토큰 = 주체 id"가 아닌가**: 그러면 클라이언트가 임의의 `actor_id`를 주장할 수 있고, 이 슬라이스가 증명하려는 "서버가 행위자를 정한다"가 증명되지 않는다. 서명이 있으면 클라이언트는 **자기가 받은 신원 외의 것을 주장할 수 없다** — 진짜 인증과 같은 성질을 최소 비용으로 얻는다.

**왜 JWT가 아닌가**: JWT는 만료·발급자·대상·키 회전·알고리즘 혼동 방어를 전부 딸려 오게 하고, 그중 어느 것도 이 슬라이스에서 검증되지 않는다. 절반만 구현한 JWT는 "표준을 썼다"는 잘못된 안심을 준다. 진짜 인증을 넣을 때는 JWT든 OIDC든 통째로 들어온다.

### 2. 전달 경로 — 업그레이드 요청의 `Authorization` 헤더

```
GET /ws HTTP/1.1
Authorization: Bearer <token>
```

- **업그레이드 전에** 검증한다(`rust-authoritative-server` §6). 실패한 요청에는 WebSocket 연결이 존재하지 않으므로 세션도 `SESSION_OPENED`도 없다.
- 쿼리 문자열(`/ws?token=...`)을 쓰지 않는다. 접근 로그·리퍼러·프록시에 남는다.
- 자격 증명을 요청에서 꺼내는 코드는 **한 함수**에 둔다. WebGL(브라우저 WebSocket은 임의 헤더를 못 넣는다)과 진짜 인증이 바꿀 지점이 그 함수뿐이도록 한다(ADR-0005 §6).
- **클라이언트는 401과 503을 구분할 수 없다**(client 실측, ADR-0005 §6): Unity의 `ClientWebSocketOptions`에 `CollectHttpResponseDetails`가 없어 업그레이드 실패의 상태 코드를 읽지 못한다. 그래서 **인증 실패의 증거는 언제나 서버 쪽**(401 응답 로그, `SESSION_OPENED` 증가 0)이고, 클라이언트는 원인을 구분하지 않고 재시도한다. 이 비대칭은 AC를 약화시키지 않는다 — AC-4는 원래 서버 측 증거로 판정한다. `SetRequestHeader`·`KeepAliveInterval`·`AddSubProtocol`은 netstandard2.1·Mono 양쪽에 존재함이 확인됐다.

### 3. 비밀이 없으면 인증이 아니라 **엔드포인트**를 끈다

`STARFALL_DEV_AUTH_SECRET`이 비어 있거나 없으면:

- 서버는 **정상 기동한다.** `/healthz`·`/readyz`는 영향받지 않는다(p0-01 AC-2·AC-3이 계속 유효해야 한다).
- 기동 로그에 어떤 변수가 없는지 WARN으로 남긴다.
- `GET /ws`는 업그레이드하지 않고 **503**과 `{"status":"unavailable","reason":"auth_not_configured"}`을 준다. `reason`이 필요한 이유는 `/ws`가 다른 이유로도 503을 내기 때문이다(기록 백로그 초과 — ADR-0007 §4). 같은 본문이면 둘을 구분할 수 없다. `reason`은 닫힌 집합 `auth_not_configured | recording_backlog`이다.

**기본 비밀값을 코드에 두지 않는다.** 기본값이 있으면 그 값이 배포까지 따라간다. 반대로 기동을 막으면 인증과 무관한 헬스 체크까지 인증 설정에 종속된다. 그래서 "프로세스는 살고, 인증이 필요한 표면만 죽는다"를 택한다.

`.env.example`에는 이름만으로 용도가 드러나는 개발 전용 값을 둔다: `STARFALL_DEV_AUTH_SECRET=dev_only_not_a_secret`. 공개 저장소에 들어가지만 비밀이 아니다 — 이것이 비밀처럼 보이지 않는 것이 요구사항이다.

### 4. 이 토큰이 하지 **않는** 것 (전부 의도된 공백)

| 없는 것 | 결과 | 언제 생기는가 |
|--------|------|-------------|
| 만료 | 한 번 만든 토큰은 영원히 유효하다 | 진짜 인증 |
| 폐기·블랙리스트 | 유출된 토큰을 막을 방법이 없다 | 진짜 인증 |
| 키 회전 | 비밀을 바꾸면 모든 토큰이 동시에 죽는다 | 진짜 인증 |
| 계정·프로필 | `subject`는 DB 어디에도 없다. `actor_id`는 아무것도 참조하지 않는 UUID다 | p1(캐릭터) |
| 인증 시도 레이트 리밋 | 온라인 무차별 대입이 가능하다 | 서버가 127.0.0.1 밖에 노출되는 슬라이스 |
| 비대칭 키 | 검증자가 곧 발급자다. 검증만 하는 서비스를 나눌 수 없다 | 인증 서비스 분리 시 |
| 전송 암호화 | 평문 ws. 토큰이 와이어에 그대로 흐른다 | TLS 종단 슬라이스 |
| 권한·역할 | 인증된 모두가 같은 것을 할 수 있다 | 권한이 갈리는 첫 기능 |

**이 표가 이 ADR의 핵심이다.** 이 토큰을 신뢰할 수 있게 만드는 것은 암호학이 아니라 **배포 경계**다: 서버가 `127.0.0.1`에만 바인딩되고, 비밀이 개발 머신에만 있다. 그 전제 중 하나라도 깨지면(LAN 노출, 공유 개발 서버, 스테이징) 이 토큰은 즉시 부적절해진다. 그 순간이 아래 "다시 검토할 조건" (a)다.

### 5. 지금 성립하는 성질 (스파이크가 실제로 증명하는 것)

토큰이 약해도 다음은 진짜 인증과 **똑같이** 성립하며, 이 슬라이스가 이것을 검증한다.

1. **행위자는 서버가 정한다.** `actor_id`는 검증된 토큰에서만 나온다. 명령 envelope에는 행위자 필드가 없고(I-6), payload의 어떤 필드도 `actor_id`가 되지 않는다.
2. **인증되지 않으면 세션이 없다.** 401이면 소켓이 열리지 않고 `SESSION_OPENED` 행도 생기지 않는다. "연결 수"와 "인증된 행위자 수"가 같다.
3. **클라이언트는 자기 신원을 SESSION_READY로 통보받는다.** 묻지 않고 알려 준다.
4. **인증 실패는 도메인 이벤트가 아니다.** 세계에서 아무 일도 일어나지 않았다(ADR-0007 §1). 로그와 메트릭에만 남는다.

진짜 인증으로 바꿀 때 바뀌는 것은 §2의 추출 함수와 §1의 검증 함수뿐이고, 위 네 성질은 그대로다.

## 검토한 대안과 버린 이유

- **인증 없음(연결하면 익명 세션)**: `actor_id`가 서버가 만든 임의값이 되어 "누가 무엇을 했는가"가 재연결마다 리셋된다. 서버 판정 1단계를 전혀 연습하지 못한다.
- **토큰 = 주체 id(서명 없음)**: 클라이언트가 임의 행위자를 주장할 수 있다. 이 슬라이스가 증명하려는 성질이 정확히 이것이라 안 된다.
- **JWT(HS256)**: 만료·발급자·대상·`alg` 혼동 방어를 전부 딸고 오는데 어느 것도 검증되지 않는다. 라이브러리 하나로 "인증이 있다"는 착각을 산다.
- **환경 변수에 토큰 → 주체 매핑 표**: 크립토 의존성은 없지만 봇 30개에 30줄이 필요하고, 봇 수를 바꿀 때마다 설정을 고쳐야 한다. 부하 테스트의 규모를 설정 파일이 제한하게 된다.
- **비밀 미설정 시 기동 거부**: 인증과 무관한 `/healthz`·`/readyz`가 인증 설정에 종속된다. p0-01의 합의된 수용 기준이 깨진다.
- **코드에 기본 비밀값**: 기본값은 배포까지 간다. 예외 없다.
- **지금 OIDC/계정 서비스**: 계정·캐릭터 모델이 없어 붙일 대상이 없다. 범위 폭발(GDD §41)의 교과서적 시작.

## 결과

- 좋은 점: "서버가 행위자를 정한다"가 스파이크 단계에서 실제로 성립하고 테스트된다. 진짜 인증으로 가는 교체 지점이 두 함수로 좁혀져 있다. 공개 저장소에 비밀이 들어가지 않는다. 인증이 설정되지 않은 환경에서도 헬스 체크는 계속 동작한다.
- 감수할 점: 만료·폐기·회전·레이트 리밋·TLS가 전부 없다. 이 토큰은 `127.0.0.1` 바인딩이라는 **환경 가정** 위에서만 안전하고, 그 가정은 코드가 아니라 사람이 지킨다. 클라이언트가 인증 실패를 스스로 알아낼 수 없어, 토큰이 틀린 상태에서도 조용히 재시도만 한다(원인은 서버 로그에 있다).
- 다시 검토할 조건: (a) 서버가 루프백 밖에 바인딩되는 첫 순간(LAN 테스트·공유 개발 서버·스테이징) — **그 슬라이스는 진짜 인증 없이 진행하지 않는다**, (b) 계정·캐릭터 모델이 생길 때(p1), (c) WebGL 빌드에서 헤더를 쓸 수 없게 될 때(ADR-0005 §6), (d) 권한이 갈리는 첫 기능이 생길 때.
