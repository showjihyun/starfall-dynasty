# 0015. 클라이언트 데이터 배포 — 레지스트리가 사본의 범위를 정하고, 서버 전용 값은 파일로 나눈다

- 상태: **accepted** (2026-10-05, architect3 — p1-02 사용자 결정 Q3 "누출은 p1-02 에서 수용하고 데이터 배포 경로 ADR 을 다음 슬라이스 전에" 의 후속. 선택지 (c) 는 p1-02 스펙 §9.1 Q3 가 "이번 슬라이스에서 할 수 있는 가장 작은 차단책" 으로 이미 적은 것이고, 이 ADR 은 그것을 일반 규칙으로 만든다)
- 날짜: 2026-10-05
- 슬라이스: p1-03-trading
- 관련: ADR-0012 §7(파일 복사 — "이번만"), 재검토 조건 (d)(`data/` 3 → 10 파일로 충족), ADR-0002 §1a, 스펙 p1-02 I-68·§9.1 Q3, p1-02 `01_architect_tasks.md` 만기 표 2행

## 맥락

- 클라이언트는 `data/` 를 **통째로** `client/Assets/_Project/Data/` 에 복사해 읽는다(ADR-0012 §7). 동일성은 EditMode `ClientDataCopy_MatchesRepositoryOriginal`(SC-50) 이 `data/**/*.json` 전체와 사본 전체의 바이트 동일로 지킨다.
- p1-02 에서 `data/world/deposits/cradle.json` 이 **서버 전용 값**(`mineral_id`·`initial_reserve_kg`, 광맥 8행)을 갖게 됐다. 클라이언트 코드는 그 필드를 읽지 않지만(I-68 — `DepositFieldTable.cs` 에 필드가 없다) **빌드 파일을 열면 정답이 보인다.** 사용자는 p1-02 에서 이 누출을 수용하고 이 ADR 을 p1-03 착수 전 만기로 걸었다.
- **만기는 지났다.** 기계적 판정("p1-03 `00_request.md` 가 생기는 시점에 이 ADR 이 accepted 인가")은 비-통과다 — 2026-10-05 `00_request.md` 생성 시점에 `docs/adr/` 에 0015 가 없었다. 이 ADR 은 그 비-통과를 p1-03 Phase 2 안에서 닫는다. **만기 표의 닫힘 조건은 ADR 이 아니라 분모 0 이다**(서버 전용 필드가 사본에 0 개) — 그것은 p1-03 구현(T 태스크)과 qa 항목이 닫는다.
- 그리고 같은 문제의 더 넓은 모양이 있다: `data/history/rules/mineral-discovery.json`(소비자 history 뿐)도 사본에 들어간다. 해롭지 않지만 **"무엇이 클라이언트에 가는가" 를 정하는 규칙이 없다**는 증거다. 레지스트리의 data 종류 `consumers` 는 그 규칙이 될 수 있었는데 실제와 어긋나 있다 — `SHIP_CLASS`·`STAR_SYSTEM` 은 클라이언트가 읽는데(`GreyboxDataLoader.cs`, `ShipClassStats.cs`) `consumers` 에 `client` 가 없다.
- p1-03 은 정거장·시장 데이터를 더한다. 거기에 서버 전용 값(예: 숨은 수요 곡선)이 하나라도 생기면 같은 누출이 반복된다.

## 결정

### 1. 사본의 범위 = 레지스트리에서 `consumers` 에 `client` 가 있는 data 종류의 파일 — 그 밖은 복사하지 않는다

- 레지스트리의 data 종류 항목에 **`data_files`**(필수, glob 목록 — `data/` 기준 상대 경로) 를 둔다. 그 종류의 파일이 어디 있는지의 **정본**이다. `registry_version` 4 → 5.
- **클라이언트 사본 = `consumers` 에 `client` 가 있는 data 종류의 `data_files` 가 가리키는 파일 전부, 그리고 그것뿐**이다. 사본과 원본의 바이트 동일은 그대로다.
- SC-50 의 모양이 바뀐다: "원본 전체 = 사본 전체" 에서 **"레지스트리가 유도한 기대 집합 = 사본 집합(독립 순회 두 번, 바이트 동일)" + "사본에 기대 집합 밖의 파일 0"**. 기대 집합이 비면 FAIL(검증 규율 — 0 = 0 은 검사가 아니다).
- `data/` 아래의 모든 `*.json` 은 정확히 하나의 data 종류의 `data_files` 에 걸려야 한다. **어느 종류에도 걸리지 않는 파일은 FAIL**(스키마 검증도 복사 판단도 받지 않는 파일 — p1-02 AC-19(c2) "읽히지 않는 데이터 파일 0" 의 계약 쪽 판). 두 종류에 걸리는 파일도 FAIL.
- `tests/e2e/validate_data_files.py` 의 하드코딩 `TARGETS` 는 레지스트리의 `data_files` 에서 유도하는 것으로 바꾼다(손으로 적은 두 번째 목록은 레지스트리와 갈라질 자리다).
- 레지스트리 `consumers` 를 실제에 맞춘다: `SHIP_CLASS`·`STAR_SYSTEM` 에 `client` 추가(클라이언트가 이미 읽는다 — 코드 참조가 있어 커버리지 스크립트가 통과한다), `SIGNIFICANCE_RULE` 은 `history` 만 그대로 → **사본에서 빠진다.**

### 2. 서버 전용 값은 파일로 나눈다 — 필드 단위 마스킹을 하지 않는다

- 한 data 종류는 **전부 공개이거나 전부 서버 전용**이다. 한 파일 안에서 "이 필드는 클라이언트가 읽지 않는다" 는 규칙은 두지 않는다 — 그것이 p1-02 의 누출 모양이었다.
- `DEPOSIT_FIELD` 를 둘로 나눈다.
  - **`DEPOSIT_FIELD`**(`schema_version` 2) — `data/world/deposits/{star_system_id}.json`. `id`·`display_name`·`position_m`·`radius_m` 만. 소비자 server, client.
  - **`DEPOSIT_RESERVE`**(신규, `schema_version` 1) — `data/world/deposit-reserves/{star_system_id}.json`. `deposits[{deposit_id, mineral_id, initial_reserve_kg}]`. 소비자 **server 만** → 사본에 들어가지 않는다.
  - 서버 기동 검증 추가(기동 실패): 같은 `star_system_id` 의 두 파일이 짝으로 존재하고, `deposit_id` 집합이 **정확히 같다**(한쪽에만 있는 광맥 0 — 둘 다 방향). 기존 검산(광물 존재, 광물마다 광맥 ≥ 1, `regen_kg ≤ initial_reserve_kg`, 채굴 구역 비겹침)은 합친 모양에 그대로 건다.
- 데이터 파일의 `schema_version` 은 이력 보존 대상이 아니다(DB 에 저장되지 않는다). 그래서 `DEPOSIT_FIELD` 1 → 2 에 업캐스터가 없다 — 서버는 2 만 읽고 1 이면 기동 실패한다. 결정성: 광맥의 수치는 한 글자도 바뀌지 않으므로 **채굴 golden(`sim/tests/data/replay_mining/`)과 이동 golden 은 재생성 없이 통과해야 한다.**
- 새 data 종류를 만드는 사람(designer·architect)은 종류를 정할 때 "클라이언트가 이 값을 봐도 되는가" 를 **종류 단위로** 답한다. 서버 전용 값이 공개 종류에 들어가야 할 것 같으면 그 값을 서버 전용 종류로 뺀다.

### 3. 사본은 계속 파일 복사다 — 와이어 배포는 아직 아니다

- 서버가 세션 시작에 데이터를 보내거나 REST 로 내려주는 방식은 이번에 하지 않는다. 그것이 필요해지는 조건(아래 재검토)이 아직 없다. 지금의 문제는 "무엇을 보내는가" 이지 "어떻게 보내는가" 가 아니고, 1·2 가 그것을 푼다.
- 복사는 지금처럼 사람이(또는 client 가) 한다. 검사가 범위를 지킨다 — 복사기가 범위를 지키는 것이 아니다. 복사 스크립트를 만들면 그것도 레지스트리에서 집합을 유도해야 한다.

## 검토한 대안과 버린 이유

- **(a) 서버 전용 값을 `data/` 밖으로** — "`data/` 는 한 곳" 이 깨진다. 스키마 검증·출처 게이트·데이터 파일 짝 표가 두 루트를 알아야 한다.
- **(b) 전부 공개** — 발견이 탐사가 아니라 빌드 파일 읽기 경주가 된다(p1-02 디자인 Q7).
- **필드 마스킹 복사(공개 필드만 골라 쓴 사본)** — 사본이 원본과 바이트가 달라져 SC-50 의 바이트 동일 방어가 사라지고, 마스킹 규칙이 세 번째 목록이 된다.
- **와이어 배포(SESSION_READY 확장·REST)** — §3. 지금 값이 크지 않다. 클라이언트가 서버 없이 그레이박스 데이터를 읽는 테스트 경로(EditMode)도 잃는다.
- **`consumers` 대신 별도 `client_visible: bool`** — 같은 사실을 두 필드가 말하게 된다. `consumers` 는 커버리지 스크립트가 이미 코드 참조로 검사하므로 **틀리면 드러나는** 쪽이다.

## 결과

- 좋은 점: 누출 분모 2 → 0(구현 후). "무엇이 클라이언트에 가는가" 가 레지스트리 한 곳에서 기계적으로 유도되고, 검사(SC-50 개정·`validate_data_files.py`)가 같은 곳을 읽는다. 어느 종류에도 속하지 않는 data 파일이 구조적으로 FAIL 이 된다.
- 감수할 점: 광맥 하나가 두 파일에 걸친다 — 참조 무결성 검산이 하나 는다(§2). 레지스트리가 data 경로를 알게 되어 data 파일 이동은 레지스트리 수정이 된다. 클라이언트 사본에서 `history/rules/` 가 빠지므로 그 파일을 읽던 클라이언트 테스트가 있으면 고친다(architect 확인: 클라이언트 코드에 참조 없음, `ContractFixtureTests` 의 SC-50 만 전체 순회로 그것을 셌다).
- 다시 검토할 조건: (a) 서버가 data 를 재기동 없이 바꾸는 기능(핫 리로드·운영 중 가격 조정) → 와이어 배포, (b) 클라이언트 빌드와 서버 data 버전이 갈라져 배포되는 환경(외부 플레이테스트) → 세션 시작에 data 해시 대조 또는 와이어 배포, (c) WebGL 빌드 → 파일 사본의 크기·캐시 정책.
