# 0006. 시뮬레이션 tick — 주기, 게임 시간 축, 초과 정책, 명령 큐

- 상태: **accepted** (server·client 검토 반영, 2026-09-18)
- 날짜: 2026-09-18
- 슬라이스: p0-02-networking-spike
- 검토: `_workspace/p0-02-networking-spike/01_server_spec_review.md`(B-1·B-3·B-4·B-5·B-8·B-11·B-12), `01_client_spec_review.md`(R4). 반영 내역은 `01_architect_decisions.md`
- 근거 기획안 절: TECH §12 (Simulation Tick), TECH §13 (결정성), HSE §30 (Ordering), HSE §32 (Determinism), HSE §35–36 (Game Time·Calendar), GDD §33 (서버 판정)
- 관련: ADR-0002 §5(시간 표기 — tick↔달력 변환을 "tick ADR"로 미룬 항목이 여기서 결정된다), ADR-0005(프레이밍), ADR-0007(영속화)

## 맥락

세 가지가 한 덩어리로 묶여 있어 한 ADR로 정한다.

1. **tick 주기** — 한 번 정하면 클라이언트 보간 버퍼, 명령 지연 예산, 지금 저장되는 이벤트의 시간 해상도가 전부 여기에 맞춰진다.
2. **게임 시간 축** — `occurred_at`은 `tick`에서 **결정적으로 파생된 게임 달력 문자열**이다(ADR-0002 §5). 파생 규칙은 아직 정해지지 않았는데, 이번 슬라이스가 그 문자열을 DB에 쓰기 시작한다. 쓰고 나면 바꾸는 순간 과거 행이 거짓이 된다(원칙 5).
3. **명령 큐** — 아키텍처 전제("핸들러는 상태를 바꾸지 않는다")는 큐가 유한할 때만 성립한다. 가득 찼을 때 무엇을 하는가가 곧 이 전제의 실제 모습이다.

## 결정

### 1. 고정 20 Hz (tick 주기 50 ms)

`rust-authoritative-server` §2의 권장 범위(10~20 Hz)의 상단을 택한다.

- 명령이 접수되어 판정될 때까지의 큐 대기는 평균 25 ms, 최악 50 ms다. 왕복(클라이언트→서버→클라이언트)에서 tick이 차지하는 몫이 이 정도면, 로컬에서 측정한 왕복 지연의 대부분이 **큐가 아니라 전송**이라는 것을 구분해 볼 수 있다.
- 클라이언트의 "약 2 tick 지연 보간"(`unity-client` §2)이 100 ms가 되어 사람이 느끼는 범위 안에 있다.
- 10 Hz는 지금 더 싸지만, 전투가 들어올 때 반드시 올려야 하고 그때는 이미 저장된 이벤트의 시간 해상도가 10 Hz에 묶여 있다.

**tick 주기는 월드 속성이다**(§3). 서버 설정이 아니라 `worlds` 행에 기록되고, 서버는 기동 시 자기 설정과 다르면 **기동을 거부한다**. 이 규칙이 없으면 누군가 환경 변수를 바꾸는 것만으로 이미 저장된 이벤트의 게임 시간 의미가 조용히 달라진다.

### 2. tick은 건너뛰지 않는다 — 초과 시 따라잡지 않는다

```
// 전용 OS 스레드에서 돈다. tokio 태스크가 아니다 (아래 2.1).
loop {
    let started = Instant::now();
    run_tick(tick);              // 1~7단계
    tick += 1;                   // 항상 정확히 +1
    let elapsed = started.elapsed();
    if elapsed < PERIOD { std::thread::sleep(PERIOD - elapsed); }   // 초과면 즉시 다음 tick
}
```

- **tick 번호는 항상 1씩 증가한다.** 건너뛰지 않는다. `(world_id, tick, sequence)`가 촘촘해야 재생·결정성 비교가 성립한다(HSE §30·§32).
- **따라잡기(catch-up)를 하지 않는다.** 한 tick이 늦었다고 여러 tick을 몰아서 돌리지 않는다. 몰아 돌리면 한 번의 지연이 CPU 스파이크를 만들고 그 스파이크가 다음 지연을 만드는 나선이 된다.
- 그 대가: 지속적으로 초과하면 **게임 시간이 실제 시간보다 뒤처진다**. 이것을 감수하는 이유는 대안(tick 건너뛰기)이 게임 시간을 점프시켜 재생 불가능하게 만들기 때문이다. 뒤처짐은 숨기지 않고 `tick_lag_seconds`로 관측한다.
- tick 안에서 `SystemTime::now()`/`Instant::now()`를 쓰지 않는다. 위 루프의 계측은 tick **밖**(루프 제어)이다. 실제 시각이 필요한 필드(`recorded_at`)는 영속화 단계에서 붙는다(ADR-0007 §4).

### 2.1 tick 루프는 전용 OS 스레드에서 돈다 — `tokio::time::sleep`을 쓰지 않는다

**이 PC에서 `tokio::time::sleep(50ms)`의 실제 간격은 61 ms다**(server 실측, 2026-09-18). Windows 기본 시스템 타이머 해상도 15.625 ms 때문에 50 ms 요청이 4 × 15.625 = 62.5 ms로 올림된다. 결과는 게임 로직이 **하나도 없는** 루프에서 60초가 73.5초가 되는 것 — 게임 시간이 실제 시간보다 22 % 뒤처진다.

| 방식 | 간격 p50 | p99 | 60초 루프의 실제 소요 |
|------|---------|-----|---------------------|
| `tokio::time::sleep` (멀티스레드 런타임) | **61.2 ms** | 63.6 ms | **73.5 s** (lag +13.5 s) |
| **전용 OS 스레드 + `std::thread::sleep`** | **50.33 ms** | 51.2 ms | 20.14 s / 이론 20.0 s (lag +0.7 %) |
| sleep(남은−2 ms) 후 spin | 50.001 ms | 50.26 ms | 20.005 s |

**결정: 전용 OS 스레드 + `std::thread::sleep`.** `std::thread::sleep`은 고해상도 대기 타이머를 써 전역 타이머 해상도 설정과 무관하다. 새 의존성도, `unsafe`(`timeBeginPeriod`)도, spin으로 코어를 태우는 것도 필요 없다. 게이트웨이와의 통신은 `tokio::sync::mpsc`의 `try_send`(async 쪽) / `try_recv`(동기 쪽)로 양쪽 다 블로킹 없이 된다.

**이 줄이 없으면 다음 사람이 "async 서버니까 tokio 타이머"로 되돌린다.** 그리고 그 회귀는 "tick 초과율 100 %"로만 보여서 설계를 의심하게 만든다. 부수 효과로 **측정이 재현 가능해진다**: tokio 타이머는 다른 앱(Chrome, Unity Editor)이 전역 타이머 해상도를 올리면 수치가 달라지는데, AC-17이 정확히 "Unity Editor를 띄운 채 측정"이다.

### 2.2 "tick 초과"는 `run_tick()` 본문 소요다 — 루프 간격이 아니다

위 표의 마지막 열이 보여주듯 **완벽한 타이머에서도 "tick 사이 간격 > 50 ms"는 100 %다**(간격에는 언제나 오버헤드가 붙는다). 따라서:

- `tick_overrun_total`의 판정 기준은 **`run_tick()` 본문 소요 시간 > 50 ms**다. 이것만이 "설계 문제인가"에 답한다.
- 루프 주기 쪽 드리프트는 `tick_lag_seconds`로 **기록만** 한다. 이 PC의 바닥값은 전용 스레드 기준 **+0.7 %/분**이고 그보다 좋은 값은 나올 수 없다. 리포트는 측정치와 이 바닥값을 나란히 적어야 한다.
- "단일 tick 최대 소요"도 본문 소요다. 간격으로 재면 GC도 없는 빈 루프가 66 ms를 찍는다.

### 2.3 tick은 월드 단위로 재개한다 — 프로세스마다 0으로 돌아가지 않는다

초안은 "프로세스가 살아 있는 동안 1씩 증가"만 정했다. server가 **이 PC PostgreSQL 18.6에서 그 구멍의 결과를 재현했다**: 재기동하면 tick이 다시 낮은 값부터 돌아 같은 `(world_id, tick, sequence)`에 쓰게 되는데, 삽입이 `ON CONFLICT (event_id) DO NOTHING`이라 **`UNIQUE (world_id, tick, sequence)` 위반을 잡지 못하고 트랜잭션 전체가 중단된다.** tick 단위 1 트랜잭션이므로 **그 tick의 멀쩡한 이벤트까지 함께 사라진다.** 충돌 여부가 연결이 들어온 타이밍에 달려 **비결정적**이라, 원인이 봇이나 네트워크로 오진되기 가장 쉬운 종류의 버그다.

**결정: 기동 시 그 월드의 마지막 tick 다음부터 재개한다.**

```
start_tick = (worlds.last_tick 와 MAX(domain_events.tick) 중 큰 값, 둘 다 없으면 -1) + 1
```

- `worlds.last_tick`(신설, nullable)은 **이벤트를 쓰는 트랜잭션 안에서 함께 갱신**한다(ADR-0007 §2·§4). 같은 트랜잭션이라 두 출처가 구조적으로 어긋나지 않는다.
- 이벤트를 하나도 내지 않은 tick은 아무 데도 기록되지 않는다. 그래서 유휴 상태에서 재기동하면 tick이 **정체**할 수 있다 — 그러나 **뒤로 가지는 않는다.** 원칙 5가 요구하는 것은 후자다.
- 부수 효과: 다운타임만큼 `occurred_at`이 건너뛴다. 게임 시간이 멈춰 있다가 이어지는 것이고, 되감기지 않는다.
- 이 결정으로 **`UNIQUE (world_id, tick, sequence)` 위반이 다시 "버그 신호"가 된다**(재기동할 때마다 나는 에러가 아니게 된다). ADR-0007 §4가 그 신호를 삼키지 말라고 요구하는 근거가 여기서 복원된다.
- `/debug/stats`는 `start_tick`을 노출한다(§7).

### 3. 게임 시간 축 — tick → `occurred_at`

`occurred_at`은 다음 규칙으로 tick에서만 파생한다. 실제 시각은 입력이 아니다.

```
game_seconds = (tick / tick_hz) * calendar_scale          # 정수 나눗셈(내림)
occurred_at  = calendar_epoch + game_seconds              # UTC, 초 단위, GameTime 형식
```

| 상수 | 이번 월드 값 | 의미 |
|------|------------|------|
| `tick_hz` | 20 | 실제 1초당 tick |
| `calendar_epoch` | `3800-01-01T00:00:00Z` | 게임 달력 기준점 |
| `calendar_scale` | 60 | 실제 1초 = 게임 60초(1분) |

- `tick_hz`로 먼저 나누는 이유: **tick 주기를 바꿔도 게임 달력 속도가 따라 움직이지 않는다.** 두 축을 분리하지 않으면 "20 Hz로 올렸더니 역사가 2배 빨리 늙는" 결합이 생긴다.
- 세 상수는 **월드 속성**이며 `worlds` 테이블에 기록된다(ADR-0007 §2). 한 월드의 수명 동안 불변이다. 바꿔야 하면 **새 `world_id`로 새 월드를 만든다** — 과거 행을 다시 해석하지 않는다(원칙 5).
- **`calendar_scale = 60`은 사용자 결정으로 확정됐다**(2026-09-18): 현실 1초 = 게임 1분, 현실 1시간 = 게임 2.5일. 한 세션(1~2시간)이 게임 내 며칠이 되어 "역사가 쌓인다"는 감각이 생기면서도 역사 문장의 날짜가 비현실적으로 튀지 않는다.
- **같은 `world_id`를 쓰는 계약 fixture는 같은 `tick_hz`를 써야 한다.** 이 불변식을 어긴 fixture가 하나 있었고(`SESSION_READY/tick-zero.json`이 스파이크 월드 id에 `tick_hz: 1`을 썼다 — B-14) 별도 월드 id로 고쳤다. AC-20이 fixture 값을 월드 상수와 대조할 때 걸리는 종류의 모순이다.
- 공식·상수·fixture의 일치를 server가 이 PC PostgreSQL에서 계산해 **fixture 3건과 문자열까지 같음을 확인**했다(tick 1200 → `3800-01-01T01:00:00Z`, 24000 → `3800-01-01T20:00:00Z`, 86400 → `3800-01-04T00:00:00Z`).
- 구현 주의: `tick_hz`로 **먼저** 나눈다. `tick * calendar_scale / tick_hz`는 같은 값을 주지만 tick이 클 때 곱이 넘칠 수 있고, 무엇보다 **두 축의 분리라는 의도가 코드에서 사라진다.** 날짜 산술에 `chrono`가 필요 없다 — epoch 이후 초 → `YYYY-MM-DDTHH:MM:SSZ`는 civil-from-days 15줄이면 되고, 그래야 `starfall-sim`이 **의존성 0개**로 남는다. 같은 헬퍼를 `recorded_at`(RealTime) 포맷에도 재사용한다(ADR-0007 §4).
- `occurred_at`은 표시·역사 문장 전용이다. **정렬·비교·판정에 쓰지 않는다**(정본은 `tick`). 소비자가 실제 DateTime으로 파싱하지 않게 계약이 `GameTime` 문자열 타입을 쓴다.
- 역산(`occurred_at` → tick)을 지원하지 않는다. 정수 나눗셈으로 정보가 손실된다(20 tick이 같은 초에 매핑된다).

### 4. 명령 경로 — 핸들러는 큐에 넣기만 한다

```
WS 수신 태스크(연결당 1)          tick 루프(전용 OS 스레드 1)
  프레임 파싱·타입 peek     ──►   1. 이번 tick 도착분을 제출 순번으로 확정 정렬
  세션 in-flight 확인              2. 검증(중복·타입·버전)
  제어 채널 / 명령 큐에 제출       3. 상태 전이   ← 상태가 바뀌는 유일한 자리
                                   4. 도메인 이벤트 발행 (tick, sequence 부여)
                                   5. (역사 판정 — 이 슬라이스에는 없음)
                                   6. TickOutcome 반환 → 영속화 태스크 + 게이트웨이
                                   7. 게이트웨이가 세션별 송신 큐로 라우팅
```

- 수신 태스크는 **`WorldState`를 참조하지 않는다.** 크레이트 경계로 강제한다: 게이트웨이는 `starfall-sim`의 제출 핸들만 가지며 상태 타입에 접근할 수 없다.
- **`sim`의 세션 모델에 송신 채널이나 소켓을 넣지 않는다.** 가장 자연스러운 구현이 `Session { actor_id, tx: Sender<Message>, ... }`인데, 그 순간 `sim`이 tokio 채널에 묶여 (a) IO-free 주장이 흐려지고 (b) **아키텍처 전제를 증명하는 수동 step 테스트가 런타임 없이 돌지 않는다.** 경계는 이렇게 둔다.
  ```
  sim 이 소유:      SessionId -> { actor_id, correlation_id, dedup_ring, in_flight }
  gateway 가 소유:  SessionId -> mpsc::Sender<Outbound>
  tick 의 반환값:   TickOutcome { tick, events: Vec<DomainEvent>, outbound: Vec<(SessionId, Message)> }
  ```
  `sim::step()`이 순수 함수에 가까워지고(입력: 제출 목록, 출력: 이벤트 + 보낼 메시지), 게이트웨이는 라우팅만 한다.
- **제어 제출(세션 열기·닫기)은 명령 큐를 쓰지 않는다.** 둘이 같은 bounded 4096 큐를 쓰면, 큐가 가득 찬 순간 세션 종료 제출이 거부되어 그 세션은 **`SESSION_OPENED`만 있고 `SESSION_CLOSED`가 없는 상태**로 남는다 — I-16 정면 위반이고, "짝 없는 이벤트 0건"이 **부하 상황에서만** 깨진다(찾기 가장 어려운 형태다). 제어 제출은 **거부 대상이 아니며** 전용 경로(용량 = 최대 세션 수)를 쓴다. 명령과의 순서는 여전히 **한 곳에서 발급하는 전역 단조 증가 제출 번호**로 확정된다.
- **같은 tick 안의 명령 순서는 "게이트웨이 수신 순번"으로 확정한다.** 수신 시각(실수)이나 `client_sent_at`(클라이언트 값)으로 정렬하지 않는다. 순번은 전역 단조 증가 정수이고 큐에 넣을 때 부여된다.
- **`client_sent_at`은 로그·메트릭에만 쓴다.** 정렬·판정·지연 계산의 입력으로 쓰지 않는다. 왕복 지연은 **봇/클라이언트가 자기 시계로** 측정한다.

### 5. 큐가 가득 찰 때 — 거부한다 (드롭도 블로킹도 아니다)

| 큐 | 용량(이번 슬라이스) | 가득 찼을 때 |
|----|-------------------|-------------|
| 전역 명령 큐 | 4096 | `COMMAND_RESULT{REJECTED, SERVER_BUSY}` 즉시 응답. 연결은 유지 |
| 세션 in-flight(미응답 명령) | 64 | `COMMAND_RESULT{REJECTED, TOO_MANY_IN_FLIGHT}`. 연결은 유지 |
| 세션 송신 큐 | 256 | **연결을 닫는다**(close 1011, `SLOW_CONSUMER`) |

근거:

- **조용한 드롭을 하지 않는다.** 드롭하면 부하 테스트에서 손실이 관측되는데 그것이 네트워크인지 큐인지 DB인지 구분할 수 없다. 이 슬라이스의 핵심 측정(명령 1건 ↔ COMMAND_RESULT 1건)이 거부를 **관측 가능한 사건**으로 만들어 준다.
- **블로킹(백프레셔로 수신 태스크를 멈추기)을 하지 않는다.** 한 연결의 대기가 TCP 수신 창을 통해 그 클라이언트에게만 전달되는 것처럼 보이지만, 실제로는 tick이 한 번 늦어졌을 때 모든 연결의 수신 태스크가 동시에 멈추고 클라이언트는 **아무 신호도 받지 못한 채** 조용히 느려진다. 거부는 최소한 이유를 말해 준다.
- **송신 큐만 연결을 닫는다.** 느린 소비자는 시간이 지난다고 회복되지 않고, tick 루프가 그 연결을 기다리면 세계 전체가 한 클라이언트에 인질이 된다(`rust-authoritative-server` §6).
- 거부는 전부 `commands_rejected_total{reason_code}`로 센다. 반복 거부는 TECH §26의 anti-cheat telemetry로 이어지는 신호다.

**누가 거부 응답을 만드는가.** `SERVER_BUSY`·`TOO_MANY_IN_FLIGHT`·`MALFORMED_COMMAND`·`UNKNOWN_COMMAND_TYPE`·`SCHEMA_VERSION_UNSUPPORTED`는 **정의상 큐에 넣지 못했을 때** 나오므로 tick이 만들 수 없다(만들려면 큐에 넣어야 하는데 못 넣어서 거부한 것이다). **게이트웨이가 만든다.** envelope의 `tick`은 게이트웨이가 공유 원자값으로 읽는 현재 tick이고, **이 읽기는 상태 변경이 아니므로 I-13을 위반하지 않는다.** `DUPLICATE_COMMAND_ID`는 중복 제거가 `sim`에 있으므로 tick이 만든다.

**in-flight는 서버가 그 명령의 `COMMAND_RESULT`를 만든 시점에 해제한다** — 전달 확인이 아니다. 이 시점이 정해지지 않으면 AC-6(c)(`SLOW_CONSUMER`)의 도달 가능성이 달라진다: "클라이언트가 받은 시점에 해제"로 구현하면 읽지 않는 클라이언트는 in-flight 64에서 막혀 응답을 최대 128개밖에 못 만들고, **128 < 송신 큐 256이라 그 경로를 어떤 클라이언트 동작으로도 재현할 수 없다.**

**실측 결과 (2026-09-19, QA 라운드 1).** 31 연결 부하에서 압력이 걸린 곳은 명령 큐가 아니라 **송신 큐**였다: `send_queue_depth_max = 141 / 256`(**55 %**). 명령 큐는 아래 산수대로 거의 비어 있었고(왕복 p50 28.21 ms ≈ 이론 하한 25 ms + 전송, 즉 큐 대기가 사실상 없었다), tick 초과는 338,761 tick 중 **0건**이었다. **세 용량 중 먼저 재검토해야 할 것은 송신 큐 256이다** — p1에서 브로드캐스트(스냅샷·상태 변경)가 들어오면 여기가 먼저 찬다. 지금 올리지는 않는다: 올려야 할 근거는 "p1의 브로드캐스트가 얼마나 되는가"이지 "지금 55 %"가 아니다.

**용량 숫자는 잠정값이고, 이번 부하에서 `SERVER_BUSY`는 구조적으로 도달 불가능하다.** 세션 in-flight 상한이 64이므로 한 세션이 전역 큐에 동시에 올릴 수 있는 명령은 64개다. **30 세션 × 64 = 1920 < 4096** — 전역 큐는 이번 실행에서 절대 차지 않는다. 그래서 (a) `SERVER_BUSY` 경로는 **단위 테스트로만** 덮고 QA 리포트에 "부하 실행으로는 미도달(구조적)"이라고 적으며, (b) 용량 4096을 유지한다(64 세션까지의 여유). 이 산수를 여기 남기는 이유는, 첫 측정에서 `command_queue_depth` p99가 낮게 나오는 것이 "부하가 약해서"가 아니라 **"in-flight 상한이 먼저 걸려서"**임을 다음 사람이 알아야 하기 때문이다.

### 6. 프로토콜 위반 예산과 세션 내 중복 제거

- **프로토콜 위반**(파싱 불가, 바이너리 프레임, 크기 초과, `command_id`를 뽑을 수 없음): 세션당 위반 카운터를 올린다. `command_id`를 뽑을 수 있으면 `COMMAND_RESULT{REJECTED, MALFORMED_COMMAND}`를 보내고, 뽑을 수 없으면 보낼 수 없다(그래서 카운터가 유일한 신호다). **10초 창에서 8회를 넘으면 연결을 닫는다**(1002, `PROTOCOL_VIOLATION`). 프로토콜을 못 지키는 클라이언트는 같은 말을 반복해 들어도 고쳐지지 않는다.
- **세션 내 중복 제거**: 세션마다 최근 `command_id` 1024개를 기억하고, 재전송이면 `COMMAND_RESULT{REJECTED, DUPLICATE_COMMAND_ID}`로 답하며 **시뮬레이션에 두 번 넣지 않는다**.
  - **이것은 지속 멱등성이 아니다.** 연결이 끊기면 기억이 사라지고, 1024개를 넘어가면 오래된 것부터 잊는다. 따라서 "같은 명령을 재연결 후 다시 보내면 한 번만 적용된다"는 **보장되지 않으며**, 그래서 ADR-0005 §5가 재연결 시 재전송을 금지한다.
  - 지속 멱등성(`processed_commands` 테이블 + 명령·상태 변경 동일 트랜잭션)은 **상태를 바꾸는 첫 명령이 생기는 슬라이스(p1)의 필수 항목**이다. 이번 슬라이스에는 상태 변경이 없어 중복이 만들 수 있는 피해가 "PING_REPLY 2개"뿐이라 절반짜리로 둔다. 이 문단이 그 사실을 잊지 않기 위한 기록이다.

### 7. 관측

tick 루프와 큐에 대해 다음을 남긴다(ADR-0007 §8의 `/debug/stats`로 노출).

`tick`(현재), `start_tick`(이번 프로세스가 재개한 tick), `tick_total`, `tick_overrun_total`(**`run_tick()` 본문** 소요 > 50 ms), tick 본문 소요 분포(p50/p99/max), `tick_lag_seconds`, `command_queue_depth`(현재/최대), `commands_received_total{command_type}`, `commands_rejected_total{reason_code}`, `messages_enqueued_total{message_type}`, `messages_written_total{message_type}`, `ws_connections`, `protocol_violations_total`, `persist_backlog`.

**항진명제를 메트릭으로 두지 않는다(B-9·B-11).** 초안에는 검증처럼 보이지만 코드가 어떻게 틀려도 통과하는 항목이 둘 있었다.

| 버린 것 | 왜 아무것도 증명하지 않는가 | 대신 쓰는 것 |
|---------|---------------------------|-------------|
| `tick_skipped_total == 0` | tick을 건너뛰지 않기로 **설계했으므로** 상수 0을 반환하는 코드가 된다 | **`tick_total == tick − start_tick + 1`**. 루프가 어딘가에서 tick을 두 번 올리거나 건너뛰면 즉시 깨진다 |
| `ws_connections == opened − closed` | 세 값이 같은 증감 지점에서 나오면 언제나 참인 항등식이다 | `ws_connections`를 **세션 레지스트리의 실제 길이**로 계산한다. 그러면 같은 등식이 "레지스트리에서 지워졌는데 closed 카운터가 안 올랐다" 같은 진짜 버그를 잡는다 |

**송신 메시지 수(`messages_enqueued_total`/`messages_written_total`)는 손실 0을 서버 쪽에서 증명하기 위한 것이다(B-10).** 이 둘이 없으면 "봇이 3,600건 보내고 3,598건 받았다"에서 서버가 2건을 안 만든 것인지 소켓에서 샌 것인지 구분할 수 없다. `commands_received_total − messages_enqueued_total{COMMAND_RESULT} == 0`이 **서버 내부의 1:1 불변식**이 되고, `enqueued − written`이 곧 큐에 남은 양이다.

## 검토한 대안과 버린 이유

- **10 Hz**: 지금 싸지만 전투에서 반드시 올려야 하고, 그때 이미 저장된 이벤트의 시간 해상도가 묶여 있다.
- **가변 tick(프레임 기반)**: 결정성이 즉시 깨진다. 같은 입력이 같은 결과를 내지 않으면 재생·감사·속성 테스트가 전부 무너진다(원칙 9).
- **`tokio::time::sleep`으로 tick 주기 만들기**: 이 PC에서 50 ms가 61 ms가 된다(§2.1). async 서버라는 이유만으로 고르면 게임 로직 없이도 22 % 뒤처지는 서버를 p1 기준선으로 박게 된다.
- **`timeBeginPeriod`로 전역 타이머 해상도 올리기**: 워크스페이스가 `unsafe_code = "forbid"`라 별도 허용이 필요하고, **시스템 전역 설정을 게임 서버가 바꾼다**. `std::thread::sleep`이 같은 결과를 부작용 없이 준다.
- **재기동 시 tick을 0으로**: §2.3의 유실을 만든다. 그것도 **비결정적으로**.
- **실행마다 새 `world_id`**: `world_id`가 시드 상수라는 전제(AC-2, fixture)와 충돌한다.
- **`UNIQUE (world_id, tick, sequence)` 완화**: 마지막 방어선을 없애 문제를 감춘다(I-18).
- **전역 명령 큐 용량을 1024로 낮춰 `SERVER_BUSY`를 도달 가능하게**: 그 경로를 실행으로 보려고 정상 부하에서 거부가 나는 설정을 만드는 것은 앞뒤가 바뀌었다. 단위 테스트로 덮고 "구조적 미도달"을 리포트에 적는다.
- **tick 건너뛰기(catch-up으로 시간 맞추기)**: 게임 시간이 점프해 `(world_id, tick, sequence)`에 구멍이 생긴다. 재생과 결정성 비교가 불가능해진다.
- **`occurred_at`을 실제 시각에서 파생**: 게임 달력이 실제 시간 축에 올라타 "3827년"이 2026년의 다른 이름이 된다. HSE §35–36이 분리를 명시적으로 요구한다.
- **`occurred_at`을 저장하지 않고 조회 시 계산**: 계산 규칙이 바뀌면 과거 사건의 게임 시간이 소급해서 바뀐다(원칙 5 위반). 저장하고, 규칙 변경은 새 월드로 한다.
- **큐 가득 참 = 조용한 드롭**: 손실의 원인을 구분할 수 없게 만든다. 이 슬라이스는 손실을 측정하러 존재한다.
- **큐 가득 참 = 백프레셔(수신 태스크 블로킹)**: 한 tick의 지연이 전체 수신 경로를 멈추고 클라이언트는 아무 신호도 못 받는다.
- **명령 큐를 세션별로만 두기**: 전역 상한이 없어 연결 수 × 세션 큐만큼 메모리가 열린다. 전역 + 세션 두 겹으로 둔다.
- **지금 지속 멱등성 구현**: 상태를 바꾸는 명령이 하나도 없어 테스트할 대상이 없고, 테이블 설계는 경제 트랜잭션과 함께 정해야 한다.

## 결과

- 좋은 점: "핸들러는 상태를 바꾸지 않는다"가 크레이트 경계 + 큐 정책으로 실행 가능한 형태가 됐다. 게임 시간 축이 지금 고정되어, 이벤트를 저장하기 시작하는 바로 그 순간부터 의미가 일정하다. 거부가 전부 관측 가능해 부하 측정에서 손실과 거부를 구분할 수 있다.
- 감수할 점: 지속 초과 시 게임 시간이 뒤처진다. 세션 내 중복 제거는 진짜 멱등성이 아니어서, 읽지 않고 쓰는 사람에게 오해를 줄 수 있다(그래서 §6에 못박았다). 큐 용량 3종이 잠정값이라 첫 측정 후 조정이 필요하다.
- 다시 검토할 조건: (a) 전투가 들어와 20 Hz가 부족하다고 **측정**되면 tick 주기 재결정 + 새 월드, (b) `calendar_scale`을 designer가 확정할 때, (c) 상태를 바꾸는 첫 명령(p1)에서 지속 멱등성 ADR, (d) 첫 부하 측정에서 큐 용량·위반 예산 조정, (e) 단일 tick 루프가 CPU 한 코어를 채우면 병렬 시스템 분할(그 전에는 하지 않는다 — 원칙 8).
