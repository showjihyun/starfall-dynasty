# 0014. 역사 엔진 골격 — 크레이트, 입력, 테이블, 멱등, 전달

- 상태: **accepted** (history 검토 반영 2026-09-27 — `_workspace/p1-02-mining/01_history_review.md` §9.3 K1~K4·A1~A6 전부 수용. server 검토는 Phase 3 에서)
- 날짜: 2026-09-27
- 슬라이스: p1-02-mining
- 근거 기획안 절: HSE §4(Architecture), §9–12(Historical Event·중요도·스키마), §13(Lifecycle), §14–18(Evidence), §22(Truth 분리), §28–32(Event Bus·멱등·순서·결정성), §33–34(Rule Engine·Versioning), §70(최소 스키마), §88–91(MVP·10종·Vertical Slice·테스트), GDD §36 핵심 테스트
- 관련: ADR-0001 §2(history 크레이트 이름·의존 방향), ADR-0007(domain_events, append-only 트리거), ADR-0013(tick 배치 = outbox, 단일 작성자), CLAUDE.md 원칙 2·4·5·6·9

## 맥락

역사 엔진 코드는 아직 한 줄도 없다. p1-02 가 첫 규칙(`MINERAL_DISCOVERED`)을 넣으면서 다음이 동시에 정해진다 — 전부 나중에 바꾸기 비싸다.

1. 코드가 어디 살고 무엇에 의존하는가
2. 판정기가 **무엇을** 읽는가(메모리 이벤트 vs 커밋된 기록)
3. 어떤 테이블을 지금 만들고 어떤 것을 미루는가(원칙 6 과 "빈 테이블은 아무것도 증명하지 않는다" 사이)
4. 같은 사건이 두 번 기록되지 않는다는 것을 무엇이 보장하는가
5. 플레이어가 역사를 **어떻게 알게 되는가**(GDD §36 의 핵심 테스트)

## 결정

### 1. 크레이트 — `starfall-history` 는 순수 판정 코어다

- 위치 `server/crates/history`, 패키지 `starfall-history`(ADR-0001 §2 가 이름을 고정했다). 소유 history.
- **IO 없음**: `sqlx`·`tokio`·`axum`·`redis`·`rand`·`chrono` 금지, 시계 읽기 금지, `HashMap` 순회 결과를 출력 순서로 쓰지 않는다. `starfall-sim` 과 같은 규율이고 같은 검사(Cargo.toml 금지 목록)를 건다.
- 의존: **`starfall-contracts` 만.** ADR-0001 은 "history 는 domain 에만 의존"이라 적었지만 `starfall-domain` 은 만들어지지 않았고, 지금 도메인 이벤트의 타입은 계약 타입이다. `starfall-sim` 에 의존하지 않는다 — 역사는 시뮬레이션 내부가 아니라 **기록된 사실**을 읽는다.
- 모양: *판정 상태 + 도메인 이벤트 1건 → 역사 기록 0..n 건 + 새 판정 상태*. 결과에는 실제 시각이 없다(`recorded_at` 은 러너가 붙인다). 그래서 코어는 같은 입력열에 대해 **바이트 단위로 같은 결과**를 낸다.
- **라이브 `WorldState` 를 읽지 않는다.** 판정 입력은 도메인 이벤트(payload 포함) + 규칙 설정 + **history 자신의 앞선 판정 결과**뿐이다. 비동기 판정에서 소비 시점의 월드 상태는 이벤트 시점의 상태가 아니므로, 월드를 읽으면 같은 로그를 다른 시각에 재처리해 다른 답을 낸다(원칙 9). 판정에 필요한 "그 시점의 사실"은 전부 payload 에 실려야 한다 — 그래서 `MINERAL_MINED` 의 payload 는 history 가 요구한 필드를 필수로 가진다.
- **역행 입력을 거부한다.** 한 월드에 대해 직전 입력보다 `(tick, sequence)` 가 작거나 같은 이벤트가 오면 코어가 오류를 낸다. 러너의 `ORDER BY` 누락 같은 버그가 "틀린 발견자" 라는 영구 기록 대신 **정지**로 나타나게 한다.
- **판정 불가 이벤트는 건너뛰지 않는다(fail-stop).** 판정 대상 타입인데 역직렬화에 실패하거나 모르는 `schema_version` 이면 그 좌표에서 그 월드의 소비를 멈추고(커서 유지) `history_detector_halted` 를 올린다. 건너뛰면 뒤의 채굴이 잘못 "최초" 가 되고 그 오류는 영구 기록이 된다. 업캐스팅은 스키마 v2 가 생길 때.
- **결정적 ID.** `historical_event_id = UUIDv5(NS_HISTORY, "{world_id}|{event_type}|{dedupe_key}")`, `evidence_id = UUIDv5(NS_EVIDENCE, "{historical_event_id}|{evidence_type}")`. 네임스페이스는 고정값이다 — `NS_HISTORY = 29c482cc-234d-4876-a837-347b852f802d`, `NS_EVIDENCE = 503d3cb5-4cfe-4b52-9d4e-8acd439ad5c1`(바꾸면 모든 역사 id 가 바뀐다 — 바꾸지 않는다). 무작위 id 였다면 재구축이 id 를 바꾸고, 와이어의 중복 제거 키(스펙 I-65)와 p2 Claim 의 `about_event_id` 참조를 고아로 만든다. **결정성 비교에 id 를 포함한다.** UUIDv5 의 SHA-1 은 id 파생용이지 보안용이 아니다. `uuid` 크레이트의 `v5` feature 를 history 크레이트에서 켠다(sim 의 "해시 크레이트 금지" 는 sim 의 규칙이다 — sim 에는 여전히 들어가지 않는다).
- **DB 어댑터(러너)는 `starfall-persistence` 의 history 모듈**이다. 파일 소유는 history(ADR-0001 §4 의 "역사 테이블 마이그레이션 = history" 를 어댑터 파일까지 넓힌다). 크레이트 경계가 코어의 순수성을 컴파일러로 강제하고, 어댑터는 이미 sqlx 를 가진 크레이트에 산다.

### 2. 입력 — 커밋된 `domain_events` 를 `(tick, sequence)` 순으로, 커서 뒤부터

- 러너는 **DB 에 커밋된** `domain_events` 를 읽는다. tick 루프의 메모리 채널에서 받지 않는다.
  - 이유: 크래시로 사라진 꼬리(ADR-0013 §6)는 **일어나지 않은 일**이 된다. 메모리에서 판정하면 사라진 사실에 대한 역사가 남을 수 있다 — "기록이 없는 발견"이다. 커밋된 것만 읽으면 **역사의 모든 근거가 DB 에 존재한다**는 것이 구조로 보장된다.
- 순서는 `(tick, sequence)` 오름차순, 시작점은 커서 `history_cursor(world_id, consumer) → (tick, sequence)`. **워터마크**: `tick <= worlds.last_tick` 인 행만 읽는다 — 아래 전제를 코드에 명시하는 조건이다.
- **전제**: 영속화가 단일 작성자·tick 오름차순 커밋이다(ADR-0013 §6). 그래서 커서 뒤에 옛 tick 이 나중에 끼어드는 일이 없다. 이 전제가 깨지면(영속화 병렬화) 이 절을 다시 연다.
- 깨우기: 영속화 태스크가 커밋마다 "tick T 커밋" 을 러너에 알린다(채널). 알림이 유실돼도 러너는 **1 초 폴링**으로 따라온다 — 알림은 지연을 줄이는 장치이지 정확성의 근거가 아니다.
- 판정 대상 타입은 규칙이 선언한다. 이번엔 `MINERAL_MINED` 만. 나머지 타입은 읽고 커서만 전진한다(Level 0 — 원칙 4).

### 3. 테이블 — 이번에 만드는 것과 미루는 것

| 테이블 | 이번 | 이유 |
|---|---|---|
| `historical_events` | **만든다**, append-only 트리거 | 이 슬라이스의 산출물 |
| `historical_event_sources(source_event_id, detector_rule) PK` | **만든다**, append-only 트리거 | 멱등 방어 (§4) + "이 역사의 근거는 어느 사실인가" 역조회. 트리거가 없으면 멱등 둘째 겹이 DELETE 한 줄로 조용히 사라진다 |
| `evidence` | **만든다**, append-only 트리거 | HSE §90 의 "Evidence generated". 발견 1건마다 자동 증거 1건 |
| `history_cursor` | **만든다 — 가변** | §2. 기록이 아니라 진행 위치다. 트리거를 걸지 않는 유일한 역사 표이고 그 이유를 마이그레이션 주석에 적는다 |
| `historical_event_participants` / `_objects` 정규화 | 미룬다 → 행의 `participants`·`objects` JSONB | 읽는 쪽(Biography·검색, p2)이 없다. JSONB 에서 **파생 가능**하므로 나중에 채워도 역사를 고치지 않는다 |
| `claims` / `claim_evidence` / `interpretations` | 미룬다 (p2) | **생산자가 없다.** 이번 슬라이스에 주장을 쓰는 플레이어 행동이 없다. 빈 테이블은 아무것도 증명하지 않는다(ADR-0007 이 `historical_events` 를 미룬 논리) |
| `historical_event_relations` | 미룬다 | 인과 연결 규칙이 없다(첫 규칙은 단일 근거) |
| `chronicle_entries` 등 프로젝션 | 미룬다 (p2) | Chronicle 은 p2. 이번 전달은 §6 |

**원칙 6(Fact ≠ Claim ≠ Interpretation)은 테이블 수가 아니라 구조로 지킨다:**

- `historical_events` 에는 **자연어 서사 열이 없다.** 제목·문장은 표현 계층(클라이언트 로컬라이즈 키 + 파라미터)이 만든다. 원칙 2 도 같은 자리에서 지켜진다 — LLM 이 끼어들 텍스트 열이 사실 테이블에 없다.
- `fact_status` 는 이번엔 `CONFIRMED` 하나뿐이고 DB `CHECK (fact_status = 'CONFIRMED')` 로 잠근다. 값을 늘리는 것 자체가 마이그레이션 + ADR 검토 대상이 된다. 해석 상태 열을 두지 않는다(HSE §13 — 사실 상태와 해석 상태를 한 열에 섞지 않는다).
- **사실 테이블의 쓰기 경로는 하나다** — 러너가 `domain_events` 에서만 쓴다. 게이트웨이 명령·REST 어디에도 역사 테이블 쓰기가 없다. 나중의 `claims` 는 사실을 가리키고 사실은 주장을 가리키지 않으므로, p2 의 claims 는 기존 테이블을 ALTER 하지 않는 순수 추가 마이그레이션이다.
- `evidence.authenticity_status` 는 시스템 내부 진실이고 와이어에 싣지 않는다.
- `evidence` 도 이번 슬라이스의 유일한 모양(`authenticity_status = 'VERIFIED'`·`creation_method = 'automatic'`·`derived_from_evidence_ids = '{}'`)으로 CHECK 잠금이다(H2, 2026-09-28). `fact_status` 와 같은 논리 — p2 에서 편집·위조·파생 증거가 들어올 때 이 CHECK 를 푸는 것이 **마이그레이션 + ADR 검토 대상**이 된다. 잠금이 없으면 첫 위조 증거가 검토 없이 원본과 같은 표에 섞인다.

### 4. 멱등 — 세 겹

같은 도메인 이벤트를 몇 번 처리해도, 러너가 몇 번 재시작해도 역사는 하나다.

1. **커서**: 판정 결과와 커서 전진이 **한 트랜잭션**이다. 커밋 전에 죽으면 둘 다 없고, 다시 읽어 같은 결과를 낸다(코어가 결정적이므로).
2. **근거 유일성**: `historical_event_sources` PK `(source_event_id, detector_rule)`. 같은 근거·같은 규칙에서 두 번째 행은 들어갈 수 없다. **`detector_rule` 의 값은 그 행을 만든 규칙의 `rule_version` 문자열**(예: `mineral-discovery@1`)이다 — 2026-09-30 architect 판정. 마이그레이션 0003 의 주석("`rule_id`(버전 없이)")은 이 판정과 다르고, 0003 은 증거 DB 에 적용돼 동결이라 주석을 고칠 수 없다 — **정본은 이 절이다, 마이그레이션 주석이 아니다.** 판정 이유: 러너는 처음부터 `rule_version` 을 써 왔고 증거 DB 에 이미 그 값의 행이 51 개(32 월드) 있다. 값을 바꾸면 같은 열에 두 철자가 공존하고(원칙 5 로 옛 행은 못 고친다), 옛 월드에서 재배달하면 PK 가 겹치지 않아 **근거 행이 두 벌** 생긴다 — 멱등 둘째 겹이 조용히 무너진다. 두 철자의 의미 차이(규칙 @2 가 같은 근거를 다시 근거로 쓸 수 있는가)는 셋째 겹(`dedupe_key` UNIQUE)이 이미 막으므로 실익이 없다.
3. **의미 유일성**: `historical_events` 의 `dedupe_key` + `UNIQUE (world_id, event_type, dedupe_key)`, 그리고 그 키에서 파생된 결정적 PK(§1). 규칙이 키를 정의한다 — `MINERAL_DISCOVERED` 는 `"{star_system_id}/{mineral_id}"`. 키에 `rule_version` 을 넣지 않는다 — `@2` 가 같은 광물을 "다시 발견" 하지 않게. **근거가 다른 두 채굴이 각각 "최초 발견"으로 판정되는 러너 버그(판정 상태 적재 실패 등)도 DB 가 막는다.** 2 는 같은 사실의 중복을, 3 은 서로 다른 사실이 같은 역사를 주장하는 것을 막는다.

**재처리는 조용하고, 다른 근거의 충돌은 시끄럽다** — 2·3 의 제약에 걸린 쓰기(`ON CONFLICT DO NOTHING` 이 0 행)는 두 경우로 나눈다. 러너는 기존 행을 다시 읽어 **지금 쓰려던 기록과 내용 전체를 비교**한다(`recorded_at` 만 제외 — `source_event_ids`·`rule_version`·participants·payload 전부. id 가 결정적이므로 같은 코드·같은 근거면 바이트가 같아야 한다).
- **같다 → 재처리**(재시작·재배달·커서 되감기). 정상이다. 쓰지 않고 커서만 전진하며 카운터를 올리지 않는다. 증거 행도 같은 규칙.
- **다르다 → 충돌**. 근거가 다르면 코어의 판정 상태와 DB 가 어긋난 것이고, 근거가 같은데 내용이 다르면 **같은 `rule_version` 인데 코드가 다른 출력을 낸 것**(golden 이 놓친 규칙 변경)이다. 둘 다 **버그 신호**다(ADR-0007 §4 와 같은 태도): 트랜잭션을 롤백하고, 에러 로그 + `history_conflicts_total` +1 을 남기고, **러너만 멈춘다**(커서는 그 이벤트 앞). 역사는 늦어도 되지만(§7) 틀리면 안 된다.
*(개정 2026-09-27 — history 의 AC-11(h) 구현 판별 기준 확인. 초안은 "2·3 의 위반은 버그 신호" 한 문장이라 재배달까지 정지로 읽혔다. 비교 대상을 `source_event_ids` 만이 아니라 내용 전체로 넓힌 것은 architect 추가 — 근거만 보면 "같은 근거·다른 출력" 이 재처리로 조용히 통과한다.)*

### 5. 결정성과 규칙 버전

- 모든 역사 기록(과 증거)은 `rule_version` 을 가진다. 형식 `"{규칙 이름}@{정수}"`, 첫 규칙 `mineral-discovery@1`.
- 규칙을 바꾸면 버전을 올린다. **과거 기록을 새 규칙으로 다시 계산하지 않는다**(원칙 5, 역사 왜곡).
- 규칙 설정은 **규칙 하나당 파일 하나**: `data/history/rules/mineral-discovery.json`(designer 소유, 스키마 `contracts/data/significance-rule.schema.json`). 기동 시 적재·검증하고 적재한 `rule_version` 을 로그에 남긴다. 코어는 파일을 읽지 않는다 — 조립 바이너리가 읽어 값으로 넘긴다.
- **버전을 올리지 않고 값만 바꾸는 사고를 막는다**: golden 테스트가 `rule_version` 에 (a) 규칙 파일의 정규화 내용 해시와 (b) 고정 입력열에 대한 코어 출력을 묶는다(`server/crates/history/tests/data/golden/`, `STARFALL_REPLAY_BLESS=1` 일 때만 재생성 — 이동 golden 과 같은 규율). 값·코드가 바뀌었는데 버전이 같으면 실패한다.
- 판정 입력에 **데이터 표의 다른 값(희귀도 등)을 넣지 않는다.** 데이터 변경 후 재구축하면 결정성이 깨지는 두 번째 입력이 되기 때문이다. 필요해지면 그 값을 도메인 이벤트 payload 에 싣고 `@2` 로 올린다.
- 판정 상태(이번엔 "이 월드·성계에서 발견된 광물 집합")는 **기동 시 `historical_events` 에서 재구축**한다. 재구축과 "빈 상태에서 `domain_events` 전체 재생"은 같은 결과여야 하고, 이것이 결정성 테스트다: **새 월드의 `domain_events` 를 빈 판정 상태에서 재생하면 같은 역사 집합**(`recorded_at` 만 제외한 내용 비교 — **id 를 포함한다**, §1 결정적 ID).
- 동시성의 결정 규칙: 같은 tick 에 두 actor 가 같은 광물을 처음 캔다면 **`sequence` 가 작은 쪽이 단독 발견자**다. `sequence` 는 제출 순번에서 결정적으로 나온다(ADR-0006 §4). 공동 발견은 이번 규칙에 없다.

### 6. 전달 — 플레이어가 역사를 알게 되는 경로

- 서버 메시지 **`HISTORICAL_EVENT_NOTICE`** 가 역사 기록 1건을 싣는다. 두 가지 경우에 보낸다.
  - **LIVE**: 러너의 트랜잭션이 **커밋된 뒤**, 그 기록을 볼 수 있는 모든 열린 세션에.
  - **BACKFILL**: 세션이 열릴 때(`SESSION_READY` 뒤), 그 세션이 볼 수 있는 그 월드의 기존 기록 전부를 `tick` 오름차순으로.
- **커밋 뒤에만 보낸다.** 커밋 전에 알리면 크래시가 "모두가 봤는데 기록이 없는 역사"를 만든다.
- 가시성: `MINERAL_DISCOVERED` 는 `PUBLIC`. 이번 슬라이스의 필터는 "PUBLIC 이면 그 월드의 모든 세션"뿐이다. 다른 가시성 값은 계약에 자리가 있지만 생산하지 않는다.
- BACKFILL 규모: 이번 슬라이스의 역사 기록은 월드당 **(성계 수 × 광물 수) = 1 × 4** 가 상한이다. **월드의 PUBLIC 역사 기록이 32 건을 넘는 슬라이스**에서는 BACKFILL 을 조회 API(HSE §48)로 바꾼다 — 그때가 Chronicle(p2)이다.
  - *(개정 — server 추가 3)* 초안의 64 는 세션 송신 큐 용량(`SEND_QUEUE_CAPACITY` 64, ADR-0011 §5)과 같았다. 세션 시작에 `SESSION_READY` + `INVENTORY_STATE` + `DEPOSIT_FIELD_STATE` + BACKFILL 64 건이 한꺼번에 들어가면 큐를 넘고 **새 접속이 전부 `SLOW_CONSUMER` 로 끊긴다.** 트리거는 큐 용량의 절반 이하여야 한다 — 32 는 세션 시작 메시지 3 건과 그 사이 스냅샷·결과가 들어갈 여유를 남긴다. **큐 용량을 줄이는 변경은 이 트리거를 함께 내린다.**
- 게이트웨이는 게임 규칙을 두지 않는다(ADR-0001 §2). **러너가 기록(`MINERAL_DISCOVERED`)을 만들어 채널로 넘기고, 게이트웨이가 그것을 `HISTORICAL_EVENT_NOTICE` 로 포장해 나른다** — 송신 시점 tick·`message_id`·`delivery` 는 그쪽만 안다. 그래서 레지스트리의 NOTICE 생산자는 `server` 이고 `MINERAL_DISCOVERED` 생산자는 `history` 다(T0 합의, 2026-09-27 개정 — 생산자를 history 로 두면 커버리지 스크립트가 history 경로에서 NOTICE 를 찾게 되고, 그것을 맞추려면 이름만 등장하는 거짓 생산 코드가 생긴다). 게이트웨이는 **라우팅·포장·BACKFILL 목록 보관**만 한다. 가시성 판정은 러너 쪽이 붙여 보낸다.
- **누락 틈을 만들지 않는다.** "목록에 추가 + 열린 세션에 LIVE" 와 "세션 열림 → BACKFILL 송신" 을 **같은 직렬화 문맥**(게이트웨이의 한 태스크 또는 한 잠금)에서 처리한다. 둘이 따로 돌면 커밋 직후 열린 세션이 LIVE 도 BACKFILL 도 못 받는 순간이 생긴다. 반대 방향(둘 다 받음)은 허용하고 클라이언트가 `historical_event_id` 로 거른다(스펙 I-65).
- **재기동 시 목록 적재 주체는 러너다.** 러너가 기동 시 그 월드의 PUBLIC 기록을 DB 에서 읽어 게이트웨이에 넘긴 **뒤에** 게이트웨이가 연결을 받는다(ADR-0013 §7 기동 순서에 한 단계를 더한다).
- 발견자의 표시 이름은 이번 슬라이스에 **없다** — 계정·이름 체계가 없다(ADR-0008 의 개발 토큰은 주체 UUID 뿐). 클라이언트가 `actor_id` 에서 결정적 짧은 표지(예: `Pilot-3f9a`)를 만든다. 표현이지 사실이 아니며 DB 에 저장하지 않는다. 이름 체계가 생기면 NOTICE 조립 시 붙인다(로그아웃한 actor 도 조회 가능해야 한다).

### 7. 지연과 일관성

- 역사는 결과적 일관성이다(프로젝션처럼 몇 초 늦어도 된다). 인벤토리는 그렇지 않다(ADR-0013).
- 예산: 정상 부하에서 **`MINERAL_MINED` 커밋 → `HISTORICAL_EVENT_NOTICE(LIVE)` 수신 p95 ≤ 1 초(목표, 측정)**, **5 초 초과는 실패 경계**. 1 초는 designer 의 "두 박자" 배너(채굴 결과 → 곧이어 역사)가 성립하는 값이다. 러너가 멈춰서(§4) 영원히 오지 않는 것은 실패다.

## 검토한 대안과 버린 이유

- **sim 이 "최초 발견" 도메인 이벤트를 직접 발행**: 중요도 판정이 시뮬레이션에 들어간다. 원칙 4 의 경계(도메인 이벤트 ≠ 역사)가 코드에서 사라지고, 규칙 버전을 시뮬레이션 버전과 분리할 수 없다.
- **메모리 채널에서 판정**: §2. 사라진 사실 위의 역사.
- **영속화 트랜잭션 안에서 동기 판정**: tick 배치 커밋이 역사 판정의 지연·실패를 먹는다. 역사 규칙의 버그가 인벤토리 기록을 막는다(§4 의 "역사는 멈춰도 경제는 돈다" 가 깨진다).
- **HSE §70 최소 스키마 전부를 지금**: §3. 생산자·소비자가 없는 테이블은 모양이 틀려도 드러나지 않고, 틀린 모양은 첫 행이 들어간 뒤에 못 고친다.
- **조회 REST API(`GET /history/events`)로 전달**: 게이트웨이가 DB 를 읽어야 한다(현재 persistence 비의존). 기록 수가 광물 수로 묶이는 동안은 BACKFILL 이 더 싸다. 64 건 트리거로 전환한다.
- **범용 규칙 엔진/DSL**: 규칙 1 개. 명시적 Rust 함수로 시작한다(HSE §33, historical-engine 스킬 §2).

## 결과

- 좋은 점: 역사의 모든 근거가 커밋된 사실이다. 같은 광물의 발견이 한 월드에 두 번 생기는 것을 코드와 DB 가 각각 막는다. 코어가 순수해 재생 결정성 테스트가 DB 없이 돈다. 사실 테이블에 서사 텍스트가 들어갈 자리가 없다.
- 감수할 점: 역사는 커밋 뒤 비동기라 채굴 직후 1 초 안팎 늦게 알려진다. participants 를 JSONB 로 두어 "A 가 참여한 모든 사건" 질의가 지금은 느리다(p2 에서 정규화). 러너 정지(§4) 동안 역사가 쌓이지 않는다 — 경제는 계속 돈다.
- 다시 검토할 조건: (a) 규칙이 5 개를 넘거나 집계(Correlation Window) 규칙이 생길 때 코어의 모양(이벤트 1건 → 결과)을 재검토, (b) PUBLIC 기록 64 건 초과 → 조회 API, (c) 영속화 병렬화 → §2 전제, (d) 역사 처리 지연이 예산(§7)을 넘는 것이 측정될 때 러너 병렬화(월드 단위).
