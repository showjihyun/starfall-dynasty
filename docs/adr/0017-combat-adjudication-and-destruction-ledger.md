# 0017. 전투 판정과 파괴의 원장 — 조준 원뿔 히트스캔, 메모리 내구도, 파괴는 기존 장부의 새 항

- 상태: **proposed** (2026-10-10 초안 — architect5. designer5 수치·손실 규칙, history5 역사 판단, server 검토 전. p1-03 r1 동결 중이라 계약·코드는 동결 해제 뒤)
- 날짜: 2026-10-10
- 슬라이스: p1-05-basic-combat
- 근거 기획안 절: GDD §6.1(Scout S-01 — Weapon 1, Shield 100), GDD §10(전투 — 초기 1인 함선), GDD §16(죽음은 역사적 사건이 될 수 있다), GDD §33(서버 판정 8단계), GDD §36(MVP-1 "기본 전투", 핵심 테스트), GDD §43(PvP 압살 — 위험 계층), TECH §26–27(서버 권위·복사 방지), HSE §84(PLAYER_DIED), HSE §89(MVP 10종의 `SHIP_DESTROYED`·`PLAYER_DIED`)
- 관련: ADR-0006 §4(제출 순번)·§4a(메시지 id 흐름), ADR-0007 §1(기록 범위 표), ADR-0010 §3(금지 함수)·§3.1(golden)·§4(스폰), ADR-0011 §1(스냅샷)·§6(잔류)·§7(함선 비영속), ADR-0012 §5·§7(타 함선 200 ms 지연 — "명중 판정을 클라 화면으로 하면 안 된다"), ADR-0013 전부(장부·배치·정지), ADR-0014 §1·§6(payload 완결·BACKFILL 32), ADR-0016(크레딧)

## 맥락

p1-05 는 p1 의 마지막 핵심 행동 "기본 전투" 다. 다섯 가지가 함께 정해지고, 전부 나중에 바꾸기 비싸다.

1. **명중을 누가 어떻게 판정하는가.** 원칙 1 은 서버라고 답한다. 문제는 *어떤 상태로* 판정하는가다. ADR-0012 §5 에 따르면 클라이언트는 타 함선을 `remote_interp_delay_ms` 200 ms **과거**로 그린다. 최고 속도 140 m/s 에서 28 m 어긋나고, 이 값은 `hull_radius_m` 12 m 의 두 배가 넘는다. ADR-0012 §7 은 이미 "명중 판정을 클라 화면으로 하면 안 된다" 고 경고했다.
2. **내구도는 어디 사는가.** 함선은 영속하지 않는다(ADR-0011 §7). 인벤토리와 지갑은 actor 소유의 영속 상태다(ADR-0013 §1, ADR-0016 §2).
3. **파괴가 경제를 바꾸는가, 바꾼다면 어떤 장부로.** ADR-0013 §1 은 "함선 화물칸은 함선 영속화 슬라이스에서 이 결정을 다시 연다" 고 미뤄 두었다. 파괴로 화물을 잃게 하면 그 질문이 지금 온다.
4. **함선 없는 세션.** 파괴 뒤 재생성까지 그 actor 의 세션에는 함선이 없다. p1-01 I-29("열린 세션은 정확히 1척을 조종한다")는 그런 상태를 허용하지 않는다.
5. **전투 상태를 와이어로 어떻게 보내는가.** `WORLD_SNAPSHOT` 에 필드를 더하면 이동 golden(`server/crates/sim/tests/data/replay/snapshots.jsonl` — 와이어 payload 그대로다, 2026-10-10 확인)의 바이트가 바뀐다. ADR-0010 §3.1 은 그 변화를 "물리를 건드렸다" 는 신호로 정했다.

## 결정

### 1. 명중 판정 — 표적 지정 + 기수 조준 원뿔, 서버 상태 히트스캔. 수락이면 명중이다

- 명령은 **`FIRE_WEAPON{target_ship_id}`** 하나다. 위치·조준 벡터·피해·명중 여부·시각은 **어휘에 없다**(`additionalProperties: false` → `MALFORMED_COMMAND`).
- 서버는 **tick 시작 시점(이번 tick 적분 전)의 `f64` 상태**로 판정한다. 채굴·판매와 같은 시점이다(p1-02 §4.2, p1-03 §4.2).
- **원뿔은 삼각함수 없이 정의한다**(ADR-0010 §3 금지 목록). 사수 전방 단위벡터 `f`(자세 `q` 로 `(0,0,1)` 회전 — 이동 적분이 이미 쓰는 연산), 상대 벡터 `D = p_target − p_shooter` 일 때:
  - `along = f·D`. 조건은 `0 < along ≤ range_m`.
  - `perp² = |D|² − along²`. 조건은 `perp² ≤ (hull_radius_m(target) + cone_slope × along)²`.
  - 덧셈·곱셈·비교만 쓴다. `sqrt` 도 쓰지 않는다. 경계는 포함이다(`≤`).
  - 이 식은 꼭짓점이 사수 쪽으로 `hull_radius / cone_slope` 만큼 물러난 원뿔이다. 가까운 거리에서는 선체 반경이 지배하고, 먼 거리에서는 기울기가 지배한다.
- **수락 = 명중.** 빗나감이라는 결과가 없고 무작위도 없다. 사거리나 원뿔 조건을 못 지키면 **거부**다. 거부는 아무것도 바꾸지 않는다(쿨다운 포함 — p1-03 I-79 와 같은 규칙).
- **원뿔이 지연을 흡수한다.** 설계 제약은 이렇다: designer 가 정하는 최소 교전 거리 `r_min` 에서 `hull_radius + cone_slope × r_min ≥ 140 m/s × (remote_interp_delay_ms + 왕복 예산) + 여유`. 이 부등식이 깨지면 정직하게 조준한 플레이어가 지연 때문에 거부된다. 기동 검산이 아니라 **디자인 문서의 유도식**으로 둔다. 판정 입력이 지연이 아니라 데이터 상수라서 기동 시 확인할 수 없다.
- **같은 tick 의 사격은 제출 순번 순이다**(ADR-0006 §4, p1-02 I-71). 먼저 처리된 사격이 상대를 파괴하면, 뒤에 처리되는 그 상대의 사격은 사수 함선이 없어 거부된다. 동시 격추는 없다. 순서 의존성은 판매·발견에서 이미 받아들인 성질이다.

### 2. 내구도는 함선의 메모리 상태다 — 영속하지 않는다

- `hull_points` 는 함선 엔티티에 산다. 함선과 같이 생기고 같이 사라진다. 재기동이 함선을 없애므로(ADR-0011 §7) 내구도도 함께 사라진다.
- **그래서 내구도는 DB 상태 행이 아니다.** 비교 후 쓰기 대상이 아니고, 새 테이블도 없다. 대신 **원장은 있다**: `SHIP_DAMAGED` 의 `hull_before`/`hull_after` 연쇄로 "왜 지금 그 숫자인가" 를 설명할 수 있어야 한다(§3, 스펙 I-9x 항등식).
- 회복을 넣는다면 광맥처럼 **게으른 닫힌 식**(월드 tick 배수, 상한 = 최대 내구도)으로만 넣고, 이벤트를 만들지 않는다. 넣을지는 designer 가 정한다. 넣으면 `hull_before` 는 회복을 적용한 뒤의 값이다(ADR-0013 §1 의 광맥 규칙과 같다).

### 3. 기록 — 수락된 사격 1건 = `SHIP_DAMAGED` 1건 = 장부 1행

- `FIRE_WEAPON` 은 **상태 변경 명령**이다. 수락되면 그 tick 의 배치에 `processed_commands(…, 'FIRE_WEAPON', tick)` 이 들어간다. 같은 표, 같은 PK, 같은 월드 범위 기억이다(ADR-0013 §3, ADR-0016 §1). 채굴이나 판매로 수락된 `command_id` 를 사격으로 다시 보내면 `DUPLICATE_COMMAND_ID` 다.
  - 이유: 내구도는 메모리 상태지만, 수락된 사격은 **기록되는 사실**(`SHIP_DAMAGED`)을 만든다. 그리고 파괴로 이어지면 **영속 상태**(인벤토리)를 바꾼다. 명령 종류마다 장부 규칙이 다르면 "어떤 명령이 장부에 남는가" 가 두 번째 규칙이 된다. 규칙은 하나로 둔다: **수락 ⇔ 장부 행 ⇔ 그 명령을 `causation_id` 로 가진 도메인 이벤트 1건**.
  - 비용: 쿨다운이 1 s 라면 교전 중인 actor 하나가 초당 장부 1행을 만든다. ADR-0013 재검토 조건 (b)(100 만 행)가 채굴보다 일찍 온다(30명 상시 교전 ≈ 9 시간). 조건은 그대로 두고, 첫 부하 측정에서 행 증가율을 기록한다.
- `RECORDING_BACKLOG` 게이트(ADR-0013 §6)를 `FIRE_WEAPON` 에도 건다. DB 가 멈추면 전투도 1 초 안에 멈춘다. 받아들인다: 크래시가 "명중은 했는데 기록은 없는" 파괴를 만들면 안 된다.
- **`SHIP_DAMAGED`**(신규 도메인 이벤트, Level 0)는 사수·표적의 actor·ship, 표적의 presence, 위치·거리, 무기, 피해, 내구도 before/after/max, 파괴 여부를 **전부** 싣는다. 역사 판정은 월드를 읽지 않으므로(ADR-0014 §1) 필요한 사실은 전부 payload 에 있어야 한다. 정본 필드 목록은 스펙 §5 와 history5 의 검토가 정한다.
- 거부된 사격은 기록하지 않는다(ADR-0007 §1).

### 4. 파괴 — 같은 tick 의 세 사실, 그리고 짝 불변식은 그대로

`hull_after = 0` 이 되는 사격이 수락되면 **같은 tick 안에서** 아래 순서로 발행한다.

1. `SHIP_DAMAGED{…, hull_after: 0, destroyed: true}` — `causation_id` 는 `command_id` 다.
2. `CARGO_LOST`(신규, 경제 원장 — **손실 규칙이 "광물 소멸" 일 때만**, 잃은 것이 없으면 내지 않는다) — 광물별 `quantity_before/after_kg`. `causation_id` 는 1 의 `event_id` 다. 인벤토리 행은 비교 후 쓰기로 0 이 된다(지우지 않는다 — ADR-0016 §2).
3. `SHIP_DESPAWNED{despawn_reason: DESTROYED}` — 계약이 처음부터 이 값을 예고했다("destruction … add values later"). 같은 `schema_version` 에 값을 더하는 호환 변경이다. `causation_id` 는 1 의 `event_id` 다. 그래서 **`SHIP_SPAWNED`/`SHIP_DESPAWNED` 가 함선당 1쌍이라는 불변식(p1-01 I-41)은 그대로 유지된다.**

- **이름**: 역사 이벤트 `SHIP_DESTROYED`(HSE §89)와 이름이 겹치지 않게, 도메인 사실은 `SHIP_DESPAWNED{DESTROYED}` 로 둔다. p1-02 에서 `MINERAL_MINED`(도메인)가 `MINERAL_DISCOVERED`(역사)로 승격되던 구조와 같다.
- **화물칸 결정(ADR-0013 §1 의 미룬 질문)**: 소유자는 계속 **actor** 다. 테이블·키·장부를 바꾸지 않는다. 바뀌는 것은 의미 하나다. **actor 의 광물 인벤토리 전부는 그 actor 의 함선에 실려 있다고 본다.** 함선 화물칸을 별도 엔티티로 만들지 않는다. 함선 영속화나 함선 둘 이상(창고·정거장 보관)이 생기면 그때 다시 연다.
- **크레딧은 잃지 않는다**(추천 — designer5 확정 대기). 지갑은 "은행" 이다. 그래서 화폐 총량 항등식(ADR-0016)은 바뀌지 않는다.
- **잔해 회수(대안 B)를 택하면** 이 절이 바뀐다. `wrecks` 상태 표(마이그레이션 0005, 비교 후 쓰기, 게으른 만료 — 행을 지우지 않는다), `SALVAGE_WRECK` 명령, `CARGO_LOST` 의 목적지 항이 생기고, 정지 경로 표에 행이 더해진다. 스펙 §9 의 사용자 질문이다.

### 5. 함선 없는 세션 — p1-01 I-29 를 개정한다

- 파괴부터 재생성까지 그 actor 의 열린 세션은 **함선 없음(`AWAITING_RESPAWN`)** 상태다. `WORLD_SNAPSHOT.controlled_ship_id = null` 이다. 계약은 처음부터 null 을 허용했으므로 계약 변경은 없다.
- I-29 는 이렇게 바뀐다: *열린 세션은 0 또는 1 척을 조종한다. 0 척인 경우는 `AWAITING_RESPAWN` 하나뿐이다. `ACTIVE` 함선은 정확히 1 개의 열린 세션이 조종한다.* 둘째 문장은 바뀌지 않는다. 조종 세션 없는 `ACTIVE` 함선은 여전히 존재할 수 없다.
- 함선이 필요한 명령(`SET_SHIP_CONTROL`·`MINE_RESOURCE`·`SELL_MINERAL`·`FIRE_WEAPON`)은 그 동안 **`NO_ACTIVE_SHIP`**(신규)으로 거부된다. p1-02 §4.2 는 이 사유를 "구조적으로 도달할 수 없다" 는 이유로 만들지 않았다. 이제는 도달할 수 있으므로 만든다. 같은 원리를 반대 방향으로 적용한 것이다.
- **재생성은 자동이고 결정적이다.** 파괴 tick + `respawn_delay_ticks` 에 sim 이 새 `ship_id` 로 스폰한다. 위치는 ADR-0010 §4 의 스폰 링 규칙 그대로다. `SHIP_SPAWNED` 의 `causation_id` 는 그 함선의 `SHIP_DESPAWNED{DESTROYED}.event_id` 다. 지금 계약은 "같은 tick 의 `SESSION_OPENED`" 로 좁혀 두었으므로 **의미 변경이고, `SHIP_SPAWNED` schema_version 2**(+ `spawn_reason` 필드)로 올린다. v1 → v2 업캐스터는 `spawn_reason = SESSION_START` 를 채운다.
- **대기 중에 세션이 닫히면** 재생성 타이머를 버린다. 다음 접속은 "함선 없음 → 스폰"(I-29 첫 경우)이다. 잔류할 함선이 없으므로 잔류도 없다. 그래서 "죽은 채로 끊고 다시 들어와 대기를 건너뛴다" 가 가능하다. 남은 대기 시간을 actor 에 붙여 보존할지는 designer 가 정한다(스펙 열린 질문).
- **정원(I-44)**: 재생성 대기 중인 actor 는 정원을 하나 **예약**한 것으로 센다. 세지 않으면 대기 중에 다른 접속이 자리를 채우고, 재생성이 64척 상한을 넘는다. 그러면 계약을 어긴 스냅샷이 나간다(ADR-0011 §1 2차 방어가 발동하는 서버 버그다). 입장 판정식은 `함선 수 + 대기 수 ≥ 정원 그리고 이 actor 가 함선도 대기도 없다` 다.

### 6. 전투 상태는 별도 메시지다 — `WORLD_SNAPSHOT` 은 바꾸지 않는다

- `HULL_STATE`(월드 전 함선의 내구도, 세션 시작 + 바뀐 tick 마다 브로드캐스트)와 `SHOT_REPORT`(명중 1건, 월드 브로드캐스트 — 제3자 VFX·킬 피드용)를 둔다. `WORLD_SNAPSHOT.ShipState` 에 내구도를 더하지 않는다.
  - 이유: golden 이 와이어 payload 를 그대로 담고 있다(맥락 5). 필드를 더하면 물리가 같아도 golden 이 바뀌고, "golden 이 바뀌면 물리를 건드렸다" 는 신호가 전송 변경 때문에 거짓으로 울린다. ADR-0006 §4a 가 같은 이유로 id 흐름을 나눴다.
  - 대역폭: 내구도는 바뀔 때만 보낸다. 스냅샷 예산 트리거(ADR-0011 §2, 37척)가 앞당겨지지 않는다.
- 새 메시지는 **메시지 id 흐름**에서 id 를 꺼낸다(ADR-0006 §4a). 이동·채굴·판매 golden 은 한 바이트도 바뀌지 않는다.

### 7. 정지 경로 표(ADR-0013 §5a) — 추천안이면 분모가 변하지 않는다

- 추천안(광물 소멸, 크레딧 보존, 내구도·잔해 메모리)은 **새 테이블도 새 제약도 없다.** 마이그레이션 0005 가 없고 분모는 122 제약 + 트리거 4 그대로다.
- 다시 매기는 행:
  - `inventory_items_quantity_kg_check` 하한 0 — 파괴는 행을 **0 으로** 만들 뿐 그 아래로 내리지 않는다. 감소량은 그 시점 보유량 전부이고 클라이언트가 고를 수 없다(① 아니오).
  - `processed_commands_pkey` — 사격도 같은 키 공간이다(① 예, ② 월드 범위 기억, ③ 명령 종류 교차 재전송 테스트).
  - **비교 후 쓰기 #1**(CAS 0 행): 파괴가 인벤토리 행을 처음으로 "명령을 보낸 actor 가 아닌 actor" 쪽에서 바꾼다. 같은 tick 에 그 actor 의 판매와 파괴가 겹쳐도 K3 이 첫 기대값과 마지막 새 값으로 접는다. 그 경로를 테스트로 잰다(스펙 AC).
- 대안 B 를 택하면 0005(`wrecks`)의 제약 전부를 이름으로 이 표에 더하고 분모를 다시 센다. qa census 와 architect 독립 실측을 함께 한다(ADR-0013 §5a-1b 방식).

### 8. 결정성

- 판정과 피해에 무작위가 없다. 입력은 데이터 표(무기·함선), tick 시작 상태, 제출 순번이다.
- 재생성 위치는 ADR-0010 §4(시드 해시 + 간격 탐색)이다. 재생성 tick 은 파괴 tick + 상수다.
- 전투 규칙에 버전을 둔다: 무기 데이터 파일의 `combat_version`(`{id}@{n}`)을 모든 `SHIP_DAMAGED` 에 싣는다. golden 은 그 버전을 무기·원뿔 절의 정규화 해시와 고정 입력(거리·자세·내구도)의 판정표에 묶는다(ADR-0016 §4, ADR-0014 §5 와 같은 방식). 숫자를 바꾸고 버전을 올리지 않으면 golden 이 실패한다.

## 검토한 대안과 버린 이유

- **클라이언트 화면 기준 히트스캔(클라가 "맞았다" 를 보냄)**: 원칙 1 정면 위반. 명중 주장을 검증할 서버 상태가 없다.
- **지연 보상(서버가 클라가 본 tick 으로 되감아 판정)**: 클라이언트가 고르는 값(`view_tick`)을 판정 입력으로 믿어야 한다. 상한을 두어도 상한 안의 과거를 골라 쏘는 이득이 남는다. 함선마다 위치 이력 링도 필요하다. 다시 볼 조건: 사람 세션에서 "원뿔이 넓어 조준이 의미 없다" 와 "좁혀서 지연에 거부된다" 가 동시에 관측될 때.
- **서버 시뮬레이션 투사체**: 엔티티가 스냅샷에 들어간다(31척에서 예산 84 % — ADR-0011 §2). 스윕 충돌, 투사체 수명·소유, 비행 중 사수 파괴 처리가 필요하다. 지연 문제도 사라지지 않는다(앞을 겨냥해야 하고, 그 겨냥도 200 ms 과거 화면 위에서 한다). 1인 함선 무기 1종의 증명 대상이 아니다.
- **시드 난수 명중률(EVE 식 추적 공식)**: 결정적으로 만들 수는 있지만 재미 판단(무작위가 필요한가)이 먼저다. 지금은 "원뿔 안에 두는 조종 기술" 이 유일한 변수이고, 원칙 9 의 감사 비용이 0 이다. designer 가 필요성을 보이면 `combat_version` 을 올리고 시드 규약을 ADR 로 단다.
- **표적 없는 발사(서버가 원뿔 안 가장 가까운 함선을 고름)**: 어휘가 더 작다. 대신 거부 사유가 "아무도 없다" 하나로 뭉치고, p2 가 쓸 "누구를 겨냥했는가" 가 사라진다. 표적 지정을 둔다.
- **내구도를 `WORLD_SNAPSHOT` 에**: §6.
- **파괴를 새 도메인 타입(`SHIP_DESTROYED` 도메인판) + `SHIP_DESPAWNED` 생략**: 함선당 1쌍 불변식과 짝 검사 도구가 두 가지 끝을 알아야 한다. 이름도 역사 이벤트와 겹친다.
- **파괴 즉시 같은 tick 재생성(대기 없음)**: 함선 없는 세션이 생기지 않아 I-29 를 고치지 않아도 된다. 대신 같은 스폰 지점에서 바로 다시 죽는 순환이 생긴다(스폰 지점은 actor 마다 결정적이다 — ADR-0010 §4). 보호 시간만으로 막으면 "보호 중 재진입" 이라는 다른 착취가 생긴다.
- **크레딧 손실**: 화폐 총량 항등식에 소멸 항이 붙는다. 크레딧 사용처가 없는 지금(p1-03 Q1) 손실만 있으면 "번 것을 잃는다" 만 남는다.

## 결과

- 좋은 점: 서버가 자기 상태만으로 판정하고, 클라이언트의 위치·시각을 하나도 믿지 않는다. 판정은 순수 함수(무작위 없음)이고 golden 으로 묶인다. 파괴의 경제 효과는 기존 네 겹(기억·PK·배치 멱등·비교 후 쓰기) 위에 코드 추가 없이 얹힌다. 추천안에서는 새 테이블이 없고 정지 경로 분모가 바뀌지 않는다. 짝 불변식·이동 golden 이 그대로 유지된다.
- 감수할 점: 원뿔은 "가까이서 대충 겨눠도 맞는다" 는 관대함이 있다. 무기 감각의 상한이다. 동시 격추가 없고 제출 순번이 이긴다. 장부 행 증가율이 채굴의 수 배다. 재기동하면 내구도·잔해·재생성 대기가 사라진다(함선과 같은 운명).
- 다시 검토할 조건: (a) 무기 2종 이상 또는 투사체 무기 → 이 ADR 의 §1, (b) 함선 영속화 → §2·§4 의 화물칸 결정, (c) `processed_commands` 증가율이 측정상 100 만 행에 하루 안에 닿음 → ADR-0013 (b), (d) 지연 보상의 필요가 사람 세션에서 관측됨(위 "버린 대안"), (e) 잔해 회수(대안 B) 채택 → §4·§7.
