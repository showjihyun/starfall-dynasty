# STARFALL Spec — 기획안을 구현 가능한 문서로 바꾸는 규약

기획안 3개(약 6,400줄)는 제품 의도의 원천이지만 구현 지시서가 아니다. 이 스킬은 그 의도를 **이번 슬라이스에서 증명할 만큼만** 잘라, 서로 다른 에이전트가 같은 것을 만들 수 있게 문서화한다.

## 기획안 읽는 법

전체를 읽지 않는다. `references/gdd-index.md`에서 필요한 절을 찾고, 해당 파일을 `grep -n "^# {절 번호}\."`로 위치를 확인한 뒤 그 절만 Read(offset/limit)한다. 줄 번호는 문서가 수정되면 바뀌므로 색인의 줄 번호는 참고용이다.

## Phase 범위 게이트

요청을 받으면 현재 로드맵 Phase에 들어가는지 먼저 판단한다. 기획안이 가장 크게 경고하는 실패 원인이 범위 폭발이기 때문이다.

| 로드맵 Phase | 들어가는 것 | 아직 안 되는 것 | 종료 기준 |
|-------------|-----------|---------------|----------|
| **p0** 사전 제작 | 레포 구조 ADR, 계약 형식, Historical Event 스키마, 네트워킹 스파이크(WebSocket), Unity 렌더링·Rust 시뮬레이션 벤치마크, WebGL 가능성 확인 | 게임플레이 기능 | 30명 동시 접속 + 실시간 이벤트 기록 검증 |
| **p1** 코어 프로토타입 | 1 성계, 1 행성, 1인 함선, 이동, 채굴, 인벤토리, 거래, 기본 전투, 서버 판정, Historical Event | 길드, 정치, 대형 함선, 다수 성계 | 핵심 행동이 서버 판정 + 역사 기록으로 동작 |
| **p2** 역사 버티컬 슬라이스 | Historian, Archaeologist, Evidence, 사건 재구성, Chronicle, Biography, 수배·현상금, 사망 기록, 뉴스 | 연구 경쟁, 박물관, 위조 | "플레이어가 만든 사건을 다른 플레이어가 소비한다" |
| **p3** 소셜 월드 | 길드, 세력, 계약, 외교, 정치 영향력, 기관·박물관, 기자, 정보전 | 대규모 은하 | — |
| **p4** 은하 확장 | 수십~수백 성계, 절차적 자원, 탐험, 워프, 대형 함선, 함대전 | — | — |
| **p5** 지속형 MMO | 수천 성계, 영토, 국가, 대규모 전쟁 | — | — |

- 현재 Phase는 `_workspace/STATUS.md`의 가장 최근 완료 슬라이스로 판단한다. 기록이 없으면 p0이다.
- 요청이 앞선 Phase에 속하면 거절하지 말고 "현재 Phase에서 증명할 수 있는 축소안"을 만들어 사용자 확인을 받는다. 예: p1에서 "함대전" 요청 → "1인 함선 대 1인 함선 전투 + 전투 결과 Historical Event"로 축소.
- 기술 도입도 같다. MVP 스택(Unity 6, C#, URP, Rust, Tokio, Axum, WebSocket, PostgreSQL, Redis, Docker, OpenTelemetry, GitHub Actions) 밖의 기술은 측정 근거가 담긴 ADR이 있어야 한다.

## 설계 원칙 체크리스트

스펙 확정 전에 모두 확인하고, 아니라면 스펙에 이유를 적는다.

- [ ] 모든 상태 변경을 서버가 판정한다 (클라이언트 값 신뢰 없음)
- [ ] 돈·아이템 변경이 하나의 트랜잭션 + 도메인 이벤트로 기록된다
- [ ] 새 Historical Event 타입마다 중요도 레벨과 **후속 플레이 연결**("이 사건이 어떤 플레이를 만드는가")이 있다
- [ ] Fact / Claim / Interpretation이 섞이지 않는다
- [ ] 역사 기록이 수정·삭제되는 흐름이 없다
- [ ] 무작위 요소는 seed로 재현 가능하다
- [ ] LLM이 사실을 만들지 않는다
- [ ] "다른 플레이어가 이 행동의 흔적을 발견할 수 있는가?"에 답이 있다 (MVP 핵심 테스트)
- [ ] PC가 기준이고, WebGL 영향이 있으면 대체 경로가 적혀 있다

## 기능 스펙 템플릿 — `docs/specs/{slice-id}.md`

```markdown

- 로드맵 Phase: p{n}
- 근거 기획안 절: {예: GDD §36 MVP Scope, 역사엔진 §89 MVP Historical Events}

## 2. 플레이 흐름
번호 매긴 단계. 누가(플레이어 A/B/C, 서버) 무엇을 하는지.

## 3. 범위
- 포함:
- 제외(다음 슬라이스로):

## 4. 규칙과 불변식
- 서버 판정 규칙 (입력 → 검증 순서 → 결과)
- 불변식 (예: "한 command_id는 인벤토리를 최대 1회 변경한다")

## 5. 데이터 계약
- 새로 추가·변경되는 계약 파일 경로와 요지 (shape 자체는 contracts/에 있다)
- 도메인 이벤트 / Historical Event / REST / WebSocket 메시지 목록

## 6. 역사 연결
| Historical Event | 레벨 | 생성 조건 | 남는 증거 | 이어지는 플레이 |

## 7. 수용 기준
Given / When / Then. Then은 **관찰 가능한 증거**(DB 행, 이벤트, API 응답, 화면)로 쓴다.

## 8. 비기능 요구
성능 예산, 동시 접속 수, WebGL 고려.

## 9. 열린 질문
사용자 또는 다른 팀원의 결정이 필요한 것. 추측으로 채우지 않는다.
```

## ADR 템플릿 — `docs/adr/NNNN-{kebab}.md`

되돌리기 어렵거나 여러 레이어에 영향을 주는 결정만 ADR로 남긴다 (레포 구조, 계약 형식, 전송 프로토콜, 새 인프라 도입, 절대 원칙 예외).

```markdown
# NNNN. {결정 제목}
- 상태: proposed | accepted | superseded by NNNN
- 날짜:
## 맥락
## 결정
## 검토한 대안과 버린 이유
## 결과 (좋은 점 / 감수할 점 / 다시 검토할 조건)
```

부트스트랩 슬라이스(p0-01)에서 최소한 다음 ADR을 쓴다: 0001 레포·모듈 구조, 0002 계약 형식과 코드 생성 방식, 0003 로컬 개발 환경(Docker compose, 툴체인 버전 고정).

## 작업 분해 — `_workspace/{slice-id}/01_architect_tasks.md`

```markdown
# {slice-id} 태스크

| ID | 태스크 | 담당 | 수정 경로 | 선행 | 관련 수용 기준 |
|----|-------|------|---------|------|--------------|
| T1 | 채굴 명령 검증·처리 | server | server/crates/sim/src/mining/** | — | AC-1, AC-2 |
| T2 | MINERAL_DISCOVERED 판정 | history | server/crates/history/src/detector/** | T1의 이벤트 발행 인터페이스 합의 | AC-3 |
| T3 | 채굴 UI·요청 | client | client/Assets/_Project/Scripts/Mining/** | 계약 확정 | AC-4 |
```

규칙: 한 태스크 = 한 담당자 = 겹치지 않는 경로. 두 담당자가 같은 파일을 고쳐야 하면 태스크를 쪼개거나 인터페이스를 먼저 정하는 태스크를 앞에 둔다.
