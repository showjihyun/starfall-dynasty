# 역할별 모델 배정 근거

- 결정: 2026-09-19 (사용자 지시)
- 적용: 구현 역할(`server`, `history`, `client`, `techart`)은 **Sonnet 5**, 판단 역할(`architect`, `designer`, `qa`)은 **Opus 5**
- 예외: 아래 §3

## 1. 왜 이렇게 나누나

일의 성격이 다르다.

| | 판단 역할 | 구현 역할 |
|---|---|---|
| 목표 | 스스로 정의해야 한다 | 스펙·스프린트 계약으로 이미 고정돼 있다 |
| 오답 신호 | 없다. 틀린 스펙도 문법은 멀쩡하다 | 즉시 온다. 컴파일, `clippy -D warnings`, 테스트, fixture 왕복, 커버리지 스크립트 |
| 오류의 전파 | 아래 모든 단계로 번진다 | 해당 파일에 갇히고 QA 평가에서 잡힌다 |
| 되돌리는 비용 | 스펙 개정 → 계약 개정 → 재구현 | 고치고 다시 테스트 |

이 하네스는 **구현 전에 완료 기준을 합의**하도록 설계돼 있다(Phase 3 스프린트 계약). 그래서 구현 역할이 받는 것은 "알아서 잘 만들어라"가 아니라 "이 명령이 이 출력을 내면 완료"라는 74개짜리 항목표다. 판단의 폭이 좁고 피드백이 빠른 작업이다.

TDD가 이 배정의 전제다. 검증 항목을 실패하는 테스트로 먼저 만들면(red) 모델이 추측할 여지가 더 줄고, 틀렸을 때 즉시 드러난다.

## 2. 관측된 근거 (p0-01, p0-02)

**구현 역할의 산출물은 대부분 정밀한 기준의 기계적 번역이었다.** 서버 구현은 스프린트 계약 SC-01~37을, 클라이언트는 SC-38~51을 항목별로 따라갔고, 계약 변경 요청은 양쪽 모두 0건이었다.

**자원 소모가 크다.** 에이전트 1회 실행당 토큰(알림에 기록된 값): 구현 669K / 522K / 418K / 327K, 판단 552K / 504K / 451K / 440K. 이틀간 **사용량 한도 3회**(02:40, 17:10 리셋), 로그인 만료 1회, 스트림 정지 1회로 작업이 끊겼다. 구현 역할을 Sonnet으로 내리면 같은 예산으로 더 많은 슬라이스를 돌 수 있다.

**판단 역할을 내리면 안 되는 이유도 관측됐다.** 이번 슬라이스에서 값을 만든 것은 대부분 "검사처럼 보이지만 아무것도 검사하지 않는 것"을 알아본 순간이었다:
- `ws_connections == opened − closed`(항등식), `tick_skipped_total == 0`(항진명제) — 코드가 어떻게 틀려도 통과
- 백로그가 0이 될 때까지 폴링 — 정상 서버에서 영영 끝나지 않음
- 봇이 서버의 타입을 공유하면 두 출처가 사이좋게 틀림(I-25의 출발점)
- fixture 개수를 검증기로 세어 놓고 요약에서 잘못 더함

이 발견들은 테스트가 알려주지 않는다. 기준 자체를 의심해야 나온다. 그래서 스펙·계약·평가는 Opus에 둔다.

## 3. 예외 — 호출 시 모델을 올리는 경우

Agent 도구 호출의 `model`은 에이전트 정의보다 우선한다. 다음 두 경우는 구현 역할이라도 **`model: "opus"`를 명시**한다.

| 상황 | 이유 |
|------|------|
| **Phase 2 스펙·ADR 검토** (구현자가 리뷰어로 들어갈 때) | 이때의 산출물은 코드가 아니라 판단이다. p0-01·p0-02의 차단 요소 8건이 전부 이 단계에서 나왔다: tick 재개 시 이벤트 유실, Windows 타이머로 성능 게이트 100% 실패, 실행 불가능한 테스트 명령, 항진명제 검사 |
| **BUG 유형 진단** (`diagnose` 스킬 경로) | 증상에서 원인을 좁히는 일은 목표가 고정돼 있지 않다 |

즉 **"코드를 쓸 때는 Sonnet, 기준을 의심할 때는 Opus"**가 실제 규칙이다.

## 4. 재검토 조건

다음이 관측되면 해당 역할을 Opus로 되돌리고 이 문서에 기록한다.

- QA 평가에서 **스펙·계약을 잘못 읽어서 생긴 FAIL이 한 슬라이스에 2건 이상** 나올 때
- 구현 역할이 자기 영역의 **환경 함정을 놓쳐** QA가 대신 발견하는 일이 반복될 때(예: 타이머 해상도, 포트 점유, 기존 볼륨)
- 같은 지적을 받고 **2라운드 안에 고치지 못할** 때
- 반대로, Sonnet 구현이 3개 슬라이스 연속으로 FAIL 0건이면 이 배정을 기본값으로 굳히고 Opus 예외 범위를 줄인다

첫 적용은 `p0-02` 이후의 슬라이스다. p0-02는 전 역할이 Opus로 진행됐으므로, 다음 슬라이스의 QA 리포트가 비교 기준이 된다.
