# QA 처리량 — 평가가 일주일 걸리지 않게 하는 규칙

2026-10-03, p1-02-mining 회고에서 만든 문서다. Phase 4 착수(09-27)부터 Phase 5 r2 진행 중(10-03)까지 약 1주일이 걸렸다. 그런데 실제로 판정에 쓴 시간은 그중 일부였고, 나머지는 아래 다섯 가지로 새어 나갔다.

## 1. 어디서 시간이 샜나 (p1-02 실측, 파일 mtime 기준 KST)

| 구간 | 걸린 시간 | 실제 작업 | 샌 이유 |
|---|---|---|---|
| Phase 2~3 (스펙·계약) | 약 9시간 | 대부분 작업 | — |
| Phase 4 (구현 + 점진 QA) | 약 3일 | 구현 | 사용량 한도로 전원 정지 2회 |
| r1 판정 | 약 13시간 | 봇 전 케이스 약 1.5시간 | 사용량 한도, 완료 알림 대기 |
| r1 FAIL 수정 | 약 30분 | 수정 | — |
| r1 수정 → r2 시작 | **약 2.9일** | 거의 없음 | 사용량 한도 뒤 아무도 재개하지 않음. 변이 증거 방식·이름 정합·원복 증명을 두고 왕복 |
| r2 부하 → 다음 단계 | **3.5시간** | 0 | qa가 백그라운드 완료 알림을 놓치고 대기 |
| r2 게이트 → 다음 단계 | 멈춤 | 0 | 같은 이유 반복 |

다섯 가지 누수:
1. **턴 사이 대기** — 에이전트가 백그라운드 실행을 띄우고 "알림이 오면 이어서"로 턴을 끝낸다. 알림을 놓치면 몇 시간씩 멈춘다.
2. **재개 신호 부재** — 사용량 한도가 풀려도 사용자가 "이어서"를 칠 때까지 아무도 움직이지 않는다. 그 사이 재개 지점이 메시지에만 있어서, 재개할 때마다 리더가 상황을 다시 맞춘다.
3. **r1에서야 드러나는 결함** — r1 FAIL 7건은 전부 테스트가 없거나, 이름이 계약과 다르거나, 도구가 없는 것이었다. 실행 동작 결함은 0건이었다. 모두 모듈 완료 시점에 기계적으로 잡을 수 있었다.
4. **증거 기준의 사후 확정** — "변이는 기대값이 아니라 구현을 망가뜨린다", "원복은 git diff가 아니라 sha256", "기대값은 출력과 독립된 출처" 같은 기준이 FAIL 뒤에 하나씩 정해졌다. 그때마다 수정 → 재확인 왕복이 생겼다.
5. **수작업 재판정과 장수 에이전트** — r2가 다시 사람 손으로 114항목을 훑었다. qa는 6일 동안 한 대화를 이어 써서 맥락이 비대해졌다. 메시지 교차와 알림 누락이 늘었다.

## 2. 규칙

### R1. 턴 사이에 기다리지 않는다 (qa·구현자 공통)
- 오래 걸리는 실행은 **한 번의 명령으로 끝까지 도는 스크립트**로 만들고, 같은 턴 안에서 결과 파일이 생길 때까지 확인 루프(Monitor 또는 `until` 루프)로 기다린 뒤 다음 단계로 넘어간다.
- "완료 알림이 오면 이어서 하겠다"로 턴을 끝내지 않는다. 알림은 보조 신호일 뿐이다.
- 한 턴에서 끝낼 수 없을 만큼 길면(20분 초과), 그 사실과 결과 파일 경로를 `RESUME.md`에 적고 끝낸다.

### R2. 재개 지점은 파일에 둔다
- 리더는 Phase가 바뀔 때, qa는 라운드 단계가 바뀔 때마다 `_workspace/{slice}/RESUME.md`를 덮어쓴다. 형식: 현재 단계, 끝난 단계와 증거 경로, 다음 명령 한 줄, 기다리는 사람.
- 사용량 한도 뒤 재개하면 리더는 `RESUME.md`부터 읽고, 메시지를 다시 맞추지 않는다.

### R3. 모듈 완료 = 계약 자기 점검 통과 (Phase 4, 구현자)
구현자가 "모듈 완료"를 보내기 전에 자기 담당 SC 각각에 대해 아래를 `03_*_impl.md`에 표로 남긴다. qa는 모듈 완료 알림을 받으면 이 표를 실행으로 확인한다. r1에서 처음 보는 일이 없게 하는 것이 목적이다.
1. **이름 실행 확인** — 계약 방법 칸의 테스트 이름·필터 그대로 `cargo test <필터>`(또는 Unity `--filter`)를 돌려 1건 이상 실행되고, 다른 SC의 테스트가 섞이지 않는다. 출력 발췌를 붙인다.
2. **구현 변이** — 구현 코드를 잠깐 망가뜨려 그 테스트가 실패하는지 보인다. 기대값·단언을 바꾸는 것은 변이가 아니다. 변이 위치, 실패 출력, 원복 뒤 초록을 남긴다.
3. **원복 증명** — 변이를 건 파일마다 변이 전·원복 후 sha256이 같다. 이 슬라이스 변경이 커밋 전이거나 파일이 untracked면 `git diff`로는 원복을 증명할 수 없다.
4. **도구 존재** — 계약이 지명한 바이너리·스크립트·카운터가 실제로 있다.
5. **DB 테스트 이름** — `TestDb::create`에 계약 이름 그대로 넘긴다(모듈 경로 접두사 금지).

### R4. 계약에서 미리 막을 것 (Phase 3, qa)
- 수치 ⊘(유효 조건)마다 **도달 가능성 계산**을 한 줄 적는다. 예: "광맥 총 매장 59 t, 회당 25~200 kg → 10분 수락 최대 약 390회". 닿을 수 없으면 계약을 그때 고친다.
- 테스트 이름은 실제 cargo 필터로 잡히는 형태로 적는다. `mining::X`는 `mining_tests::X`를 잡지 못한다(부분 문자열 매칭).
- 기대값 열은 테스트 출력과 독립된 출처(스펙 예측, fixture 설계 의도)에서 온다. 출력을 옮겨 적은 기대값은 아무것도 재지 않는다.
- 위 R3의 증거 형식을 계약 §0에 그대로 적어 둔다. 기준이 사후에 정해지면 왕복이 생긴다.

### R5. 라운드는 자동 실행기 한 번으로 돈다 (Phase 5, qa)
- qa는 Phase 4 동안 `tests/e2e/run_round.py`(슬라이스 공용)를 만든다. 한 번 실행으로 게이트, census, 반복 실행, 실서버 봇 전 케이스, 파이썬 판정, Unity, 해시 대조를 순서대로 돌리고 `evidence/r{N}/summary.json`에 항목별 판정을 쓴다. 사람 판단이 필요한 단계 앞에서만 멈춘다(DB 정지 공지, 사람 세션).
- 리포트는 이 summary를 보고 쓴다. 에이전트가 단계마다 손으로 명령을 치지 않는다.
- r2 이후의 **판정 대상**은 FAIL·미검증 항목과, 고친 파일에 걸린 항목이다(SC → 파일 경로 대응표로 뽑는다). 나머지는 실행기의 자동 회귀가 덮는다. 회귀가 깨진 항목만 사람이 다시 본다.

### R6. 동결은 파일 표지와 감시로 한다
- 동결은 `_workspace/{slice}/FREEZE` 파일로 건다(시작 시각, HEAD, 범위). 팀원은 편집 전에 이 파일을 확인한다. 있으면 편집하지 않는다.
- qa의 실행기는 소스 해시 스냅샷과 15초 감시(Unity·cargo 프로세스, 소스 mtime)를 돈다. 위반이 보이면 그 실행을 무효로 표시하고 계속한다.
- 리더가 팀원마다 동결 공지를 보내고 확인을 받는 왕복은 하지 않는다. 시작과 해제만 한 줄씩 알린다.

### R7. 에이전트 수명을 제한한다
- 구현자는 자기 태스크가 끝나면 종료한다. FAIL이 나오면 그때 `03_*_impl.md`를 인계로 새로 띄운다.
- qa는 **라운드마다 새로 띄운다.** 이전 qa는 `RESUME.md`와 리포트·증거 경로를 남기고 종료한다. 한 대화를 며칠씩 이어 쓰면 맥락이 비대해지고 알림을 놓친다.
- 팀원 교체는 `messaging-stopped-teammate-resumes-it` 메모리의 순서를 따른다(옛 에이전트 종료 확인 → 새 이름과 금지 이름 공지 → 태스크 담당 재확인).

### R8. 메시지 한 번, 한 곳
- 같은 결과를 리더와 qa에게 따로 쓰지 않는다. 결과는 파일(`03_*`, `04_*`, `evidence/`)에 쓰고, 메시지는 경로와 한 줄 요약만 보낸다.
- 리더는 결정만 보낸다. 팀원 사이의 사실 전달을 중계하지 않는다.
